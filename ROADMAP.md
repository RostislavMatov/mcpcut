**2026-09-03 — ADR-0011: пилотов и трека B не будет, продукт выходит открытым кодом под Apache-2.0.** Строки про партнёров ниже сохранены как история; актуальный «следующий шаг» — публикация санированной копии и работа по issues.

Горизонт: MVP «ядро + admin UI» → ~~пилоты с design-партнёрами~~ открытый релиз (ADR-0011). Оценка: **~12 недель** от старта кода (ориентир: старт середина августа 2026 → pilot-ready к началу ноября 2026). Недели — относительные, сдвигаются от фактического старта.

Работа идёт в два параллельных трека. Кодовый трек без партнёрского не имеет смысла — валидация гипотезы требует пилотов.

### Почему M4.5 вклинился перед M5

Замеры 2026-08-13 (в ADR-0006, воспроизводимые скрипты переносятся в репозиторий первой волной) показали, что хеш-цепочка M5 на текущей раскладке не строится честно: она требует атомарного «прочитать предыдущее звено — записать следующее», а сегодня каждая сессия пишет свой JSONL из своего процесса. Глобальная цепочка потребовала бы общего лока на каждую запись — 553 зап/с (измеренный потолок `store.update` при 8 конкурирующих процессах) против 18 387 rec/с текущего журнала. Цепочка «на файл» доказывает только порядок внутри файла: **удаление целого файла сессии не обнаруживается ничем**.

**Гейт пройден 2026-08-13** прямым прогоном на версиях CI-матрицы (бинарники nodejs.org): v20.20.2 — модуля нет (`ERR_UNKNOWN_BUILTIN_MODULE`), v22.23.2 — работает без флага (но без класса `Session`), v24.19.0 — полный API включая `Session`. Решение: **пол рантайма — Node 24 LTS** (20.x вышел из поддержки в апреле 2026); `engines: >=24`, CI-матрица `['24']`, `@types/node@24`. Весь сьют (2 579 тестов) + lint + build прогнаны под v24.19.0 — зелёные. ADR-0006 переведён в «принято».

Попутно поглощаются четыре пункта бэклога ниже: окно CAS при `rename`, кэш `agents.json` по mtime, retention `approvals/resolved` и истории дескрипторов, а также долговечность записи (fail-open журнала закрывается частично — политика поведения при отказе записи остаётся решением M5).

### Технический бэклог из ревью M1 (решить в рамках M2/M5)

Осознанно отложенные находки ревью (все CRITICAL/HIGH и большинство MEDIUM/LOW закрыты в M1):

- **Политика fail-open журнала** (M2): при постоянных ошибках записи прокси продолжает ретранслировать без журнала и выходит с кодом 0. Для enterprise-сегмента нужен конфигурируемый fail-closed (убить child, ненулевой код) + счётчик потерянных записей.
- **Child имеет write-доступ к своему журналу** — **частично закрыто в M5**: hash-цепочка + подписанная Ed25519 глава + оффлайн-проверяемый экспорт делают переписывание **обнаружимым** — но только против якоря, записанного вне хоста: процесс под тем же uid перепишет цепочку целиком и переподпишет её тем же ключом. Открытым остаётся именно предотвращение: отдельный uid писателя, append-only атрибут, отгрузка off-box — кандидаты после пилотов (ADR-0007, «модель угроз»).
- **JSON-RPC batch** классифицируется как `invalid` (осознанно, зафиксировано тестом) — пересмотреть при переходе на спеку 2026-07-28.
- Мелкое: shallow `Object.freeze` записей (payload мутабелен), UTF-8-разрыв на границе overflow-флаша (достижим только через capped-путь).

**Осознанные решения, о которых стоит помнить:**

- **Членство хранится в документе группы**, а не полем `memberOf` у агента (уточнение G3): инвариант «группу с членами не удалить» проверяется и пишется одним CAS одного документа, а `agents.json` остаётся байт-в-байт прежним — этим гейт «агент без групп ведёт себя как до M5.5» верен тривиально.
- **Персональный грант перекрывает группу целиком** (G2, вопреки рекомендации плана этапа): добавление узкого персонального гранта **сужает** эффективные права члена группы. UI обязан говорить это словом («overrides group:x»), иначе правило откроется на проде.
- **Каскад `server remove` не атомарен** — три документа, три независимых CAS; крах между шагами оставляет висячий грант (то же состояние, что было всегда до этого захода). Починка описана механизмом, а не надеждой (ADR-0010 §5): половины каскада изолированы друг от друга, запись `access-edit` несёт поле `cascade: { agents, groups }` со словом `done`/`failed` по каждой, а повтор `server remove` на уже незарегистрированном имени **подчищает висячие гранты** и печатает `pruned dangling grants: N agent grants, M groups` (выход 0); `server add` на имя, которое кто-то ещё раздаёт, предупреждает.
- **`server remove` без `MCP_ADMIN_TOKEN`** пишет запись с `actor.adminName: null` и предупреждением на stderr, а не отказывает: команда старше именных админов и живёт в скриптах. Паритет с `policy set` — одна строка, но это правка ADR-0010.

**Хвосты в бэклог:**

- **Журналирование персональных `agent grant/ungrant/revoke`** — сейчас только stderr-аудит; в `access-edit` идут только операции групп и каскад `server remove`. Расширение категории — отдельное решение с ответом «что это делает с объёмом отчёта».
- **Отзыв доступа у одного члена группы** не выражается в модели, которая только расширяет: нужен либо персональный грант, либо правило политики. Если пилот попросит — это вычитающая семантика и правка ADR-0010.
- **Вложенные группы** — резолвер одноуровневый намеренно (обход графа + вопрос «чей грант победил»).
- **Скоуп ролей по группам** («этот owner правит только эти группы») — ролевая модель остаётся одномерной (ADR-0004).
- **Экран Groups из дизайна** переносится языком, не моделью: там группа — эндпоинт с объединением тулзов, здесь — носитель прав. Расхождение зафиксировано, не устранено.

**Хвосты ревью (волна 4) — ЗАКРЫТЫ решениями владельца T1–T5 (2026-09-01).** Формулировки решений —
в ADR-0010, блок «Решения владельца 2026-09-01 (T1–T5)»; поправка ролевой таблицы — в ADR-0004
(2026-09-01). Что стало с каждым пунктом:

1. **Расширяющий `agent ungrant` → T1 + T4.** Персональные гранты теперь журналируются
   (`access-edit` с `agent.create|grant|ungrant|revoke`), а сама команда требует owner-токена.
   Запись у расширяющего снятия — обычная `agent.ungrant`; `[warn]` остался.
2. **`group grant` без `--tools` → T2.** Флаг стал обязательным для групп: отсутствие — ошибка
   использования с именем флага, код 1. `--tools '*'` — явный способ выдать всё. У `agent grant`
   дефолт сохранён.
3. **Паритет предупреждения `server add` в UI → T3.** Drawer регистрации показывает то же
   «имя уже кому-то роздано» (правка UI-поверхности).
4. **Порог `/agents/*` → T4.** Поднят с `operator` до `owner`, CLI `agent *` впервые требует
   `MCP_ADMIN_TOKEN`. Обоснование переписано не на радиус, а на направление: персональный грант —
   сужающий инструмент (G2), поэтому его снятие расширяет доступ.
5. **Ремонт на `not-found` в `server remove` → T5.** Убран: неизвестное имя — отказ (код 1) без
   единой записи, с подсказкой о висячих грантах; починка живёт в явном `--prune-grants`.

Исходные формулировки хвостов (для истории):

1. **`agent ungrant` на перекрывающей строке РАСШИРЯЕТ эффективные права.** Снятие персонального гранта у члена группы возвращает грант группы (G2 наоборот): команда, которая называется «отнять», может дать больше. Сейчас UI подтверждает это интерстишелом, а CLI печатает предупреждение. Открыто: должна ли эта правка ещё и **писать `access-edit`** — сегодня персональные `agent grant/ungrant/revoke` в журнал не идут вовсе (см. хвост про журналирование выше), и решать это надо одним ответом на оба.
2. **`group grant` без `--tools` выдаёт `'*'` сразу N членам.** Асимметричный дефолт унаследован от `agent grant` (там же он оправдан: один агент, один оператор, одно решение). У группы цена ошибки умножается на число членов. Открыто: оставить дефолт ради паритета одной формы гранта (G1) или требовать явный `--tools` именно для групп.
3. **Паритет предупреждения `server add` в UI.** CLI после успешной регистрации имени, которое всё ещё кто-то раздаёт, печатает `[warn] "x" is already granted to N agents and M groups from an earlier registration`. В UI (`/servers`, drawer регистрации) такого предупреждения пока нет — это отдельная правка UI-поверхности.
4. **Порог роли `/agents/grant` и `/agents/ungrant` — `operator`, а не `owner`.** Таблица маршрутов (`src/ui/authz.ts:74-76`) отдаёт правку персональной матрицы прав `operator`'у, а CLI `agent grant/ungrant` вообще не требует токена. При этом ADR-0010 §4 и §«Риски» опираются на утверждение «`agent grant` уже owner-only», обосновывая им owner-порог групп. Тексты приведены к фактам (правка 2026-08-31), но **сам порог не менялся** — это решение владельца: либо поднять `/agents/*` до `owner` и завести токен для CLI `agent grant`, либо признать `operator` достаточным и переписать обоснование G4 на «группа = массовая правка, поэтому строже».
5. **Ремонт висячих грантов на `not-found` в CLI `server remove`.** `repairDanglingGrants` (`src/cli/server-cmd.ts:301-302`) на незарегистрированном имени прогоняет обе половины каскада и пишет `access-edit`, то есть `server remove` на неизвестном имени — не только чтение. UI приведён к тому же поведению (правка 2026-08-31, паритет F2c), но **сама семантика не подтверждена владельцем**: альтернатива — отдельная команда `server repair <name>`, чтобы «удалить» и «починить» не назывались одним словом.

### Страница журнала по `Journal.dc.html` (закрыто 2026-08-28)

Заход по запросу владельца: догнать `/journal` до экрана `Journal.dc.html` дизайн-проекта. Сделано: в шапке панели — вкладки `Sessions`/`Records`, где **`Records` — новый сквозной поток записей всех сессий** (`/journal?view=records`; до этого сквозной вид открывался только текстовым поиском, то есть «показать всё подряд за период» было недоступно); строка фильтров дополнена **агентом** (нативный `<select>`, варианты — из реестра агентов, а не из записей: агент, который ещё не действовал, тоже должен выбираться) и **периодом** (пресеты `24h/7d/30d`, календарь, `All`, `Done`). Штамп времени — `Aug 27 26 09:02:11` (полный ISO остался в `title`), колонка `Lat` теперь безусловна (`—` там, где замера нет), пейджер и вкладки несут применённые фильтры. Фильтры `agentName`/`from`/`to` добавлены в `search-filters.ts`, поэтому их получили оба плеча чтения сразу. Смок `docs/smoke-journal-dc.md`, скриншоты `docs/design/mcpcut/journal-*.png`.

**Как период-пикер работает без JS.** В дизайне это JS-попап с состоянием в компоненте. Здесь его ячейки — **submit-кнопки формы фильтров**: день шлёт `pick=<день>`, пресет `period=24h|7d|30d|all`, стрелки месяца `pmnav=<месяц>`, `Done` — `close=1`; свёртка в `from`/`to` (правило дизайна `setPeriod`: первый клик начинает период, второй закрывает, клик раньше начала меняет концы местами) живёт на сервере в `src/ui/handlers/journal-query.ts`. Сабмит формы, а не ссылка, выбран сознательно: **набранный, но не применённый текст фильтров переживает клик по дню**. Попап остаётся открытым между кликами, потому что обработчик открывает его на любом из этих параметров без `close`; месяц календаря едет скрытым `pm`, чтобы стрелки не откатывались следующим кликом.

**Осознанно НЕ перенесено:**

- **Кастомная выпадашка агента** — у нас нативный `<select>` в той же коробке (2px рамка, каретка, белая при выбранном значении). В дизайне список кастомный, потому что в Claude Design нативный `select` не стилизуется; нативный работает без JS и с клавиатуры и участвует в сабмите наравне с текстовыми полями (попап на ссылках терял бы набранный текст).
- **Агент в строке фильтров списка сессий.** Дизайн отвечает на него, пробегая свой in-memory массив записей; на сервере это значило бы читать записи каждой сессии, чтобы нарисовать список. Список сужается только тем, что знает строка сводки: id и промежуток активности (период — по пересечению, а не по вложенности).
- **Пейджер у вкладки `Records`.** Сквозной обход ограничен потолками (файлы/байты/дедлайн) и не имеет offset'а: «страница 2» была бы обещанием, которого читающий слой не даёт. Вместо него — счётчик `all sessions · N shown` и штатный баннер усечения.

**Хвосты в бэклог:**

- **Пейджинг сквозного вида** — если пилот упрётся в «первые N записей», это запрос на offset/курсор в `searchAllSessions`, а не на UI-костыль.
- **Закрытие попапа по `Escape` и кликом по фону** — в дизайне их делает JS-обработчик; у нас закрывают `Done`, повторный клик по кнопке периода или любой сабмит. Просится как progressive enhancement в `app-js.ts`.
- **`pick`/`pmnav` остаются в URL после свёртки** (результат уже в `from`/`to`, повторное применение идемпотентно, но URL читается хуже). Лечится редиректом на канонический URL — не делали, чтобы не плодить 303 на каждый клик по дню.
- **Узкий экран (< 820 px)** — правила есть, глазами не смотрели.
- **Firefox/WebKit-плечо** — как и во всех прошлых смоках, не прогонялось (Chromium headless shell).

### Технический бэклог из смока 2026-08-25 (карантин в UI, wrap вне реестра)

- **`wrap` принимает любую метку `--server <name>` без сверки с реестром** — трафик, заявки, карантин и журнал ключуются этой меткой, а `/servers` в админке показывает только реестр: сервер «есть в очереди, но нет в списке» (обнаружено на dogfood-конфиге `.mcp.json`: `playwright`/`memory` шли через `wrap`, в реестре был только `github`). Закрыто на этой установке регистрацией под теми же именами (`server add`, инвентарь подхватился по ключу). Решить продуктово до M6: (а) `wrap` предупреждает/отказывает для незарегистрированного имени, или (б) `/servers` показывает «незарегистрированные» имена из инвентаря/журнала как призрачные строки. Без решения пилот может получить ту же «невидимую» заявку.
- **Контракт «скриптовая форма постит свои поля»** закрыт тестом в `tests/ui/page-contracts.test.ts` (карантин approve/reject отправлял пустое тело → 400 с волны 2 M4; браузерные смоки M4/UI-hardening этот путь не покрыли — в чек-лист смока добавить клик по approve/reject карантина при следующем смоке UI).
- **Approve/reject в карантине перезагружал страницу** (25.08): `app-js.ts` после любого 2xx делал `location.reload()`. Закрыто: действие внутри региона с `data-live-settle` перерисовывает регион (счётчики вне его — `data-live-text`), поколения `refreshRegion` защищают от гонки со SSE-вотчером, `setBusy` гасит кнопки формы (раньше `disabled` вешался на `<form>` и не блокировал ничего). Смок — headless Chromium скриптом. **Остаток**: дашборд `/` оставлен на reload намеренно — тайлы, «last decisions» и полоса серверов лежат вне региона очереди и без перезагрузки протухали бы. «Полностью живой» дашборд (несколько регионов или один общий с сохранением состояния `<details>`/фильтра) — отдельная работа, решить перед M6 по итогам пилота: сколько одобрений делают с `/`, а не с очереди.

- **Сирота `connect`/`wrap` при смерти клиента крутился на 100 % CPU и не реагировал на SIGTERM** (найден 25.08: процесс смока 22.08 прожил ~3 дня на ядре). Механизм: клиентский процесс умер → `process.stderr` (труба к нему) даёт EPIPE → сплайс stderr сервера ловит `'error'` и сообщает через `onDiagnostic` → запись в тот же `process.stderr` → EPIPE → … Stdio-потоки Node не уничтожаются (`destroy` — no-op), ошибка переизлучается через `nextTick`, event loop не доходит до poll-фазы, JS-обработчик SIGTERM (форвардинг сигнала в дочерний процесс) не выполняется. Закрыто `proxy/diagnostics.ts` (`guardDiagnostics`: диагностика замолкает после первого `'error'` цели; подключено в `connect`, `wrap` и `serve`, тест с контрольным «убеганием»). Сквозная проверка: после фикса сирота завершается сам ≤ 2 с. **Остаток**: общее свойство прокси — при установленном форвардинге сигналов процесс выходит только через конец сессии, т.е. любая будущая синхронная петля снова «съест» SIGTERM.

### Требования к M5 из внешних обсуждений

Вход не от аудитора, а от смежного вендора (основатель ECZ-ID, тред `python-sdk#1705`, 2026-08-11) — это дизайн-вход, не валидация формата отчёта; интервью с практикующим аудитором (открытый вопрос PRD) он не заменяет.

- **Разделить в контракте экспорта целостность записи и текущую авторитетность.** Хеш-цепочка доказывает релаинг-парти, что полученная история решений не изменена задним числом. Она **не** отвечает на вопрос, является ли субъект, политика или оператор в этой записи текущим авторитетом. Три слоя держим раздельно: enforcement (что разрешено/заблокировано) → receipt/export (что произошло и цела ли запись) → resolvable current state (что считать авторитетным сейчас). Практическое следствие: экспорт обязан нести явный as-of и **не должен** формулироваться как утверждение о текущих правах.
- **Пинить провенанс решения в самой записи** (предпосылка предыдущего пункта, правка `DecisionInfo`): сегодня решение несёт `rule` строкой, но не отпечаток эффективной политики и матрицы грантов на момент решения. Даже с цепочкой хешей релаинг-парти не сможет ответить «по какой редакции правил это было разрешено» и не сможет её воспроизвести. Добавить `policyHash` и `grantsHash` (канонический хеш эффективного документа политики и матрицы грантов — механика уже есть в `src/policy/hash.ts`). Делать до подписи записей, иначе цепочка зафиксирует записи без провенанса.
- **«Кто на самом деле нажал approve» — открытый вопрос по `approvals approve`** (вход из dogfood-контура смока 2026-08-16, находка 9 `docs/smoke-ui-hardening.md`). Текст отказа, возвращаемый **заблокированному агенту**, содержал готовую команду `mcpcut approvals approve <id>`: инструкция снятия блокировки доставлялась ровно той стороне, которую блокируют. Строку из кода убирают в этом заходе — но дизайн-вопрос остаётся открытым и относится к M5: (а) должен ли `approvals approve` требовать контекст, недоступный агентскому процессу — сегодня агент с доступом к shell под тем же uid одобряет себя сам, и гарантия human-in-the-loop держится не на механизме, а на его нежелании набрать команду; (б) **разрыв атрибуции**: UI и CLI-путь одобрения проставляют `actor` (админа), а `approvals approve` из shell не даёт `actor` вовсе. Это та же тема, что `policyHash`/`grantsHash` выше: запись решения должна отвечать не только «по какой редакции правил», но и «кем» — иначе подписанная цепочка зафиксирует одобрение без субъекта. Смежно: ADR-0004 в разделе «От чего НЕ защищаемся» этот случай не называл (там только компрометация хоста/uid, а здесь агент под тем же uid работает штатно) — кандидат на правку ADR. **Закрыто частично в M5, волна 2 (решение владельца O3, поправка ADR-0004 от 2026-08-18):** (б) закрыт — `approvals approve|deny` требует персональный админ-токен (`MCP_ADMIN_TOKEN`), резолюция несёт `actor: 'cli:<adminName>'`, и минимальная роль на CLI та же, что на HTTP-маршруте (`operator`, общая константа `APPROVAL_RESOLVE_MIN_ROLE`). (а) **остаётся открытым**: токен даёт атрибуцию, а не барьер — процесс под тем же uid читает его из окружения, и гарантия human-in-the-loop против такого агента остаётся организационной. Технические кандидаты (отдельный uid одобряющей поверхности, внеполосное подтверждение) — после пилотов.
- **Resolver/authority-система — вне периметра.** Третий слой (кто авторитетен сейчас) мы не строим: это чужой продукт и чужая ответственность. Наш экспорт должен композироваться с внешним резолвером, не подменять его и не тащить приватные входы, из которых получено исходное решение.

### Отложенное исполнение write-intents + уведомления (идея 2026-08-13; кандидат после M5, решение по данным пилотов)

Мотивирующий сценарий: ассистент записывает заказ клиента в CRM через плоскость и ловит таймаут (очередь одобрений или медленный апстрим) — сегодня агент получает ошибку с инструкцией ретрая, а конечный пользователь слышит «попробуйте позже». Не «кафка для MCP» (брокер, оффсеты, гарантии доставки не нужны: заявки уже durable-очередь write-intents с полными `args`, журнал уже append-only лог), а три фичи поверх существующего:

- **Ключевой инвариант границы**: прокси — единственная точка системы, знающая, был ли вызов отправлен апстриму. Отложенно исполнять можно **только не-отправленное** (застряло на одобрении/политике/недоступности сервера); случай «отправлено, ответ потерян» не переигрывается без идемпотентного ключа на стороне тулза — иначе дубли side-effect'ов.
- **Approve-and-execute** вместо approve-for-retry: сегодня позднее одобрение создаёт грант и ждёт повторного вызова агента (`gate-approvals.ts`, `resolveLateApproval`); шаг вперёд — плоскость сама исполняет сохранённый в заявке вызов, персистит результат, ретрай агента получает его из стора. Закрывает dogfood-хвост M2 «одобрение в пустоту» (4 случая за неделю).
- **`queued`-семантика синтетической ошибки**: в `data` добавить `reason: 'queued'` + id задачи — ассистент может честно сказать пользователю «заказ принят, обрабатывается», а не «попробуйте позже».
- **Completion-webhook** на API приложения-ассистента (пуш в умершую MCP-сессию протокол не даёт — только out-of-band) — то же расширение, что «внешние уведомления о заявках» из бэклога M4, другое событие.

Сдвиг модели доверия — проговорён: плоскость становится актором (инициирует вызовы **новым** rpcId от своего имени — «один исход на id» не нарушается, byte-identity к отложенному пути не применяется). Именно поэтому — строго после M5: исполнение чужих write-операций плоскостью требует доказуемого провенанса записи (подпись, `policyHash`/`grantsHash`): «запрошено агентом X в сессии Y, одобрено админом Z, исполнено плоскостью в T, доставлено webhook'ом в T+1». Opt-in per-tool в политике; спросить design-партнёров, есть ли у них этот класс сценариев.
