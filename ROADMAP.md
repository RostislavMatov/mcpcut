# Roadmap — MCP Control Plane

Горизонт: MVP «ядро + admin UI» → пилоты с design-партнёрами. Оценка: **~12 недель** от старта кода (ориентир: старт середина августа 2026 → pilot-ready к началу ноября 2026). Недели — относительные, сдвигаются от фактического старта.

## Треки

Работа идёт в два параллельных трека. Кодовый трек без партнёрского не имеет смысла — валидация гипотезы требует пилотов.

### Технический бэклог из ревью M1 (решить в рамках M2/M5)

Осознанно отложенные находки ревью (все CRITICAL/HIGH и большинство MEDIUM/LOW закрыты в M1):

- **Политика fail-open журнала** (M2): при постоянных ошибках записи прокси продолжает ретранслировать без журнала и выходит с кодом 0. Для enterprise-сегмента нужен конфигурируемый fail-closed (убить child, ненулевой код) + счётчик потерянных записей.
- **Child имеет write-доступ к своему журналу** (M5): дочерний процесс работает под тем же uid и может переписать `~/.mcp-journal/*.jsonl`. До hash-chain (M5) журнал не tamper-evident; варианты — отдельный uid писателя, append-only атрибут, отгрузка off-box.
- **JSON-RPC batch** классифицируется как `invalid` (осознанно, зафиксировано тестом) — пересмотреть при переходе на спеку 2026-07-28.
- Мелкое: shallow `Object.freeze` записей (payload мутабелен), UTF-8-разрыв на границе overflow-флаша (достижим только через capped-путь).

### Технический бэклог из ревью M3 (осознанно отложено)

Все CRITICAL/HIGH и бо́льшая часть MEDIUM закрыты в M3 (волна 5b, `e5ddff8`). Отложено:

- **Кэш `agents.json` по mtime** (до пилота): каждый HTTP-запрос и каждый ревокационный полл каждой сессии перечитывает файл с диска; при 64 сессиях — заметный I/O. Memoize `read()` по `stat().mtimeMs`.
- ~~**Валидация `Host`-заголовка** в HTTP-фронте~~ — **закрыто 2026-08-11 (M4, волна 0)**: общий `src/net/origin-host.ts` для агентского фронта и UI; проверка до аутентификации; allowlist = bound host + localhost + `--allowed-host`; DNS-rebinding-форма → 403.
- ~~**Грант-словарь для resources/prompts**~~ — **закрыто 2026-08-11 (M4, волна 1)**: `AgentGrant` получил `resources?`/`prompts?` (URI-паттерны с сегментной границей, canonicalization через WHATWG URL); дефолт «поля нет» = fail-closed M3 байт-в-байт (тесты M3 не правились). Правила политики (allow/deny/require-approval) для этих методов — бэклог M5.
- **Дубликация connect-upstream/serve-upstream** (при первом расхождении): общая сборка апстрима — кандидат на `src/session/upstream.ts`; header-политика уже общая (`session/per-message-headers.ts`).
- ~~**Lockfile без holder-токена**~~ (`policy/store.ts`, `vault/files.ts`) — **закрыто 2026-08-11**: окно стреляло (флак `store-concurrency` под нагрузкой — потерянное обновление). Лок вынесен в общий `src/lockfile.ts` с `nonce`-токеном владения; `update` перепроверяет владение перед коммитом и переигрывает read-modify-write под одним общим дедлайном, релиз не удаляет чужой лок и не бросает из `finally`, исчерпание попыток даёт `StoreLockLostError`. Вольт репортит потерю лока `VaultLockLostError` (переигрывать `fn` нельзя — rekey не идемпотентен). Контракт `update()`: `fn` обязана быть чистой и переживать повторный вызов — под это починен `registry.removeServer`, который рапортовал об удалении, которого не было.
- **Compare-and-swap на запись стора** (остаток от правки лока 2026-08-11): между проверкой владения локом и `rename` в `writeAtomic` остаётся окно в один сисколл — чтобы его использовать, конкурент должен уложить полный read-modify-write ровно туда. Закрывается монотонной `revision` в документе стора: читаем `R`, отказываемся от rename, если на диске уже не `R`. Обвязка ретрая (`UPDATE_MAX_ATTEMPTS`) уже есть. До тех пор потерянное обновление возможно, хоть и не воспроизводимо.
- ~~**Битый чужой лок больше не самоисцеляется**~~ — **закрыто 2026-08-11 (M4, волна 0)**: непарсимый чужой лок с неизменной mtime старше N×`staleMs` удаляется с видимой оператору строкой; живой писатель (меняющаяся mtime) не крадётся.
- ~~**CI (GitHub Actions: build+test+lint)**~~ — **закрыто 2026-08-11**: `.github/workflows/ci.yml` — push/PR в `main`, матрица Node 20/22, `npm ci` (кэш) → lint → build → test (coverage-пороги vitest валят джоб), `permissions: contents: read`, `persist-credentials: false`, concurrency cancel-in-progress, timeout 15 мин. Ревью Approve (0 блокеров). Активируется при первом пуше на GitHub-remote (его пока нет).
- **Трансляция моделей sessionful↔stateless** (решение ~октябрь 2026 по адопции финальной ревизии): в M3 — transport-both/translate-none (ADR-0002), мисматч-пары отклоняются.
- **Агрегация виртуальных серверов** (один endpoint на агента с неймспейсингом тулзов): отвергнута в M3 (ломает байт-идентичность и «один исход на id»); вернуться, если попросят партнёры.
- ~~**Несимметричный источник политики у `connect` и `serve`**~~ — **закрыто 2026-08-11 (M4, волна 1, ADR-0005)**: источник определяется классом доверия входа (`agent-launched` vs `operator-launched`), не именем команды; модуль `src/policy/source.ts`, проверяемо через `policy show --entry-point`.
- ~~**`classOverrides` для серверов без аннотаций**~~ — **закрыто 2026-08-11 (M4, волна 4)**: рецепт в README (раздел политик), попутно исправлена устаревшая ссылка на имя поля.
- ~~**Структурный дифф схемы в очереди одобрений**~~ — **закрыто 2026-08-11 (M4, волна 1 + 3)**: `src/policy/schema-diff.ts` (чистый дифф + вердикт `surfaceDelta`), инвентарь хранит полный капнутый дескриптор (retention: две версии на тулзу — approved + quarantined), дифф виден в UI-карантине и `quarantine show` (паритет CLI).
- **Сигнал `surfaceDelta` как вход в классификацию** (задача M5; в M4 сделана дешёвая половина): `surfaceDelta: widened` вычисляется, персистится и показывается оператору, но класс тулза не меняет. M5 добавляет ветку в `classifyTool` — эскалация класса при расширении поверхности требует провенанса решения (`policyHash`/`grantsHash`) и подписи записи, иначе аудитор видит «правила поменялись сами». Открытый порог: любое ли расширение эскалирует — ответ собирается на dogfood-данных M4.

### Технический бэклог из ревью M4 (осознанно отложено)

Оба финальных ревью M4 (TS + security, 2026-08-11) — без CRITICAL/HIGH. Отложено:

- **Rate-limit логина за reverse-proxy + owner-резерв слотов сессий** (пара, M5): за `--behind-tls`-прокси все логины приходят с адреса прокси — per-address-лимит деградирует в общий bucket (README требует лимитировать `/login` на прокси); кап сессий (64 глобально / 8 на админа) без резерва для owner — 8 viewer-учёток могут заполнить пул, и owner не войдёт до истечения TTL (8 ч). Варианты: `--trusted-proxy-header` (только с перезаписью XFF на прокси), idle-timeout сессий, резерв слотов owner. Оба — availability-компромиссы одного fix-коммита, перенастраивать вместе.
- **Глобальный потолок логин-лимита как lockout-примитив** (LOW): локальный процесс с алиасов `127.0.0.0/8` может набрать 100 отказов и запереть вход всем. Требует code exec на хосте плоскости; вариант — деградация в задержку вместо отказа.
- **Правила политики (allow/deny/require-approval) для `resources/*`/`prompts/*`** (M5): в M4 — только гранты; спросить первого партнёра с чувствительными файловыми ресурсами.
- **Retention/прунинг `approvals/resolved/` и истории дескрипторов** (M5, вместе с retention журнала): файлы копятся вечно; чтение в M4 ограничено, удаление — нет.
- **Мгновенное закрытие SSE при out-of-process отзыве** (при жалобе): `admin remove/rotate/role` из CLI закрывает стрим на следующем heartbeat (SLA ≤ 15 с, задокументировано); запросы отказываются немедленно. Хук `hub.closeForAdmin()` уже существует.
- **Per-admin квота SSE-подписок** (LOW): один админ может занять все 64 слота; деградация — поллинг-фолбэк, не потеря функции.
- **HSTS + `__Host-`-префикс cookie при `--behind-tls`**; **обязательный `Origin` на UI-POST** (сейчас покрыто Host-скринингом + SameSite=Strict + CSRF); **интерстициал подтверждения на `servers/add`** (RCE-by-design, той же силы, что CLI `server add`; owner-only + CSRF) — три дешёвых укрепления одним заходом.
- **Внешние уведомления о заявках** (Slack/webhook/desktop, после пилотов): решение по данным dogfood — сколько заявок протухает при закрытой вкладке.

### Требования к M5 из внешних обсуждений

Вход не от аудитора, а от смежного вендора (основатель ECZ-ID, тред `python-sdk#1705`, 2026-08-11) — это дизайн-вход, не валидация формата отчёта; интервью с практикующим аудитором (открытый вопрос PRD) он не заменяет.

- **Разделить в контракте экспорта целостность записи и текущую авторитетность.** Хеш-цепочка доказывает релаинг-парти, что полученная история решений не изменена задним числом. Она **не** отвечает на вопрос, является ли субъект, политика или оператор в этой записи текущим авторитетом. Три слоя держим раздельно: enforcement (что разрешено/заблокировано) → receipt/export (что произошло и цела ли запись) → resolvable current state (что считать авторитетным сейчас). Практическое следствие: экспорт обязан нести явный as-of и **не должен** формулироваться как утверждение о текущих правах.
- **Пинить провенанс решения в самой записи** (предпосылка предыдущего пункта, правка `DecisionInfo`): сегодня решение несёт `rule` строкой, но не отпечаток эффективной политики и матрицы грантов на момент решения. Даже с цепочкой хешей релаинг-парти не сможет ответить «по какой редакции правил это было разрешено» и не сможет её воспроизвести. Добавить `policyHash` и `grantsHash` (канонический хеш эффективного документа политики и матрицы грантов — механика уже есть в `src/policy/hash.ts`). Делать до подписи записей, иначе цепочка зафиксирует записи без провенанса.
- **Resolver/authority-система — вне периметра.** Третий слой (кто авторитетен сейчас) мы не строим: это чужой продукт и чужая ответственность. Наш экспорт должен композироваться с внешним резолвером, не подменять его и не тащить приватные входы, из которых получено исходное решение.
