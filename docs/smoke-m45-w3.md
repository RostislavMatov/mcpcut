# Ручной смок M4.5 волна 3 — очередь одобрений на SQLite, глазами из браузера

**Пройден 2026-08-15.** Стенд: скретч-каталог (реальный `~/.mcp-journal` не использовался,
кроме одной оговорки — находка 3), продовый `dist/`, реальный HTTP UI (`:8093`, Chromium через
Playwright), connect-сессия с инжектированным stdio и автоповтором gated-вызова. Перед стендом
в каталог посеяны legacy-файлы очереди в формате M2–M4: 1 живая pending + 2 resolved.
Политика: `write: require-approval`, окно ожидания 180 с. Драйвер стенда — в скретчпаде сессии
(`smoke-w3/driver.mjs`), там же скриншоты до/после.

## Часть 1 — миграция и legacy-совместимость

| # | Действие | Факт |
|---|---|---|
| 1 | `mcp-journal migrate` на каталоге с посеянными файлами | ☑ `state: approvals/ -> imported (1 pending, 2 resolved)`, остальные сторы `no file`, итог «Migrated 1 store(s)» |
| 2 | Импортированная legacy-pending в UI | ☑ карточка `notes/legacy.md` в очереди рядом с живыми, `apiKey: "[REDACTED]"` из файла сохранён |
| 3 | Повторный запуск `migrate` | ☑ `already migrated` (проверено на реальном dogfood-каталоге — см. находку 3) |
| 4 | Файлы после работы | ☑ в `pending/`/`resolved/` — только посеянные; ни одна новая заявка файлом не записана (всё в `state.db`) |

## Находки

1. **Dogfood-вотчер (`tools/approvals-watch.mjs`) ослеп после переезда очереди — исправлено в ходе смока.**
   Вотчер читал `pending/*.json` напрямую; новый код пишет в `state.db` → уведомления о новых
   заявках молча перестали приходить (воспроизведено вживую: gated-вызов Playwright этой же
   сессии провисел 60 с без уведомления). Фикс: вотчер читает ОБЪЕДИНЕНИЕ двух носителей
   (модуль очереди из `dist/` + файлы на переходный период); заодно устранено задвоение —
   работали два экземпляра вотчера. **Урок волны 2 подтверждается в обратную сторону: внешняя
   обвязка, читающая носитель напрямую, ломается молча — при смене носителя грепать не только
   `src/`, но и `tools/`, LaunchAgent'ы и прочую обвязку.**
2. **Переходный разрыв: pending-файл от долгоживущей сессии на старом коде невидим и
   нерезолвим новым CLI.** Живой пример: wrap-прокси Playwright текущей Claude-сессии (старый
   код) писал заявки файлами; `approvals approve <id>` нового кода их не находит (state.db-only,
   ленивый импорт уже прошёл — маркер стоит). Резолвятся они только старым кодом; сессия сама
   пометит их expired при завершении. **Следствие для волны 5 (README): процедура апгрейда =
   `migrate` + перезапуск долгоживущих процессов (`serve`, `ui`, wrap/connect-сессии,
   вотчеры) — задокументировать обязательно.** Добавлено в бэклог ROADMAP.
3. **Оговорка прогона: `migrate` без journalDir-шва ушёл в реальный `~/.mcp-journal`** (в
   dispatch-опциях `migrate: { journalDir }` — отдельный ключ, а не top-level). Реальный
   dogfood-каталог домигрирован до волны 3: state.db уже существовал (волна 2 там жила),
   добавились маркер очереди и 44 resolved-записи. Миграция аддитивна, файлы не тронуты,
   повторный запуск честно говорит `already migrated`. Побочный плюс: подтверждена миграция на
   настоящих данных M2-эпохи.
4. Накопление протухших ретраев в очереди (8 карточек одного и того же вызова) — штатное
   следствие пары «pending живёт до teardown ради поздней санкции» × «агент ретраит». Дизайн
   M2 (UX-хвост «approve после таймаута требует повтора») + бэклог LIMIT/retention из ревью
   волны 3 это покрывают; нового пункта не заводим.
5. Консоль браузера: 1–2 известные косметические ошибки (SSE `/events` без сессии на логине,
   `favicon.ico` → 403) — уже в бэклоге M4, без изменений.

## Гигиена после прогона

- Стенд погашен (SIGTERM), скретч-каталог остался в скретчпаде сессии для справки.
- Вотчер: работает один экземпляр на новом коде (LaunchAgent перезапустил сам).
- Два pending-файла от gated-вызовов Playwright в реальном каталоге оставлены — их владелец
  (живой wrap-прокси на старом коде) пометит их expired при завершении сессии.
- Owner-токен стенда одноразовый и умер вместе со стендом; реальные учётки не создавались.
