# MCP Control Plane — концепция редизайна админ-панели

Конверсия референса «Cyclops Campaign Dashboard» (детальная страница сущности с живыми метриками) + «BizLink CRM» (сводная полоса метрик и колонки-лейны) под сущности MCP Control Plane.

Дизайн опирается только на поля, которые реально существуют в коде (`src/ui/pages/*`, `src/journal/*`, `src/policy/*`, `src/registry/schema.ts`, `src/agents/schema.ts`). Всё, чего в домене нет, вынесено в отдельный раздел «Чего нет в данных» — это не дизайнерские хотелки, а список бэкендовой работы, без которой соответствующий блок рисовать нельзя.

---

## 0. Инвентарь данных (что реально есть)

| Сущность | Поля, доступные UI | Действия (мин. роль) |
|---|---|---|
| Pending approval | `approvalId`, `serverName`, `toolName`, `toolClass` (read/write/destructive), `argsRedacted`, `argsHash`, `sessionId`, `requestedAt`, `expiresAt` (окно гранта), `agentName?`, `waitExpiresAt?` (ожидание агента), `decisionRule?`, `expired` | approve / deny (operator); bulk approve только для `read` |
| Resolved approval | всё из pending + `resolution.outcome` (approved/denied/expired), `resolution.actor?`, `resolution.reason?`, `resolvedAt` | — (только чтение; **сегодня в UI не выводится вообще**) |
| Карантин | `serverName`, `toolName`, `state` (new/changed), `firstSeenAt`, `description?`, `surfaceDelta` (widened/narrowed/changed/neutral), `changes[] {kind, path}` (16 видов kind), `truncated` | approve / reject (operator) |
| Approved tool | `schemaHash`, `approvedAt`, `descriptor?`, `schemaTruncated?` | — |
| Server (реестр) | `name`, `transport` (stdio/http); stdio: `command`, `args?`, `env?`; http: `url`, `protocol`, `headers?` | add / remove (owner) |
| Agent | `name`, `createdAt`, `revokedAt?`, `grants{server → {tools, resources?, prompts?}}` (`tokenHash` никогда не рендерится) | create / grant / ungrant / revoke (operator) |
| Admin | `name`, `role`, `createdAt`, `rotatedAt?` | add / remove / rotate / role (owner) |
| Vault | `name`, `createdAt`, `updatedAt` — значений нет по конструкции | — (read-only, owner) |
| Journal session | `sessionId`, `firstTs`, `lastTs`, `count`, `skippedLineCount`, `size`, `mtimeMs` | — |
| Journal record | `id`, `ts`, `sessionId`, `direction` (client→server / server→client / server-stderr), `kind`, `method?`, `rpcId?`, `payload`, `durationMs?` | — |
| Decision record | `outcome` (allow / deny / require-approval-pending / approved / denied-by-operator / timeout / quarantined), `rule`, `serverName`, `toolName`, `toolClass`, `quarantineState`, `argsHash`, `approvalId?`, `agentName?`, `latencyMs?` | — |
| Поиск по журналу | фильтры `kind`, `direction`, `method`, `toolName`, `outcome`, `text`; честный учёт скана: `scannedLineCount`, `skippedLineCount`, `hasMore`, `truncated`, `stoppedBy`, `filesScanned` из `filesTotal`, `bytesRead` | — |
| Точка входа | `EntryPoint` (connect/wrap/serve/ui) → `TrustClass` (agent-launched / operator-launched) — свойство **входа**, не сервера | — |
| SSE | ровно три топика: `approval-pending`, `approval-resolved`, `quarantine-changed`; watcher поллит очередь раз в 1 с | — |

**Редакция секретов**: отдельного счётчика нет. В данных есть только литерал `[REDACTED]` внутри payload и маркер `…[TRUNCATED]`. Любая «метрика редакций» — это подсчёт записей с маркером **в просканированном окне**, и подписывать её нужно именно так.

## 1. Концепт-идея

Cyclops строит экран вокруг **одной сущности, которая живёт во времени**: шапка с идентичностью и статусом, полоса метрик «сколько всего произошло», блок живых данных с честной отметкой «Updated 2s ago / Click to refresh», и ниже — разрезы: кто участвовал (таблица), как распределилось (bar), из чего состоит (radar). У нас ровно такая же сущность есть, и она сейчас нигде не собрана: это **MCP-сессия** (один прогон агента через контрольную плоскость) и её долгоживущий родитель — **MCP-сервер** из реестра. Сегодня UI показывает пять плоских списков (очередь, карантин, серверы, агенты, журнал), между которыми нет ни одной связи: из одобрения нельзя провалиться в сессию, из сессии — в сервер, из сервера — в его тулзы и агентов. Редизайн переносит метафору так: **сервер — это «кампания», сессия — это её «запуск», журнал — это её живая лента, а очередь одобрений — это единственное место, где человек вмешивается в идущий процесс**. Метрики Cyclops (лайки/шеры/engagement) конвертируются в счётчики решений политики (вызовы / одобрено / отказано / карантин), таблица инфлюенсеров — в таблицу агентов с их грантами, распределение по возрасту/полу — в распределение вызовов по тулзам с разрезом allow/gated, а карта охвата — в **живую полосу активности с честной отметкой свежести**, потому что «Updated 2s ago · Click to refresh» — это ровно та честность, которой требует аудит-продукт: данные читаются с диска с потолками скана, и UI обязан говорить, насколько они свежие и полны.

## 2. Навигация (сайдбар)

Сейчас: горизонтальная полоса `mcp-journal | Approvals | Quarantine | Servers | Agents | Journal | имя · роль`. Дефекты, которые чинит редизайн: `/vault` и `/admins` **отсутствуют в навигации вообще** (на `/admins` можно попасть только по ссылке со страницы агентов), нет контрола выхода (маршрут `POST /logout` существует, кнопки нет), нет счётчиков, роль подана как текст без визуального веса.

Вертикальный сайдбар, три смысловые группы (порядок = порядок рабочего дня оператора):

**Работа** (что требует человека прямо сейчас)
1. `Обзор` — `/` (новый экран, см. §3)
2. `Одобрения` — `/approvals` · **бейдж**: число pending. Второй, амбер-бейдж — сколько из них с истёкшим окном ожидания агента (`waitExpiresAt` в прошлом): это не «просто ждут», это «агент уже сдался, одобрение даст только ретрай». Разница операционально важная и сейчас видна только внутри карточки.
3. `Карантин` — `/quarantine` · **бейдж**: число карантинных тулзов; красная точка, если среди них есть хоть один `surfaceDelta: widened` (схема стала принимать больше входа — единственный класс изменения, который расширяет поверхность атаки).

**Наблюдение**
4. `Журнал` — `/journal` (лента записей + поиск)
5. `Сессии` — `/journal/sessions` (список сессий как сущностей; сегодня это дефолтный вид `/journal`, в редизайне разделяется)

**Конфигурация**
6. `Серверы` — `/servers`
7. `Агенты` — `/agents`
8. `Вольт` — `/vault` (owner; иначе пункт не рендерится)
9. `Администраторы` — `/admins` (owner; иначе не рендерится)

**Профиль — внизу сайдбара** (в Cyclops он вверху; вниз — потому что у нас это не переключатель аккаунта, а идентичность + выход):
- имя админа, под ним роль как чип с цветом (`owner` — тёмный, `operator` — синий, `viewer` — серый контур);
- для viewer рядом с чипом — надпись «только чтение»;
- `Выйти` — форма `POST /logout` с CSRF-полем.

Счётчики бейджей обновляются по уже существующим SSE-топикам (`approval-pending`, `approval-resolved`, `quarantine-changed`). Сайдбар — это `data-live-region` с этими тремя топиками; текущий клиент умеет перезапрашивать регион и подменять его.

Бейджи считать **только по тому, что дёшево**: длина списка pending-файлов и число карантинных записей. Никаких метрик журнала в сайдбаре — они требуют скана.

## 3. Экран «Обзор» (новый)

Цель: за 5 секунд ответить на «нужно ли мне что-то сделать прямо сейчас» и «что вообще происходило».

### 3.1 Полоса метрик (по образцу CRM-референса — плотная строка над контентом)

Разделена на две зоны с разной ценой и разной честностью — это принципиально, зоны нельзя смешивать в одну строку без визуальной границы:

**Зона A — точные, дешёвые (листинг директорий, без скана журнала):**
| Плитка | Значение | Клик ведёт |
|---|---|---|
| Ожидают решения | N pending | `/approvals` |
| Из них ожидание истекло | M (`waitExpiresAt` в прошлом) — амбер | `/approvals?lane=wait-elapsed` |
| Карантин | K тулзов, подпись «new: x · changed: y» | `/quarantine` |
| Расширенная поверхность | сколько из K имеют `surfaceDelta: widened` — красный, если > 0 | `/quarantine?delta=widened` |
| Сессий в журнале | всего из индекса; подпись «активных за 15 мин: n» (по `lastTs`) | `/journal/sessions` |

**Зона B — производные от скана, с потолком (визуально отделена, с подписью окна):**
| Плитка | Значение |
|---|---|
| Вызовы (24 ч) | число decision-записей в окне |
| Одобрено / Отказано | `allow` + `approved` / `deny` + `denied-by-operator` |
| Ушло на одобрение | `require-approval-pending` |
| Истекло по таймауту | `timeout` |
| Заблокировано карантином | `quarantined` |
| Записей с маркером редакции | подпись «в просканированном окне» |

Под зоной B — обязательная строка честности, ровно та же формулировка, что уже используется в журнале: **«Просканировано N из M файлов, остановлено по `stoppedBy`; результат неполный»** или «Просканированы все M файлов». Если скан усечён, все числа зоны B показываются с префиксом `≥`. Это не украшение: продукт продаётся как доказательный журнал, и метрика без границы скана здесь — репутационный риск.

### 3.2 Живая лента (конверсия блока «Campaign Reach + карта» из Cyclops)

Вместо карты — **лента последних решений** (правая колонка, ~50% ширины), 20 последних decision-записей:
`время · агент · сервер·тулза · чип toolClass · чип outcome · rule` — строка кликом ведёт в сессию журнала с преднастроенным фильтром.

Слева от ленты — **полоса активности по часам** (24 бара, высота = число вызовов, цветовая доля = gated/denied). Это замена карты охвата: тот же жанр «одна картинка, показывающая масштаб и распределение», но по оси, которая у нас есть (время), а не по географии, которой нет.

Под лентой — **честная отметка свежести Cyclops**: `Обновлено 4 с назад · Обновить`. Реализация: топика `journal-appended` в SSE **сегодня нет** (есть только три топика очереди/карантина), поэтому лента живёт на поллинге региона с интервалом 5 с, и отметка свежести — это не декор, а правда о механизме. Когда появится топик (см. §10), поллинг заменится на push без изменения вёрстки.

### 3.3 Полоса «требует внимания»

Над метриками, показывается только если непусто: до 3 самых срочных pending-карточек в компактном виде с кнопками Approve/Deny прямо здесь. Смысл: типичный визит оператора заканчивается на «Обзоре», без перехода в очередь.

## 4. Экран «Сервер» и экран «Сессия» (конверсия Cyclops)

Cyclops-страница разбивается на два уровня, потому что у нас две сущности разной длительности.

### 4.1 Сервер — `/servers/:name`

**Шапка сущности** (аналог «Blue Chips Chicago · Active · Created on August 20, 2021»):
- Аватар → монограмма из имени сервера, цвет детерминирован от имени (никаких загружаемых картинок — CSP `default-src 'none'`, внешних ресурсов быть не может).
- Имя сервера, под ним — цель: `command args…` для stdio или `url` для http (моноширинно, обрезается).
- Чипы: `stdio` / `http` + `protocol`; для http — хост из URL.
- `Секреты: N vault-ссылок` — считается по `env`/`headers` со значением `vault:*`; чип-ссылка на `/vault` (owner). Это делает видимым инвариант «секретов в реестре нет, только ссылки».
- **Статус**: честного health-статуса в домене нет. Вместо выдуманного «Active» — производный чип по журналу: `активен` (есть decision-записи за 15 мин) / `тихо N ч` / `нет активности в журнале`. Подпись — «по журналу», чтобы не читалось как health-check.
- **Дата регистрации отсутствует в `registry.json`** — вместо неё показывать «Первая одобренная тулза: `min(approvedAt)`» из инвентаря или «Первая запись в журнале». Настоящий `registeredAt` — в бэклог (§10).
- Справа — действия по роли: `Удалить` (owner, ведёт на существующий интерстишал подтверждения с перечислением агентов с грантами).

**Табы** (аналог Tiktok / Instagram / Facebook):
`Тулзы` · `Агенты` · `Сессии` · `Журнал`

**Карточки метрик** (4 плитки, аналог Likes/Comments/Shares/Engagement), все по окну скана с честной подписью:
1. `Вызовы` — decision-записи с этим `serverName`
2. `Ушло на одобрение` — `require-approval-pending` + `approved` + `denied-by-operator`
3. `Отказы` — `deny` + `denied-by-operator` + `timeout`
4. `Карантин` — текущее число карантинных тулзов сервера (точное, из инвентаря) + `quarantined`-решений в окне

**Таб «Тулзы»** (замена «Audience Age & Gender» + основной таблицы):
- Таблица: тулза · класс (read/write/destructive) · статус (approved / quarantined new / quarantined changed) · `approvedAt` или `firstSeenAt` · вызовов в окне.
- Рядом — **двусторонняя гистограмма по тулзам** (прямая конверсия male/female-графика): влево — `allow`, вправо — всё gated (`require-approval-pending` / `deny` / `denied-by-operator` / `timeout` / `quarantined`), с общей осью тулз посередине. Читается за секунду: какие тулзы работают сами, а какие постоянно дёргают человека.

**Таб «Агенты»** (замена таблицы инфлюенсеров — 1:1 по жанру):
- Строка: агент · гранты для этого сервера (`tools` / `resources` / `prompts`, где `*` подаётся как чип `all`, пустое — как `—`) · вызовов в окне · отказов · чип `revoked`, если `revokedAt`.
- Действия: `Ungrant` (operator) — уже существующая форма.

**Вместо radar-графика интересов** — radar отвергнут осознанно: у нас 7 значений `outcome` с несопоставимыми величинами (allow на три порядка чаще, чем destructive-deny), radar на таких данных врёт формой. Замена — **«спектр решений»**: одна горизонтальная 100%-полоса, сегментированная по всем семи outcome с фиксированной цветовой семантикой (зелёный allow → синий approved → амбер pending → красный deny/denied-by-operator → серый timeout → фиолетовый quarantined), с абсолютными числами в тултипе и легендой-списком под ней. Плюс маленькая плитка «микс классов»: доля read / write / destructive среди вызовов.

**Таб «Сессии»** — список сессий, в которых встречается этот сервер (см. ограничение в §10: связь «сессия ↔ сервер» выводится только сканом decision-записей).

**Таб «Журнал»** — встроенный журнал с преднастроенным фильтром по этому серверу.

### 4.2 Сессия — `/journal/sessions/:id`

Та же анатомия, но сущность короткоживущая. Это главный экран для расследования «что натворил агент».

**Шапка**: `sessionId` (моно, с кнопкой копирования) · чипы производных сервера и агента (из decision-записей сессии) · `firstTs → lastTs` и длительность · `count` записей · `size` файла · **`skippedLineCount` нечитаемых строк — всегда, и жирным, если > 0** (уже существующее правило журнала, его нельзя терять в редизайне).

**Метрики сессии**: вызовы · одобрено · отказано · медиана `latencyMs` по decision-записям (поле есть) · записей с маркером редакции.

**Тело**: та же живая лента, что на «Обзоре», но в границах сессии, с фильтр-чипами и пагинацией; блок скана (`scannedLineCount`, `truncated`) остаётся дословно.

## 5. Журнал

Три режима на одном маршруте, переключатель сверху: **Сессии** (список) / **Записи** (внутри сессии) / **Поиск** (кросс-сессионный). Сейчас это три разных рендера без явного переключателя — пользователь не понимает, где он.

**Список сессий**: таблица `sessionId · записей · нечитаемых · первая · последняя · размер`, сортировка по `lastTs`, у активных (за 15 мин) — пульсирующая точка.

**Живой поток**: лента записей, новые приходят сверху. Правила поведения, обязательные для аудит-продукта:
- Новые записи **не сдвигают** просмотр: при прокрутке ниже верха появляется пилюля «N новых записей ↑», вставка происходит только по клику или когда пользователь наверху.
- Автопрокрутка на паузе, пока запись раскрыта.
- Тумблер `Живой поток / Пауза` + отметка `Обновлено N с назад · Обновить`.

**Поиск и фильтры** — фильтры уже существуют, меняется подача: вместо ряда безымянных текстовых полей — **чипы-фильтры** с типизацией:
- `kind`, `direction`, `outcome`, `toolClass` — селекты с фиксированными словарями (значения известны из типов, свободный ввод здесь бессмысленен и рождает пустые выдачи);
- `method`, `tool` — комбобоксы с подсказками из просмотренного окна;
- `text` — свободный поиск.
Активные фильтры — снимаемые чипы над лентой, кнопка «Сбросить». Состояние остаётся в query-строке (ссылку на выдачу можно приложить к тикету — это ровно то, зачем аудитору UI).

**Строка записи**: `ts · направление (стрелка ← / →, для stderr — отдельный значок) · kind · method` + свёрнутый payload. Decision-записи имеют свой раскрас: `outcome`-чип, `serverName·toolName`, `toolClass`, `rule`, короткий `argsHash`, ссылка на одобрение (`approvalId`) — эта ссылка уже есть, но ведёт на `/#approval-…`; в редизайне она должна вести на карточку **resolved**-одобрения с именем решившего.

**Отметка редакции** — важный элемент доверия, сейчас его нет: если в payload встречается `[REDACTED]`, у записи появляется чип `секреты отредактированы` с тултипом «поле удалено при записи; оригинал никогда не сохранялся». Сами маркеры внутри payload подсвечиваются (моноширинный бейдж вместо голого текста). Аналогично `…[TRUNCATED]` → чип `payload усечён`. Смысл: пользователь должен видеть, что пропуск в данных — это гарантия продукта, а не потеря данных.

## 6. Очередь одобрений

**Kanban из CRM-референса — нет, лейны — да.** Drag-and-drop для одобрения недопустим: это необратимое решение безопасности, а перетаскивание — жест без имени, без подтверждения и с высокой ценой промаха. Но идея колонок со счётчиками используется: колонки становятся **лейнами срочности**, вычисляемыми из часов, без перетаскивания.

**Раскладка**: три лейна слева (ширина ~70%) + правый рейл «Недавно решённые».

| Лейн | Условие | Смысл |
|---|---|---|
| `Агент ждёт` | `waitExpiresAt` в будущем | одобрение доставит вызов **сейчас** |
| `Ожидание истекло` | `waitExpiresAt` в прошлом | агент сдался; одобрение даст только грант на ретрай |
| `Окно гранта истекло` | `expired` | решение уже почти бессмысленно; сворачивается по умолчанию |

Внутри лейна — сортировка по возрастанию оставшегося времени. Заголовок лейна несёт счётчик (как в CRM-референсе).

**Состав карточки**:
- Строка идентичности: `агент → сервер · тулза`, чип `toolClass` (read — серый, write — амбер, destructive — красный с иконкой).
- `rule: <decisionRule>` — почему это вообще спросили.
- Два разных по весу таймера: **крупный обратный отсчёт ожидания агента** (или явная плашка «ожидание истекло — одобрение даст только ретрай», текст уже есть в коде) и мелкая подпись «окно гранта: Ns».
- `argsRedacted`: первые 3 ключа inline, полный JSON — по «показать аргументы»; чип `секреты отредактированы`, если есть маркер; короткий `argsHash` с копированием.
- Подвал: `requestedAt`, ссылка на `sessionId` (в сессию журнала) — сейчас `sessionId` в карточке **не показывается вовсе**, хотя в данных есть; это разрыв расследования, который редизайн закрывает.

**Действия**:
- `Одобрить` — primary. Для `write` и `destructive` — двухшаговое подтверждение прямо в карточке («Одобрить → Подтвердить: destructive»), без модалки; для `read` — сразу.
- `Отказать` — destructive-стиль (контурная красная), без подтверждения (отказ — безопасная сторона).
- Массовое одобрение — **только для `read`**, правило уже зашито в код (`eligibleForBatch`): чекбоксы появляются только на read-карточках, плавающая панель «Одобрить выбранные (N)» внизу.
- Обе кнопки блокируются на время запроса; ошибка — тост в существующий `toast-region` + разблокировка.

**Поведение при SSE**:
- `approval-pending` → новая карточка появляется в своём лейне с подсветкой 2 с; если оператор прокручен вниз или раскрыл карточку — вместо вставки пилюля «N новых».
- `approval-resolved` для карточки, которую решил **другой** админ, → карточка не исчезает молча, а на 5 с превращается в плашку «Одобрено · <actor>» и затем уезжает в правый рейл. Тихое исчезновение карточки под курсором — прямой путь к промаху по соседней кнопке.
- Карточка, на которой открыт диалог подтверждения, никогда не переупорядочивается.
- Обновление таймеров — локально, раз в секунду, без перезапроса.

**Правый рейл «Недавно решённые»** — новая поверхность на существующих данных (`listResolved`, сегодня в UI не выводится): `тулза · outcome (approved/denied/expired) · actor · resolvedAt`, ссылка в журнал. Это закрывает вопрос «кто это одобрил» без grep по файлам и напрямую работает на позиционирование «именная атрибуция».

## 7. Карантин

Карточка на тулзу, сортировка: `widened` → `changed` → `narrowed` → `neutral` → `new`.

**Шапка карточки**: `сервер · тулза` · чип состояния (`new` / `changed`) · **чип `surfaceDelta` с явной семантикой словами**, а не термином:
- `widened` — красный, «принимает больше входа, чем раньше»
- `narrowed` — синий, «принимает меньше»
- `changed` — амбер, «форма входа изменилась»
- `neutral` — серый, «изменены только формулировки»
Ниже — `firstSeenAt` и `description` тулзы.

**Структурный дифф** (сейчас — плоский список `path — kind`, читается плохо). Подача: сгруппировать 16 видов `kind` в три блока по влиянию, каждый блок раскрывается/сворачивается:
1. **Поверхность расширена** — `property-added`, `enum-widened`, `required-removed`, `type-changed`, `keyword-removed` → раскрыт по умолчанию, красная линейка слева.
2. **Поверхность сужена** — `property-removed`, `enum-narrowed`, `required-added`, `keyword-added` → раскрыт, синяя линейка.
3. **Без влияния на вход** — `description-changed`, `annotation-changed`, прочие neutral → свёрнут, счётчиком «+N косметических изменений».

Строка изменения: путь как хлебные крошки (`properties.filters.mode` → `filters › mode`), полный путь моноширинно, справа — человекочитаемая метка вида изменения («добавлено поле», «enum расширен», «поле стало обязательным»). Плашка `дифф усечён (схема слишком велика)`, если `truncated`.

**Для `new`-тулзов дифф отсутствует** (не с чем сравнивать) — вместо пустоты показывать **поверхность, которую вы одобряете**: список свойств `inputSchema` из `descriptor` с пометкой обязательных. Сейчас там просто фраза «New tool — no prior schema to diff», и оператор одобряет вслепую.

**Действия**: `Одобрить схему` (primary) / `Отклонить` (destructive), operator+. Для `surfaceDelta: widened` — двухшаговое подтверждение, как у destructive-одобрений. Обновление по `quarantine-changed` по тем же правилам, что в §6.

## 8. Роли: что видит viewer / operator / owner

Правило: **скрывать, а не дизейблить**. Задизейбленная кнопка обещает возможность, которой у роли нет и не будет; форма, которую viewer видит и которая вернёт 403, — это баг доверия. Исключение — одно: если действие недоступно временно (запрос в полёте, срок истёк), тогда дизейбл с объяснением.

| Поверхность | viewer | operator | owner |
|---|---|---|---|
| Обзор, метрики, живая лента | ✅ | ✅ | ✅ |
| Очередь: просмотр карточек, аргументы, таймеры, рейл решённых | ✅ | ✅ | ✅ |
| Очередь: approve/deny/bulk | ✖ скрыто | ✅ | ✅ |
| Карантин: просмотр диффов | ✅ | ✅ | ✅ |
| Карантин: approve/reject | ✖ | ✅ | ✅ |
| Журнал, сессии, поиск | ✅ | ✅ | ✅ |
| Агенты: матрица грантов (чтение) | ✅ | ✅ | ✅ |
| Агенты: create / grant / ungrant / revoke | ✖ | ✅ | ✅ |
| Серверы: список и детальная | ✅ | ✅ | ✅ |
| Серверы: add / remove | ✖ | ✖ | ✅ |
| Вольт (имена и даты) | ✖ пункт нав. скрыт | ✖ | ✅ |
| Администраторы | ✖ | ✖ | ✅ |

**Дефекты текущей реализации, которые чинит редизайн:**
- `pages/agents.ts` рендерит формы `Create agent` и `Grant a server` **всем ролям**, включая viewer, — маршруты пинятся на `operator`, так что viewer получит 403 по клику. Формы должны рендериться по роли (как уже сделано на странице серверов через `canManage`).
- Ссылка «Manage admins» живёт на странице агентов, а не в навигации; `/vault` не достижим из навигации вообще.
- У viewer нет визуального объяснения, почему экран «пустее» — нужен чип «только чтение» рядом с ролью в профиле.

## 9. Приоритизация

**Волна 1 — оболочка и место принятия решений** (сюда приходит ценность продукта):
1. Новый шелл: вертикальный сайдбар, группы, бейджи pending/карантина по существующим SSE-топикам, профиль с ролью и кнопкой выхода, скрытие пунктов по роли.
2. Редизайн очереди одобрений: лейны срочности, новая карточка (sessionId, rule, чип редакции, два таймера), правило подтверждения для write/destructive, правила SSE-обновления, правый рейл решённых (нужен маршрут `GET /approvals/resolved` поверх готового `listResolved`).
3. Фикс ролевых дефектов §8 (дёшево, повышает доверие сразу).

**Волна 2 — доказательная часть:**
4. Журнал: три явных режима, чипы-фильтры с фиксированными словарями, отметки редакции и усечения, живой поток с пилюлей «N новых».
5. Карантин: группировка диффа по влиянию, человекочитаемые метки, поверхность для `new`-тулзов.
6. Экран «Обзор» — зона A (точные метрики) + полоса «требует внимания». Зона B и лента откладываются до агрегатора.

**Волна 3 — сущности и разрезы:**
7. Страница сессии `/journal/sessions/:id` с шапкой и метриками.
8. Страница сервера `/servers/:name` с табами; двусторонняя гистограмма по тулзам и «спектр решений».
9. Зона B «Обзора», полоса активности по часам, живая лента — после появления агрегатора и топика `journal-appended`.

**Отложить сознательно:**
- Всё, что относится к M5 (tamper-evident, экспорт аудит-отчёта): никаких плашек «verified», «audit-ready», иконок замка и кнопок «Экспорт отчёта» — до появления реальной подписи. Показывать несуществующую гарантию хуже, чем не показывать никакой.
- Тёмная тема, настраиваемые колонки, сохранённые фильтры, мобильная раскладка (админ-консоль self-hosted — десктоп).
- Health-check серверов, графики задержек, любые прогнозы.

## 10. Чего нет в данных (бэкенд-работа, без которой блок не рисуется)

1. **Агрегатор метрик** — сегодня ни один слой не считает счётчики по outcome за окно. Нужен модуль поверх `journal/search.ts` с теми же потолками (`maxFiles`/`maxBytes`/`timeBudgetMs`) и обязательным возвратом `truncated`/`stoppedBy`/`filesScanned`/`filesTotal`. Блокирует: зону B «Обзора», все метрики сервера и сессии, обе диаграммы.
2. **SSE-топик `journal-appended`** — сейчас топиков ровно три, все про очередь и карантин; watcher журнал не читает. Без него любая «живая лента» — это поллинг, и отметка «Обновлено N с назад» обязана быть честной.
3. **Связь «сессия ↔ сервер/агент»** — в индексе сессий её нет, выводится только сканом decision-записей внутри файла сессии. Для одной сессии это дёшево (один файл), для списка сессий — нет. Решение на волну 3: денормализовать `serverName`/`agentName` в `SessionSummaryEntry` при построении индекса.
4. **`registeredAt` у сервера** — в `registry.json` даты нет; шапка сервера до этого показывает производную дату с явной подписью.
5. **Маршрут решённых одобрений** — данные (`listResolved`) готовы, HTTP-маршрута и страницы нет.
6. **Счётчик редакций** — отдельного поля нет; метрика выводится подсчётом маркера `[REDACTED]` в просканированном окне и подписывается именно так. Добавлять поле в запись — решение уровня M5 (запись входит в хеш-цепочку), в этом редизайне не предполагается.
7. **Health/статус сервера** — отсутствует; в шапке используется производная «активность по журналу», не выдавать за проверку доступности.
