# Сценарий ручного смока — заход «укрепление UI + availability»

**Статус: ПРОЙДЕН С НАХОДКАМИ** (прогон 2026-08-16, ветка `feat/ui-availability-hardening`,
сборка из `2bfc77b`). Ниже — сценарий с заполненной колонкой «Факт», вердикт и находки.

**Чем прогоняли и чего не покрыли:** браузерная часть выполнена в **Chromium** (Playwright MCP,
живой браузер, не эмуляция `fetch`). **Firefox не прогнан** — второго браузерного плеча в стенде не
было. Расхождение M4 было именно браузероспецифичным, поэтому firefox-плечо остаётся открытым
хвостом (см. «Не покрыто»). Часть 5 выполнена за **настоящим TLS** (самоподписанный сертификат +
node-прокси), но браузерное плечо части 5 упёрлось в `ERR_CERT_AUTHORITY_INVALID`: Chromium в стенде
не пускает самоподписанный сертификат, а добавлять его в системный трастстор ради смока не стали.

## Зачем этот смок обязателен

Урок M4 (`docs/smoke-m4.md`, находка 1): `Referrer-Policy: no-referrer` заставлял Chromium
сериализовать `Origin` у form-POST как `null`, который наш же Origin-скрининг отвергал — вход в UI
из любого Chromium был невозможен. **Ни один тест на `node:http`/`fetch`/curl эту связку не
эмулирует.** Текущий заход трогает ровно тот же класс поверхностей:

- `Origin` стал ОБЯЗАТЕЛЕН на каждом POST (форма, `fetch`, logout);
- имя сессионной cookie за TLS сменилось на `__Host-`-префиксное, и неprefixed больше не принимается;
- добавлен редирект анонимного `GET /`;
- добавлен маршрут `/favicon.ico` и `<link rel="icon">`;
- со страницы логина убран SSE-атрибут (проверяется только консолью браузера);
- у `servers/add` появился шаг подтверждения.

Автотесты покрывают контракт, браузер — реальность.

## Стенд

Реальный `~/.mcp-journal` не трогать — подменять `HOME` на скретч-каталог, как в смоке M4.5:

```
export SMOKE=/tmp/smoke-ui-hardening
mkdir -p "$SMOKE"
npm run build
HOME=$SMOKE node dist/cli.js ui --port 8091
# токен owner печатается на stderr один раз — скопировать
```

Для части 5 (TLS-режим) нужен второй запуск за прокси, терминирующим TLS. **Важно (находка 5):**
за прокси, слушающим другой порт/имя, экземпляр надо поднимать с `--allowed-host <публичный host:port>`,
иначе Host-скрининг отвечает 403 на всё ещё до аутентификации:

```
HOME=$SMOKE node dist/cli.js ui --port 8092 --behind-tls --allowed-host 127.0.0.1:8443
```

## Не покрыто этим прогоном

1. **Firefox** — второе браузерное плечо. Расхождение M4 было браузероспецифичным, так что это
   реальный остаточный риск, а не формальность.
2. **Браузерная приёмка `__Host-`-cookie** — нужен доверенный сертификат; контракт проверен по HTTP
   через настоящий TLS, но не глазами браузера.
3. **`SESSION_IDLE_TIMEOUT_MS` (60 мин)** — не смокается за разумное время; остаётся на автотестах.

## Вердикт

**Pass с находками.** Главный риск захода закрыт: вход формой из живого Chromium работает,
регресса класса M4 (`Origin: null`) нет; страница логина больше не стучится в `/events`; отзыв
сессии доходит до открытой вкладки меньше чем за секунду; заполненный viewer-ами пул больше не
запирает owner-а; потолок логина действительно задерживает, а не отказывает. **В периметре захода
находок уровня CRITICAL/HIGH нет**; находки 1 и 2 — MEDIUM, обе про UX, не про безопасность.
Находки 9–10 к заходу не относятся: они пришли из боевого dogfood-контура, через который шёл сам
прогон, и вынесены в отдельный раздел.

## Находки

1. **MEDIUM — из UI нельзя выйти.** `POST /logout` существует, работает и корректно требует
   `Origin` — но ни одна страница не рисует кнопку или форму выхода: `src/ui/pages/layout.ts`
   отрисовывает только `whoami` (`owner · owner`). Воспроизведение: на `/` под сессией
   `Array.from(document.forms)` → `[]`. Следствие: сессию нельзя завершить из браузера — только
   idle-timeout (60 мин), TTL (8 ч) или `admin rotate`. На общей машине это ровно тот сценарий,
   ради которого выход и нужен. Пункт 2.1 сценария невыполним как написан. Решение: кнопка выхода
   в шапке (form-POST на `/logout` с CSRF-токеном) — в бэклог захода.
2. **MEDIUM — форма регистрации сервера обнуляется на ошибке валидации.** 400 (секрет в `env`)
   перерисовывает форму пустой: все восемь полей теряются, включая корректно заполненные. Секрет
   при этом правильно не эхо-ится обратно в HTML — но заодно теряется и всё остальное. Решение:
   вернуть введённые значения, кроме поля, признанного секретом.
3. **LOW — бейдж во вкладке повторяет усечённое число.** Тело страницы честно пишет
   `500 of 520 pending (showing the oldest)`, а `<title>` — `(500) Approvals`. Оператор,
   смотрящий на вкладку (а не на страницу), видит именно то число, ради опровержения которого
   строка усечения и сделана. Решение: `(520)` либо `(500+)` в заголовке.
4. **LOW — интерстициал склеивает `args` пробелом.** Показывает `args: server.js --flag`, то есть
   аргумент с пробелом внутри выглядит как два. Экран подтверждения запуска команды — последнее
   место, где такая неоднозначность уместна. Решение: рендерить по одному аргументу на строку или
   в кавычках.
5. **LOW (документация, не код) — часть 5 неисполнима без `--allowed-host`.** За TLS-прокси
   браузер шлёт `Host` публичного фронта (`127.0.0.1:8443`), Host-скрининг сверяет его с bind-адресом
   (`127.0.0.1:8092`) и отвечает 403 ещё до аутентификации — выглядит как поломка `--behind-tls`,
   хотя это его штатная защита. Флаг `--allowed-host` существует и решает вопрос, но не был
   упомянут ни в шаге стенда, ни в usage-подсказке рядом с `--behind-tls`. Исправлено в этом
   документе; стоит добавить строку и в README-раздел про TLS.
6. **INFO — вес страницы одобрений при глубокой очереди.** 500 карточек = 613 КБ. Живой регион
   рефетчит документ целиком на каждое SSE-событие, то есть всплеск одобрений при недренированной
   очереди = поток рефетчей по 0.6 МБ на вкладку. Сегодня безопасно (сервер отдаёт за ~7 мс),
   но это естественный кандидат в бэклог, если пилот придёт с длинной очередью.
7. **INFO — `/events` после выхода даёт одну 403-ошибку в консоли.** После `POST /logout` открытый
   `EventSource` один раз переподключается, получает 403 и закрывается (`readyState=2`, цикла нет).
   Не регресс и не утечка, но консоль после выхода не пуста.
8. **INFO — голый `policy show` не называет точку входа.** С флагом всё точно: `--entry-point connect`
   печатает `entry point: connect (agent-launched)` и ту же строку `ignoring …`, что и сам `connect`,
   а `--entry-point ui` — операторский источник. Но **без** флага вывод печатает `source: …` без
   пометки, чью резолюцию он показал; в проектном каталоге это операторский файл, а агент в этот
   момент судится по другому. Решение: в голом выводе помечать точку входа и намекать на
   `--entry-point`. (`--entry-point agent-launched` — не значение флага; допустимы `connect|wrap|serve|ui`.)

## Находки вне периметра захода — из живого dogfood-контура

Сам прогон шёл через боевой контур владельца: Playwright и memory обёрнуты `mcp-journal wrap`,
проектная политика — `defaultDecision: require-approval`. За смок контур пропустил через очередь
**32 вызова агента: 31 одобрен человеком вручную** (медиана резолюции ~3 с), 1 оставлен без
решения. Это дало два наблюдения, не относящихся к UI-заходу, но относящихся к M5 и ADR-0004.

9. **HIGH (модель угроз, не эксплойт) — текст отказа содержит готовую команду самоодобрения.**
   Заблокированный вызов возвращает АГЕНТУ строку вида «An operator can approve it with
   `mcp-journal approvals approve <id>` — retry this call after they confirm». То есть инструкция,
   как снять блокировку, доставляется ровно той стороне, которую блокируют, в канал, который она
   читает и которому по умолчанию доверяет. Агент с доступом к shell — а в dogfood-контуре это
   ровно наш случай — может выполнить её и одобрить себя сам; гарантия human-in-the-loop
   держится тогда не на механизме, а на нежелании агента набрать команду.
   Воспроизведение: любой вызов, попавший под `require-approval`, при таймауте ожидания.
   Решения на выбор: (а) не печатать команду в ответ агенту — человек видит заявку в UI и CLI,
   ему подсказка в этом канале не нужна; (б) требовать для `approvals approve` админский
   контекст, недоступный агентскому процессу. Пункт (а) дешёвый и закрывает основную часть.
   Смежное: в UI и CLI одобрение уже атрибутируется человеку (`actor`), но `approvals approve`
   из shell атрибуции не даёт — для M5 (`policyHash`/`grantsHash` в записи решения) это тот же
   вопрос «кто на самом деле нажал».
10. **MEDIUM — брошенная заявка живёт в `pending` до конца сессии.** Заявка, по которой человек не
    принял решения, после `expiresAt` не убирается: `markExpired` вызывается только из
    `cancelPending()` при teardown сессии (`src/proxy/gate-core.ts:372`), а сессия `wrap` в
    dogfood/пилотной форме живёт часами. `approvals list` честно печатает `expires_in=expired`,
    но `countPending()` такие записи считает — значит они попадают и в бейдж вкладки, и в строку
    «N of M pending». Воспроизведение: не отвечать на заявку, дождаться `expiresAt`, оставить
    сессию живой. Решение: подметать истёкшие `pending` независимо от жизни сессии, либо не
    учитывать их в `countPending()`.
