# Смок: сквозной путь пользователя — от разворачивания до аудит-отчёта

**Статус: ПРОЙДЕН; H1, H2, M1 и все LOW ЗАКРЫТЫ в тот же день (разделы «Закрытие»)**. Исходно: 2 находки HIGH + 1 MEDIUM (прогон 2026-09-18, `main` = `331bd97`, `npm run build` перед прогоном, Node 25.6 / macOS 14). Все функции отработали как описаны в README; находки — про то, чего README не обещает, но пользователь вправе ожидать. На момент прогона код не менялся; исправления — ветка `fix/user-journey-findings`.

**Чем прогоняли:** только то, что есть у пользователя — `mcpcut` на `PATH` (шим на `dist/cli.js`), README как единственная инструкция. Изолированный `HOME` + `MCPCUT_CONFIG` в скретче (реальные `~/.mcp-journal`, `~/.mcpcut` не тронуты), порты 57096 (`ui`) / 57097 (`serve`). Мастер и консоль — pty-драйвер `drive.py` (из `docs/smoke-mcpcut.md`); веб-админка — headless Chromium через Playwright-скрипты (рецепт из памяти, без MCP-гейта); агент — свой stdio-клиент на 30 строк поверх `mcpcut connect` и `curl` поверх `serve`. MCP-серверы: **настоящий** `@modelcontextprotocol/server-filesystem` через `npx` (14 тулзов с аннотациями) + фикстуры `m4-server.mjs` (v1/v2), `http-server-sessionful.mjs`, `http-server-stateless.mjs`.

## Находки

### H1 (HIGH, security) — агент сам выбирает класс тулза: без `tools/list` `destructive` становится `write`

Политика `classDefaults: {read: allow, write: allow}`, `defaultDecision: require-approval`; `files/write_file` выпущен из карантина; сервер объявляет `destructiveHint: true`.

| Сессия | Решение в журнале |
|---|---|
| `tools/list`, затем `tools/call write_file` | `class: destructive · outcome: require-approval-pending · rule: defaultDecision` |
| сразу `tools/call write_file` (без `tools/list`) | `class: write · outcome: allow · rule: classDefaults.write` — файл записан без одобрения |

Причина: `src/proxy/tool-catalog.ts` кеширует дескрипторы только из `tools/list` **этой сессии**; без него классификация идёт по одному имени. Комментарий у `MAX_CACHED_DESCRIPTORS` называет это «безопасным направлением» (никогда не `read`) — но между `write` и `destructive` направление небезопасное, и вызывать ли `tools/list`, решает агент. Одобренный дескриптор с аннотациями при этом лежит в инвентаре (`state.db`), и UI показывает класс именно по нему: карточка сервера обещает `APPROVAL`, а прокси даёт `ALLOW`. Предложение: при промахе кеша сессии брать одобренный дескриптор из инвентаря; имя — только когда нет и его.

### H2 (HIGH, продукт) — журнал не называет агента у обычных решений

`agentName` стоит только на записях `require-approval-pending`. Все `allow`/`deny`/`approved`/`timeout`, `request`/`response` и сама сессия агента не называют: из 20 записей сессии `web-bot` имя несут 2; у HTTP-сессии `ops-bot` (одни `allow`) — 0. Следствия: фильтр «agent» на `/journal` находит только удержанные вызовы (`agent=web-bot` → 2 записи), дашборд пишет `files/<session>`, а экспортированный отчёт не отвечает на вопрос «какой агент сделал этот разрешённый вызов» — связать можно только косвенно через `grantsHash`. Для позиционирования «доказательный журнал» это дыра в атрибуции. Предложение: `agentName` на каждой `decision`-записи (или запись открытия сессии `kind:'session'` с агентом и сервером).

### M1 (MEDIUM) — `serve`, запущенный до появления `policy.json`, остаётся journaling-only до рестарта

Путь README: `setup` (поднимает службы) → позже «drop a `policy.json`» → «running proxies re-read the policy file». Факт: `connect` подхватывает файл (новый процесс), а демон `serve` стартовал с `no policy file found; journaling only` и **не замечает появления файла** — HTTP-агент получил `outcome=allow rule=defaultDecision` при `defaultDecision: require-approval` в файле. После `mcpcut stop serve && start serve` — `policy loaded`, одобрения работают. Горячая перезагрузка покрывает «файл изменился», но не «файл появился». Минимум — фраза в README §Policies и предупреждение в `status`/UI («serve работает без политики, файл на диске есть»); лучше — следить за путём и при отсутствии файла.

### LOW / UX

1. **Веб-вход с неверным токеном** заканчивается голой страницей `{"error":"unauthorized"}` (401 JSON) — без формы и текста; нужен «Назад». Консоль на том же месте говорит `Token not recognised: it may have been rotated…`.
2. **Анимация входа ~5,5 с** между кликом `Enter console` и `POST /login` — при каждом входе (и перед показом ошибки).
3. **`probe: vault-refused — … crm-token?Add each with: …`** — перевод строки в сообщении пробы превращён в `?` (`server add`, `server show`).
4. **`agent: method not grantable in M3: resources/list`** — текст отказа устарел: с M4 ресурсы выдаются грантом, агенту просто не выдали. Там же `Call to tool "resources/list"` — это метод, не тулз.
5. **Viewer видит кнопки `APPROVE`/`REJECT` на `/quarantine`** (сервер отвечает 403, остальные страницы формы прячут); ссылки `VAULT`/`ADMINS` в навигации ведут viewer'а на 403.
6. **Ошибка значения флага печатает весь `USAGE`** (~110 строк) — `prune --older-than 0s`: сама ошибка уезжает за экран.
7. **`ExperimentalWarning: SQLite…`** — две строки stderr на каждую команду и в `logs ui` (Node 24–25.6).
8. `approvals list` показывает `expires_in=4m55s` (TTL заявки), хотя вызов агента ждёт 60 с — оператору не видно, сколько осталось до таймаута агента (`waitExpiresAt` есть в `--json`).
9. `server add`/`server remove` без токена работают и не атрибутируются (README это оговаривает для `remove`; для `add`, который ещё и исполняет команду пробой, — нет).
10. В консоли панель вывода переживает смену раздела: на вкладке Journal остаётся `$ mcpcut approvals list` до первого запуска.
11. `serve` отвечает `400 {"error":"no-grant"}` агенту без гранта — по смыслу `403`.
12. Дашборд после approve/deny перезагружается целиком (известный бэклог), карантин — нет.

## Закрытие H1 и H2 (2026-09-18, ветка `fix/user-journey-findings`)

По TDD, ревью `ecc:typescript-reviewer` + `ecc:security-reviewer` — без CRITICAL/HIGH; все MEDIUM/LOW ревью закрыты в той же волне.

**H1.** У инвентаря появился седьмой синхронный метод контракта — `descriptorOf(toolName)` (третья карта в `buildSnapshots`: карантинный, то есть последний наблюдённый, дескриптор перекрывает одобренный — ровно то, что закешировал бы `tools/list` этой сессии). `ToolCatalog.descriptorOf` теперь: кеш сессии → инвентарь → только имя. Находка security-ревью (MEDIUM), закрыта: враждебный сервер мог раздуть дескриптор за `MAX_STORED_DESCRIPTOR_CHARS`, и `boundDescriptor` выбрасывал аннотации целиком — для сессий без `tools/list` класс снова падал до `write`; теперь аннотации ужимаются до двух хинтов класса (`readOnlyHint`/`destructiveHint`), которые переживают любой кап. Тесты: `tests/policy/inventory-descriptor.test.ts` (8), `tests/proxy/gate-inventory-class.test.ts` (3, включая «листинг сессии перекрывает инвентарь»).

**H2.** `agentName` штампуется в единственной точке записи решений (`stampProvenance`, `src/proxy/gate-decision-writer.ts`) из того же снимка, что `policyHash`/`grantsHash`; имя из черновика отбрасывается (как `grantsHash`), так что запись называет агента тогда и только тогда, когда он есть у scope сессии. Попало на все виды решений: `allow`, `deny`, отказ по гранту, bookkeeping `tools/list`, `approved`/`denied-by-operator`/`timeout`, отзыв агента. Сессии `wrap` по-прежнему без ключа. Фильтр агента на `/journal` и поле Caller на дашборде заработали без правок UI. Записи, сделанные до 18.09, имя несут только на `require-approval-pending`. Тесты: `tests/proxy/gate-agent-attribution.test.ts` (10).

Живая проверка на стенде смока (агент `web-bot`, `edit_file` **без** `tools/list`, `classDefaults.write: allow`):

| Запись | До | После |
|---|---|---|
| `edit_file` | `class: write · allow` | `class: destructive · require-approval-pending` → `timeout`, файл не тронут |
| `agentName` на `allow`/`timeout` | нет | `web-bot` |
| `verify` | — | цепочка цела (266 записей) |

Наблюдения security-ревью вне объёма волны (владельцу): (1) для `changed`-тулза можно складывать хинты одобренного и карантинного дескрипторов «только на повышение» — при `quarantine.enabled: true` на исход не влияет, только на поле `toolClass` в журнале; (2) `catalogObserved` остаётся посессионным: агент, не вызывающий `tools/list`, не попадает под shadow-tool-ветку для имени, которого **никто никогда** не наблюдал, — задокументированный компромисс `decide.ts`, родственный H1.

## Закрытие M1 (2026-09-18, решение владельца: подхватывать)

Процесс, стартовавший без файла политики (`serve`, `connect`), больше не держит статический fallback: `createAwaitingPolicyProvider` (`src/policy/reload-await.ts`) на горячем пути смотрит кандидаты своей точки входа и один раз привязывается к первому **валидному** файлу; дальше — обычный закреплённый провайдер. Битый файл не подхватывается и сообщается. Поправка в ADR-0009, README §Policies, CHANGELOG. Тесты: `tests/policy/reload-await.test.ts` (11), `tests/cli/serve-policy-adopt.test.ts` (2, настоящий фронт, уже открытая сессия), `tests/cli/connect-policy-adopt.test.ts` (2, включая «проектный файл из cwd агента не подхватывается никогда»).

Живой повтор сценария находки (тот же стенд, `serve` поднят без `policy.json`, сессия HTTP-агента открыта):

Ревью M1 (`ecc:typescript-reviewer` + `ecc:security-reviewer`): CRITICAL нет; единственная существенная находка (HIGH у TS, MEDIUM у security — одна и та же) закрыта в волне: `mapPolicyProvider` копировал `sourcePath` в момент обёртки, а обе точки входа оборачивают провайдер до гейта (`--fail-closed`), так что после подхвата обёртка навсегда называла бы `<no policy file>`. На решения и `policyHash` не влияло (они идут через `current()`), только на диагностику; поле стало геттером-сквозняком, регрессионный тест в `reload-await.test.ts` (12). Дубль `safely()` вынесен в `reload-fs.ts`. Проверено ревью и найдено чистым: класс доверия ADR-0005 (required-кандидат не может ждаться — его отсутствие на старте это ошибка, а не `disabled`), направление (подхват не расширяет), гонки (`bound` ставится один раз, синхронно), `policyHash` корректно двигается в момент подхвата. Оставлено владельцу: у файла политики нет предела размера (пробел существовал и в обычной перезагрузке; непринятый битый файл перечитывается каждые 250 мс; кандидаты пишет только оператор).
