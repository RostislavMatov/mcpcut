# ADR-0008: Активная проба MCP-сервера — состояние подключения ценой исполнения по обращению

- **Статус**: принято (2026-08-24, M5.5 пункт 1)
- **Область** (целевая — кода пробы на момент принятия нет): новый документ состояния
  `server-status.json` в таблице `documents` базы `state.db` (через существующий `createJsonStore`
  с CAS), новый модуль пробы (рабочее имя `src/probe/**`), `src/ui/pages/servers.ts`,
  `src/ui/authz.ts` (новая строка таблицы маршрутов), `src/cli/server-cmd.ts` (`server refresh`),
  `src/policy/inventory-observe.ts` (вход результата `tools/list` из пробы), `src/journal/**`
  (новая категория записей — факт и исход пробы). `src/registry/schema.ts` **не меняется**.
- **Основание**: `.claude/plans/milestone-5.5.plan.md`, пункт 1, блок «Решения владельца PRD по
  пункту 1 (2026-08-24)» — решения **O1–O8**. Этот ADR **оформляет** принятые решения и не
  пересматривает их. Гейт этапа требует: «Модель угроз пробы (побочный эффект — спавн процесса /
  сетевой запрос) явно согласована с ADR, описывающим регистрацию stdio-сервера, — либо отдельным
  ADR, либо дополнением существующего». Выбрана форма отдельного ADR; ADR-0004 получает
  поправку-ссылку в разделе «От чего НЕ защищаемся».

## Контекст

Реестр серверов чисто декларативен: `registry.json` (строка в таблице `documents` базы `state.db`)
хранит `name`/`transport`/target и ничего о состоянии — ни статуса, ни last-seen, ни таймстампов
(`src/registry/schema.ts`). Следствие, зафиксированное в плане M5.5: оператор узнаёт о нерабочем
сервере тем же способом, что и агент — по факту неудачного вызова. Ни `/servers`, ни
`server list/show` не отвечают на вопрос «жив ли он и с какой задержкой».

`journal.db` знает **активность**, а не **доступность**: сервер, к которому просто никто не
обращался, в журнале неотличим от мёртвого. Только что зарегистрированный сервер не имеет в журнале
вообще ничего — и по той же причине плоскость не знает ни одного его тулза: инвентарь наполняется
исключительно из живого трафика, перехватывая ответы `tools/list` через прокси
(`src/policy/inventory-observe.ts`).

Против этого стоит рамка, действовавшая с M3: **плоскость исполняет чужую командную строку только
тогда, когда человек эту строку подтвердил**. Регистрация `stdio`-сервера — remote code execution
по архитектуре, и экран подтверждения существует именно затем, чтобы оператор увидел точную команду
до того, как плоскость её заспавнит (`src/ui/pages/servers.ts:191–219`; тот же экран стоит и перед
`/servers/edit`). `http`-регистрация мягче по механике, но не по существу: плоскость обращается к
названному эндпоинту **с учётками из вольта**.

Активная проба ломает эту рамку, потому что состояние подключения нельзя узнать, не подключившись.
План M5.5 рекомендовал минимальный размен — «проба только по кнопке, ручная и атрибутируемая».
Владелец PRD выбрал иной размен (O2, O5): проба **ленивая, но автоматическая**, и триггерит её в
том числе просмотр страницы ролью `viewer`. Причина выбора — страница обязана отвечать на вопрос,
за которым её открывают; статус, появляющийся только после отдельного действия, оставляет оператора
в исходном положении ровно в тот момент, когда информация нужна. Этот ADR существует, чтобы
изменение модели угроз было **названо**, а не проехало явочным порядком вместе с фичей.

## Решение

### 1. Источник статуса — гибрид: журнал первичен, проба закрывает тишину (O1)

Пока по серверу идёт трафик, статус выводится из журнала — бесплатно и без побочных эффектов.
Тишина дольше порога (ориентир ~1 час; конкретная константа фиксируется в плане волн) означает,
что журнал больше не отвечает на вопрос, и статус берётся из активной пробы.

Словарь статусов: **жив** · **отвечает с ошибкой** · **не отвечает** · **проверяется**
(и «не проверялся» как начальное состояние записи).

### 2. Триггеры пробы: ровно три, фонового таймера нет (O2, O8)

| Триггер | Кто/что запускает | Минимальная роль |
|---|---|---|
| `register` — один автозапуск сразу после подтверждения регистрации (с `tools/list`) | человек только что подтвердил ровно эту командную строку | `owner` (роль `POST /servers/{add,edit}`) |
| `view` — ленивая проба при обращении к статусу, если данные устарели (`GET /servers`, `server list/show`) | просмотр страницы или CLI-чтение | `viewer` |
| `refresh` — принудительная проба вне порога свежести, с переснятием `tools/list` | явное действие админа | `operator` |

**Инвариант, который этот ADR делает нормативным**: у пробы нет ни таймера, ни крона, ни фонового
watcher-а. Без обращения человека (или его браузера) плоскость не исполняет ничего — остановленный
`ui` и неоткрытая страница дают гарантированный ноль проб. Это единственное, что отделяет принятое
решение от «незаявленного демона, исполняющего чужие команды в пустой комнате» (см. таблицу
отвергнутого).

`tools/list` **никогда** не выполняется до подтверждения регистрации человеком: «показать тулзы до
подтверждения» означало бы исполнение до согласия.

### 3. Метрика — одна на оба транспорта (O4)

Время от начала попытки (spawn процесса / установление соединения) до **валидного ответа на
`initialize`**. Это первая точка, где сервер доказывает, что говорит по протоколу MCP, а не просто
«процесс запустился»/«порт слушает». `tools/list` в замер **не входит** — это отдельный, более
дорогой шаг пробы, стоимость которого зависит от числа тулзов и исказил бы метрику.

### 4. Хранение — отдельный документ, реестр остаётся декларативным (O3)

`server-status.json` (рабочее имя) — отдельная строка в таблице `documents` базы `state.db`, через
тот же `createJsonStore` с CAS, по образцу `registry.json`/`agents.json` (ADR-0006). Состояние
разделяется между `ui` и CLI, поэтому «жив, проверено 3 минуты назад» одинаково видно с обеих
поверхностей и переживает перезапуск процесса.

Поля состояния **не** добавляются в `registry.json`: смешение декларативного конфига с изменчивым
рантайм-состоянием противоречит тому, зачем реестр выделен в отдельную схему, и заставляло бы
каждую пробу крутить `rev` документа через CAS ради данных, которые конфигурацией не являются.

### 5. Права: чтение триггерит исполнение, принуждение — нет (O5)

`GET /servers` остаётся доступным от `viewer` — минимальная роль в таблице ADR-0004 (Решение 4) не
меняется, **меняется её смысл**: теперь этот маршрут может повлечь спавн процесса на хосте.
Таблица маршрутов пополняется одной строкой:

| Маршрут | Минимальная роль |
|---|---|
| `POST /servers/refresh` | `operator` |

`refresh` — та же роль, что уже отвечает за карантин и очередь одобрений, то есть за действия с
последствиями за пределами просмотра. CLI-паритет обязателен (`server refresh` с тем же порогом
роли — иначе таблица обходится через терминал, урок поправки ADR-0004 от 2026-08-18).

### 6. Журналируется факт и исход, не трафик обмена (O6)

Каждая проба даёт **одну** запись: сервер, триггер (`register` | `view` | `refresh`), инициатор,
исход, латентность, причина ошибки. Обмен `initialize`/`tools/list` в журнал целиком **не** идёт —
служебный трафик плоскости раздул бы журнал и, что важнее, размыл бы доказательную картину «что
сделал агент».

Атрибуция инициатора **структурно отлична** от агентского вызова: `actor` записи пробы называет
плоскость и человека, по чьему обращению проба произошла (форма — по образцу `cli:<adminName>` из
M5, волна 2), и никогда не имя агента. Записи пробы обязаны быть **отделимы** от трафика агентов и
в поиске UI-журнала, и в экспорте аудит-отчёта M5: иначе служебная проба попадёт в отчёт как
действие агента и исказит то, ради чего отчёт существует.

Редакция секретов — тот же единственный путь в журнал: заголовки `http`-сервера, разрешённые из
вольта, в записи пробы не появляются никогда (тест-гарантия, как для обычного трафика).

Записи пробы идут **существующим** путём записи — тот же батч-писатель, то же звено хеш-цепочки,
та же подписанная глава (ADR-0007). Новая категория записей, а не новый путь: журнал остаётся
tamper-evident **with an external anchor** без исключений для служебных записей.

### 7. `tools/list` из пробы идёт в штатный инвентарь, не во второй (O8)

Результат `tools/list` попадает в тот же инвентарь, что и наблюдённый трафик: тулз с совпадающим
`schemaHash` повторно **не** карантинится, новый или изменённый — попадает в карантин со структурным
диффом штатным путём. Отдельного «инвентаря из проб» не появляется — два источника истины о
поверхности тулзов означали бы два разных мнения о том, что карантинить. Требование закрепляется
отдельным тестом (явное указание O8).

Описания тулзов — текст, контролируемый сервером, untrusted-for-render: экранирование как у
карантинного диффа. Урок финального ревью M5 применяется напрямую: **усечение длинных описаний
обязано быть явным**, а не «уверенным» — усечённый вывод, выглядящий полным, уже однажды оказался
каналом, которым враждебный сервер удерживал устаревший `allow`.

### 8. Отображение: страница не ждёт пробу (O7)

Страница отдаётся мгновенно с последними известными статусами; устаревшие проверяются в фоне
процесса `serve`/`ui`, и полученный статус проставляется без перезагрузки — SSE-пуш по образцу
дашборда. Это **осознанное отступление** от «вся админка работает без JS»: без JS страница
деградирует до последних сохранённых статусов, свежие приходят по перезагрузке.

Индикатор — точка в стиле McpCut: белая = жив (по пробе); белая мигающая = жив, есть недавняя
активность в трафике; серая = не живой; серая мигающая = идёт проверка. Тултип обязателен и несёт
источник (трафик/проба), время, латентность или причину ошибки: голая точка без метки времени
превращает многочасовую пробу в ложное «сейчас жив», что хуже отсутствия индикатора.

## Изменение модели угроз — что именно стало иначе

**Было**: плоскость исполняет чужую командную строку (или обращается к чужому эндпоинту с
секретами) только по прямому подтверждению человека, один раз на подтверждение.
**Стало**: **чтение может исполнить.** Просмотр страницы или CLI-чтение статуса может повлечь спавн
процесса на хосте плоскости и сетевой запрос с учётками вольта.

Последствия, которые ADR обязан назвать прямо:

1. **`viewer` становится триггером исполнения.** Роль, задуманная как «только смотрит», теперь
   опосредованно запускает код на хосте. Формально строка таблицы authz не изменилась — изменилась
   её семантика, и это ровно тот случай, когда «минимальная роль» перестаёт описывать реальные
   последствия запроса.
2. **Исполняется уже подтверждённая строка, а не новая.** Проба берёт запись реестра байт-в-байт и
   не принимает от запроса никаких параметров, влияющих на то, что будет запущено. Человек
   по-прежнему решает, **что** исполняется; он больше не решает, **когда** и **сколько раз**.
3. **`http`-проба отправляет секреты вольта на URL из реестра.** Обращение к статусу становится
   обращением к третьей стороне с чужими учётками. URL выбирает `owner` при регистрации, а
   отправку триггерит `viewer` — разделение «кто выбрал цель» и «кто вызвал обращение» новое, и оно
   же делает поверхность похожей на SSRF: цель ограничена реестром, но инициировать обращение может
   роль чтения.
4. **Фан-аут и усиление.** Один просмотр `/servers` при N серверах с устаревшим статусом = до N
   спавнов/запросов. Открытая на киоске или автообновляемая вкладка превращает «ленивую» пробу в
   фактический таймер — то есть даёт ровно тот фоновый исполнитель, который решение O2 отвергает.
   Это самая неприятная часть размена, и компенсации ниже адресуют именно её.
5. **Сломанный сервер как источник шума.** Сервер, который стабильно падает при спавне, при каждом
   просмотре даёт процесс-однодневку и запись в журнал; без ограничителя это самоподдерживающийся
   мусор в доказательной цепочке.
6. **Сервер узнаёт, что на него смотрят.** Проба — наблюдаемый снаружи сигнал о том, что админ
   открыл страницу. Малый по значимости, но реальный побочный канал; называется здесь, чтобы не
   всплыл как «сюрприз» на пилоте.

### Компенсирующие меры

- Проба исполняет **байт-в-байт** ту командную строку (или тот URL и набор имён секретов), которая
  лежит в подтверждённой записи реестра; ни один параметр запроса не влияет на исполняемое.
  Изменение записи проходит через тот же экран подтверждения (`/servers/edit`), поэтому пробуемая
  строка всегда подтверждена последним человеком, который её менял.
- **Никакого фонового исполнения без обращения**: нет таймера, нет крона, нет watcher-а.
  Остановленный процесс UI = ноль проб, и это проверяемое утверждение, а не обещание.
- **Порог свежести** (проба только если статус устарел), **cooldown на сервер** (в том числе
  усиленный после неудачи — backoff), **дедупликация in-flight** (одна проба на сервер
  одновременно, параллельные обращения ждут её результата) и **ограничение параллелизма** на
  просмотр — четыре ограничителя против фан-аута из пункта 4.
- **Таймаут пробы** обязателен: зависший спавн не держит ни страницу, ни слот.
- **Журналирование факта и исхода** с атрибуцией инициатора, отделимой от агентского трафика — то
  есть исполнение по чтению не бесследно: у каждой пробы есть named человек, по чьему обращению она
  произошла.
- **Редакция секретов** — тот же единственный путь в журнал; `Authorization`/`Bearer` не попадают в
  журнал никогда.
- **`refresh` (принудительная проба) — `operator`+**: обход порога свежести остаётся действием, а не
  чтением.
- **Ноль новых прод-зависимостей** (ADR-0001): проба использует существующий транспорт и платформу.

### Что этими мерами НЕ закрыто

- `viewer` остаётся триггером исполнения. Закрыть это можно только сузив триггер до `operator`+ —
  вариант, рассмотренный и отвергнутый владельцем (см. таблицу ниже). Принятая цена, не дефект
  реализации.
- **Политика к пробе не применяется.** Проба — не вызов агента, у неё нет ни агента, ни гранта, ни
  класса тулза; `allow`/`deny`/`require-approval` её не гейтят, и `deny`-правило на сервер не
  запрещает пробу этого сервера. Это следует из решения, а не из недосмотра, но выглядит
  неожиданно и вынесено в открытые вопросы владельцу.
- **Граница доверия uid не меняется** (ADR-0003, ADR-0004): процесс под тем же uid и без пробы может
  запустить ту же команду. Проба не понижает и не повышает эту границу — она меняет то, **что
  делает сама плоскость**, а это разговор об ожиданиях оператора, не о новом канале для атакующего,
  уже получившего uid.

## Что отвергнуто и почему

| Вариант | Почему нет |
|---|---|
| **Проба только по кнопке** (рекомендация плана M5.5 по вопросам 1–2) | Даёт нулевой побочный эффект от чтения, но оставляет экран без ответа ровно в тот момент, когда его открыли ради ответа; для ни разу не использованного сервера статус и список тулзов не появляются вообще без отдельного действия. Отвергнуто владельцем (O2) в пользу «страница отвечает на свой вопрос». Сохранено частично: `refresh` — это и есть та кнопка, для случаев «проверь сейчас» |
| **Фоновый таймер / крон** | Превращает разовое подтверждённое исполнение в незаявленный демон, спавнящий чужие командные строки без человеческой причины для каждого конкретного запуска. Хуже ленивой пробы по обоим измерениям: нет привязки к обращению человека и нет естественного ограничителя частоты. Отвергнуто (O2) |
| **Только пассивный сигнал из журнала** | Бесплатен и не меняет модель угроз, но отвечает на другой вопрос: активность ≠ доступность. Тихий сервер неотличим от мёртвого, только что зарегистрированный — всегда «неизвестно», а сценарий «вижу тулзы в момент добавления» не выполняется вовсе |
| **Поля состояния в `registry.json`** | Смешивает декларативный конфиг с изменчивым рантайм-состоянием и крутит `rev` документа через CAS на каждую пробу ради данных, которые не конфигурация (O3) |
| **Не хранить состояние вовсе, считать на лету** | Нет паритета CLI/UI (каждый процесс пробует сам), перезапуск обнуляет историю, и «последняя известная проба» — единственное, что позволяет отдать страницу мгновенно (O7) |
| **Триггер только `operator`+, `viewer` видит лишь сохранённое** (рекомендация плана по вопросу 5) | Отвергнуто владельцем (O5): `viewer` с пустым или заведомо устаревшим экраном не выполняет своей роли. Записано как принятая цена, а не как недосмотр |
| **Активная проба только для `http`** (для `stdio` — пассивный сигнал) | Ответ на вопрос «жив ли сервер» обязан быть одинаковым для обоих транспортов; расщепление семантики статуса по транспорту дороже локальной экономии риска, а `stdio` — как раз преобладающий случай |
| **`tools/list` до подтверждения регистрации** (чтобы форма сразу показала тулзы) | Исполнение до согласия. Прямо запрещено: экран подтверждения существует ровно затем, чтобы человек увидел командную строку **до** её исполнения |
| **Отдельный «инвентарь из проб»** | Два источника истины о поверхности тулзов = два разных мнения о том, что карантинить, и щель, в которую пролезает изменённая схема (O8) |
| **Писать в журнал полный обмен пробы** | Раздувает журнал служебным трафиком и, главное, искажает доказательную картину «что сделал агент» в экспорте отчёта M5 (O6) |
| **Дать пробе собственный ключ/канал записи в журнал** | Второй путь записи означает второе место, где может разъехаться хеш-цепочка; проба идёт существующим путём и попадает под ту же подписанную главу (ADR-0007) |

## Последствия

- (+) Страница и CLI отвечают на вопрос, ради которого их открывают, включая сервер, которым ещё ни
  разу не пользовались; список тулзов появляется в момент добавления, а не после первого агента.
- (+) Реестр остаётся чисто декларативным; состояние живёт отдельно и разделяется UI и CLI.
- (+) Каждое исполнение по чтению атрибутировано и попадает в ту же доказательную цепочку, что и
  остальной журнал; отчёт M5 умеет отделить пробу от действий агента.
- (+) Нет фонового исполнения: остановленный UI — гарантированный ноль проб.
- (−) **Право чтения приобретает побочный эффект исполнения** — главная цена решения, названная
  выше целиком.
- (−) Открытая на постоянном экране страница фактически возвращает периодическое исполнение;
  сдерживается только порогом свежести и cooldown, то есть константами, а не структурой.
- (−) `http`-проба отправляет секреты вольта по обращению роли чтения.
- (−) Журнал получает новую категорию записей, растущую от просмотров, а не от работы агентов:
  взаимодействие с retention-prune и с объёмом отчёта нужно проверить на пилоте.
- (−) SSE-пуш статуса — второе отступление админки от «работает без JS» (первое — дашборд).

**Требования к тестам** (нормативная часть, без них решение остаётся прозой):

1. Без обращения проб не происходит: прогон времени вперёд при отсутствии запросов даёт ноль
   спавнов (доказательство отсутствия таймера).
2. Пробуемая командная строка/цель байт-в-байт равна записи реестра; параметры запроса на неё не
   влияют.
3. `schemaHash`-совпадение из пробы не карантинит тулз повторно; изменённая схема карантинится со
   структурным диффом (явное требование O8).
4. Ни одно значение вольта не встречается в записи пробы, в SSE-потоке и в отчёте.
5. Записи пробы отделимы от агентского трафика в поиске журнала и в экспорте отчёта.
6. Матричный тест authz покрывает `POST /servers/refresh`; CLI `server refresh` требует ту же
   минимальную роль.
7. Дедупликация in-flight и cooldown: N параллельных просмотров дают одну пробу на сервер.

## Когда пересматриваем

- **Партнёр держит UI открытым постоянно** (киоск, дежурный экран, автообновление): ленивая проба
  становится таймером де-факто. Ответ — ужесточение cooldown или сужение триггера до `operator`+;
  это правка данного ADR, а не тихая правка константы.
- **Не-localhost развёртывание**: между браузером и плоскостью появляется сеть, и аутентифицированный
  `viewer` с другой машины получает способ вызывать исполнение на хосте плоскости. Пересмотр
  обязателен вместе с пересмотром модели угроз ADR-0004.
- **Появится скоуп по серверам в ролевой модели** (ADR-0004 предсказывает «маршрут × роль × скоуп»):
  тогда «кто может пробовать какой сервер» перестаёт быть одномерным.
- **Партнёр потребует непрерывный мониторинг/SLA по серверам**: это фоновый агент, то есть ровно
  то, что здесь отвергнуто; такое требование закрывается отдельным решением и отдельным ADR (с
  отдельным ответом на «чем это не незаявленный крон»), а не расширением этого.
- **`http`-проба окажется путём во внутренние сети партнёра**: потребуется операторский allowlist
  целей на уровне плоскости.
- **Отложенное исполнение write-intents** (бэклог ROADMAP): плоскость становится актором от своего
  имени в общем виде; тогда провенанс действий плоскости решается одним механизмом, а запись пробы
  становится его частным случаем.
- **Пилот покажет, что записи проб доминируют в журнале**: тогда пересматривается либо гранулярность
  записи (одна запись на серию), либо взаимодействие с retention.

## Связанные решения

- **ADR-0004** — модель угроз Admin UI и таблица «маршрут × минимальная роль». Этот ADR добавляет в
  таблицу `POST /servers/refresh` (`operator`) и **меняет смысл** существующей строки
  `GET /servers` (`viewer`): маршрут чтения получил побочный эффект исполнения. В ADR-0004 внесена
  поправка-ссылка в разделе «От чего НЕ защищаемся».
- **ADR-0005** — класс доверия входа. И `ui`, и операторский CLI остаются `operator-launched`;
  проба не меняет источник политики и сама через политику не проходит (см. «Что не закрыто»).
- **ADR-0003** — граница доверия «учётная запись ОС»; `http`-проба отправляет секреты вольта, но
  границу не сдвигает.
- **ADR-0006** — хранилище: `server-status.json` — документ в `documents` базы `state.db` с CAS,
  по образцу `registry.json`/`agents.json`.
- **ADR-0007** — доказательный журнал: записи пробы идут существующим путём записи (звено цепочки,
  подписанная глава), проходят редакцию и обязаны быть отделимы в экспорте отчёта. Журнал остаётся
  «tamper-evident **with an external anchor**». Урок финального ревью M5 об усечённом дифф-выводе
  применён к описаниям тулзов из пробы.
- **ADR-0002** — обе модели сессий Streamable HTTP: `http`-проба выбирает модель по полю `protocol`
  записи реестра и между моделями не транслирует.
- **ADR-0001** — граница зависимостей: проба не добавляет прод-зависимостей.

  (2026-08-24) — источник всех решений этого ADR.
