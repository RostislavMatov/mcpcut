# ADR-0019: подтверждение вызова прямо в клиенте (MCP form elicitation)

- **Статус**: принято (2026-10-01, решение владельца M17 «P2 и P3 в выпуске до запуска»; предложение P2).
  **Пересмотрено 2026-10-02** (решение владельца M19): подтверждение в клиенте — отдельное правило, а не
  второй способ ответить на заявку админа. Прежняя редакция (окно закрывало ту же заявку в очереди,
  `approveInClient`, `approval.askClient`) не выпускалась.
- **Область**: `src/policy/confirm-in-client.ts`, схема `servers.<имя>.confirmInClient`,
  `src/proxy/client-confirm.ts` (+ `-text.ts`), `gate-confirm.ts` (шаг гейта), `gate-call.ts` (порядок
  решения), `gate-router.ts` (перехват ответов, `initialize`), `gate-approvals.ts` (`confirmedBy` на
  записях), точки входа `wrap` и `connect`
- **Дополняет**: очередь одобрений M4 и правило атрибуции M5 (`cli:<admin>`, `ui:<admin>`)

## Контекст

Главный сценарий владельца: Claude Code в полном автомоде (вплоть до `--dangerously-skip-permissions`), всё
проходит без вопросов, и только названные инструменты останавливаются, а вопрос задаётся прямо в сессии.
MCP form elicitation позволяет серверу задать человеку вопрос в интерфейсе клиента. Баг Claude Code #62319
закрыт без исправления, поэтому сначала была живая проверка: 2026-10-01 Claude Code 2.1.286 и 2.1.287
объявили `elicitation: {form, url}`, показали окно «MCP server … requests your input … ❯ Accept Decline ·
Esc to cancel» и вернули `accept` / `decline` / `cancel` по нажатию; 2026-10-02 — то же в режиме
`--dangerously-skip-permissions`.

Владелец (2026-10-02): «подтверждение админа и подтверждение клиента — две разные сущности. У инструмента
может быть подтверждение клиента без подтверждения админа, подтверждение админа без подтверждения клиента
или и то и другое», и указывать нужно, **каких агентов** это касается.

## Решение

1. **Два независимых правила у инструмента.** Админское — прежнее `servers.<имя>.tools` (`allow` /
   `require-approval` / `deny`, очередь одобрений). Новое — `servers.<имя>.confirmInClient`:

   ```json
   "confirmInClient": { "write_file": ["*"], "delete_*": ["laptop", "alice-cursor"] }
   ```

   Ключи — как у `tools` (точное имя или `префикс*`, побеждает самое точное **вместе со своим списком**:
   при `{ "write_*": ["*"], "write_file": ["laptop"] }` `write_file` подтверждает только `laptop` — как у
   `tools`, где точное правило заменяет шаблон; объединять списки не стали, чтобы точная запись могла
   сузить шаблон и чтобы UI показывал одно правило на инструмент). Значение — непустой список
   имён агентов (формат имён — как в хранилище агентов) или `"*"`: все агенты **и** локальный `wrap`, у
   которого агента нет. Агенты не из списка получают только правило админа.

2. **Порядок в гейте** (`gate-call.ts`): `deny` побеждает всё → если нужно подтверждение в клиенте —
   окно → после Accept вызов **решается заново** под правилами на этот момент (человек думал секунды, и
   правило, ставшее `deny`, сильнее его Accept) → `allow` пропускает, `require-approval` ставит в очередь
   админа. Получается:

   | Админ | Клиент | Итог |
   |---|---|---|
   | allow | — | проходит |
   | allow | вкл | окно → Accept → проходит; админ не нужен |
   | require-approval | — | очередь админа; окна нет |
   | require-approval | вкл | окно → Accept → очередь админа; Decline — отказ сразу, админа не беспокоим |
   | deny | любое | отказ, окна нет |

3. **Подтверждение никогда не подменяет админа, и наоборот.** Окно не закрывает заявку в очереди; Esc,
   ошибка и тайм-аут не отправляют вызов в очередь. Поэтому исчезла гонка прежней редакции («правило
   изменилось, пока окно было открыто, — ответ недействителен»): устаревшее подтверждение ничего не
   открывает, оно лишь добавляет проверку.

4. **Любое «не подтверждено» — отказ**, с записью в журнал и ответом агенту (`client_confirm_*`):
   Decline и Esc — `denied-by-operator` с actor `client:<имя>` (правила `client-confirm-declined`,
   `-cancelled`); Accept быстрее секунды дважды — `deny`, `client-confirm-too-fast`; нет ответа за
   `approval.timeoutMs` — `timeout`, окно закрывается `notifications/cancelled`; клиент не умеет форму
   или ответил ошибкой — `deny`, `client-confirm-unavailable` / `-failed`, а в stderr оператора — строка,
   что сделать; конец сессии — `client-confirm-session-ended`; вызов без id — `client-confirm-idless`.

5. **Где работает.** Окно задаётся на stdio-путях — `wrap` и `connect` агента (`confirmInClient` у гейта
   есть). У HTTP-путей (`serve`, пул, hosted, `connect --url`) канала к клиенту нет: вызов, которому
   нужно подтверждение, отклоняется (`unavailable`) — закрыто, а не открыто. Часть Б (HTTP) — после
   запуска. Ожидание (`approval.timeoutMs`, читается при старте сессии) считается от вызова, а не от
   показа окна: окна идут по одному, и при нескольких вызовах сразу у поздних окон времени меньше — так
   вызов агента не ждёт дольше окна.

6. **Журнал.** Новое необязательное поле записи решения `confirmedBy` (`client:<имя клиента из
   initialize>`, проходит через редактор, как `actor`) — на `allow`, на `require-approval-pending` и на
   итоговой записи очереди. На `approved` `actor` — админ, `confirmedBy` — человек у клиента. Читатель
   журнала лишние поля принимает (`line-source.ts`), отчёт и `verify` их не трогают.

7. **Что видит агент.** Сообщение об отказе говорит, чего не хватило, но не как снять правило: агент с
   доступом к файлам мог бы сам убрать инструмент из политики. Строка с именем правила — только в stderr
   оператора.

8. **Окно** (`client-confirm.ts`): форма с пустой схемой, `mode: "form"` — только клиенту, объявившему
   `form`. Свои id `mcpcut-confirm-<случайная метка сеанса>-<n>[-2]`: ответы на них прокси забирает из
   потока и не пересылает серверу, метка не даёт серверу угадать или занять такой id. Вопросы — строго по
   одному. Окно открывается с фокусом на Accept, поэтому Accept быстрее 1 с не засчитывается: вопрос
   задаётся ещё раз с пояснением; быстрый Decline засчитывается.

9. **Текст**: аргументы по полям (до 12 полей, значения до 160 знаков через редактор секретов, без
   управляющих символов, с пометкой о скрытом); если что-то скрыто — «Not everything is shown. Decline if
   you are not sure.» (в очереди вызова ещё нет — читать целиком негде). Последняя строка говорит, что
   будет: «Accept runs it now.» или, при `require-approval`, «Accept passes it on to an admin, who
   approves it too.»; «Decline or Esc refuses it.»

10. **Каждый вызов подтверждается отдельно** — окна доверия на N секунд нет (решение владельца).

## Отвергнуто

- **Окно как второй способ ответить на заявку админа** (первая редакция) — смешивает две сущности: при
  «оба» человек получил бы два окна об одном вызове, а правило «без админов окно закрывает любую заявку»
  делало подтверждение незаметной заменой админа.
- **`approvals approve` с токеном агента** — токен лежит в конфиге клиента, модель с оболочкой прочтёт его
  и одобрит свой вызов.
- **Различать агентов по имени клиента** (`clientInfo.name`) — клиент называет себя сам; право
  подтверждать на этом строить нельзя. Для `wrap` без токена — только `"*"`.
- **При клиенте без окна — в очередь админа** — снова смешивает сущности; отказ с понятной строкой честнее.

## Последствия

- Stop в Claude Code — один клик в той же сессии, без второго терминала; полный автомод клиента и стоп на
  названных инструментах совместимы.
- Граница доверия: агент не отвечает на вопрос сам — его видит человек в интерфейсе клиента. Клиент под
  управлением программы (SDK-хост, CI) ответит сам — такому агенту подтверждение в клиенте не назначают;
  правило «быстрее секунды не считается» ловит мгновенные автоответы, но не медленные. Сказано в
  руководстве.
- Свои инструменты Claude Code (Bash, Write, Edit) идут мимо MCP, и mcpcut их не видит — отдельное
  предложение P4.
- Не проверено: Cursor и другие клиенты; повторный вопрос после Esc; URL elicitation.
