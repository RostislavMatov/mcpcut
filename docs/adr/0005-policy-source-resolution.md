# ADR-0005: Источник политики определяется классом доверия входа, а не самим входом

- **Статус**: принято (2026-08-11, Волна 0 M4)
- **Область**: `src/policy/source.ts` (новый), `src/policy/load.ts`, `src/cli/connect-policy.ts`,
  `src/cli/serve-cmd.ts`, `src/cli/wrap-cmd.ts`, `src/cli/policy-cmd.ts`, `src/cli/ui-cmd.ts`
- **Основание**: `.claude/plans/admin-ui-approvals.plan.md` (Task 7, «Интеграция пяти пунктов
  бэклога M3»); бэклог-пункт ROADMAP «Несимметричный источник политики у `connect` и `serve`»
  (из ручного смока 2026-08-10)

## Контекст

`policy/load.ts` определяет четыре источника `policy.json`, проверяемые по порядку, **первый
найденный побеждает — слияния нет** (слияние security-конфига из нескольких мест — классический
footgun «откуда взялся этот allow?», решение M2):

1. `--policy <path>` (явный флаг CLI);
2. `$MCP_JOURNAL_POLICY`;
3. `<cwd>/.mcp-journal/policy.json` (проектный уровень);
4. `<journalDir>/policy.json` (каталог состояния плоскости, по умолчанию `~/.mcp-journal/`).

Источники 1 и 2 названы оператором явно — отсутствие файла там жёсткая ошибка; 3 и 4 —
умолчания, их отсутствие означает переход к следующему кандидату, а при полном отсутствии —
journaling-only.

`connect` ведёт себя иначе: он **отказывает** на `--policy` и **игнорирует** `$MCP_JOURNAL_POLICY`
и проектный файл, оставляя только каталог состояния. Это правильное поведение, но до сих пор оно
существовало **как комментарий в `src/cli/connect-policy.ts` и больше нигде**. Ручной смок
2026-08-10 предъявил результат: оператор увидел, что `serve` подхватывает
`./.mcp-journal/policy.json`, а `connect` его демонстративно игнорирует, и не смог вывести это
различие ни из справки, ни из документации — асимметрия выглядела случайной. В бэклог она попала
формулировкой «свести к одному правилу разрешения в M4».

M4 добавляет четвёртый вход — `mcp-journal ui` — и без явного правила пришлось бы решать
заново, как ведёт себя он.

## Решение

**Источник политики определяется классом доверия входа, а не именем команды.**

Каждый вход относится к одному из двух классов:

- **`agent-launched`** — процесс запускается **конфигом агента** (например, `.mcp.json` клиента).
  Значит `argv`, `cwd` и окружение — недоверенная сторона границы: их контролирует та же сторона,
  которую политика и ограничивает. Такой вход читает политику **только из каталога состояния
  плоскости**.
- **`operator-launched`** — процесс запускает человек-оператор из своей оболочки. `argv`, `cwd`
  и окружение здесь операторские, то есть доверенные ровно настолько же, насколько сам запуск.
  Такой вход сохраняет полный четырёхуровневый порядок `load.ts` **без изменений**.

### Таблица: вход × класс доверия × источники по порядку

| Вход | Класс доверия | Источники по порядку | `--policy` | `$MCP_JOURNAL_POLICY` | Проектный `<cwd>/.mcp-journal/policy.json` |
|---|---|---|---|---|---|
| `connect <server> --agent <name>` | `agent-launched` | 1. `<journalDir>/.mcp-journal/policy.json`<br>2. `<journalDir>/policy.json` | **отказ** (exit `EXIT_CODE_REFUSED`) с объяснением, где политика обязана лежать | игнорируется, одна заметка в stderr | игнорируется, одна заметка в stderr |
| `wrap -- <cmd>` | `operator-launched` | Порядок `load.ts` 1→4 | уважается (обязан существовать) | уважается (обязан существовать) | уважается |
| `serve` | `operator-launched` | Порядок `load.ts` 1→4 | уважается | уважается | уважается |
| `ui` | `operator-launched` | Порядок `load.ts` 1→4 (только чтение, для показа) | уважается | уважается | уважается |

Уточнение к строке `connect`: оба кандидата резолвятся **внутри** каталога состояния — окружение
подменяется пустым, а `cwd` для резолвинга указывает на `journalDir`, поэтому проектный кандидат
`load.ts` тоже остаётся внутри операторского каталога. Агент-контролируемые источники здесь
**нейтрализованы**, а не просто понижены в приоритете: понижение приоритета оставляет их
работающими там, где старших кандидатов нет.

### Что становится кодом

- `src/policy/source.ts` — `resolvePolicySource({entryPoint, journalDir, env, cwd, explicitPath})`
  возвращает класс доверия входа, упорядоченный список кандидатов, перечень проигнорированных
  агент-контролируемых источников и, для `connect` с `--policy`, отказ. Один модуль — одно место,
  где правило записано.
- **Один набор сообщений на stderr**: ровно одна строка-объяснение на каждый проигнорированный
  источник, и только если этот источник реально существует (заметка на каждом прогоне научила бы
  оператора её пропускать). `--policy` у `connect` остаётся распознаваемым флагом именно для того,
  чтобы отказ мог объясниться, а не схлопнуться в usage-текст.
- `policy show --entry-point connect|serve|wrap|ui` печатает **тот самый** источник, который
  реально загрузит указанный вход, с его классом доверия. Проверяемость правила из CLI — часть
  решения, а не удобство: без неё правило снова станет комментарием.
- Гейт правки: наблюдаемое поведение всех существующих входов не меняется — тесты
  `connect-policy`, `serve-cmd`, `wrap-cmd`, `policy/load` проходят **без изменения ожиданий**.

### Следствие для UI, которое нельзя пропустить

Панель «эффективная политика и её источник» в UI обязана показывать источник **для класса входа**,
а не «свой собственный». Иначе оператор увидит политику, которую загрузил бы `ui`
(`operator-launched`, четыре источника), и решит, что именно она принуждается в его
`connect`-сессии (`agent-launched`, каталог состояния). Панель показывает обе строки явно; UI
политику не редактирует — `policy.json` остаётся единственным hand-edited файлом (решение M3).

> **Поправка 2026-08-25 (ADR-0009).** Последняя фраза абзаца выше **заменена** решением
> [ADR-0009](0009-policy-editing-and-hot-reload.md): по запросу владельца UI (карточка сервера на
> `/servers`) и CLI (`policy set`) редактируют per-tool правила, а работающие прокси перечитывают
> политику без перезапуска. Пишется **только** `<journalDir>/policy.json` — тот единственный
> источник, который читает `connect`; `--policy`, `$MCP_JOURNAL_POLICY` и проектный файл остаются
> только для чтения и **показываются** панелью источников (обещание этого раздела закрывается тем
> же заходом). Порядок резолва и таблица «вход × класс доверия» не меняются. Текст выше оставлен
> как есть намеренно: ADR фиксирует решение на момент принятия.
>
> **Уточнение 2026-08-26 (ADR-0009, «Поправка 2026-08-26»).** Фраза «пишется только
> `<journalDir>/policy.json`» **заменена**: UI и `policy set` правят тот источник **этого же
> порядка**, который резолвится для их собственного процесса (operator-launched, четыре
> источника), и явно сообщают, кто этот файл читает — в частности, что `connect` читает
> `<journalDir>/.mcp-journal/policy.json` → `<journalDir>/policy.json` и может остаться без
> политики вовсе. Порядок резолва и таблица выше по-прежнему не меняются: поправка касается
> только выбора файла для записи и того, что об этом сказано оператору.

## Что отвергнуто и почему

| Вариант | Почему нет |
|---|---|
| **Унифицировать все входы на четырёхуровневый порядок** (`connect` тоже уважает `--policy`/env/проектный файл) | Прямая дыра: `connect` запускается конфигом агента, поэтому строка `--policy /tmp/allow-all.json` в `.mcp.json` нейтрализует одобрения и карантин — то есть всё, что решает политика. Гранты устояли бы (они в `agents.json`), но принуждение политики исчезло бы целиком. Агентский конфиг — недоверенная точка для подмены политики |
| **Унифицировать все входы на «только каталог состояния»** | Ломает рабочие сценарии оператора: `wrap` с проектной политикой в репозитории и `serve` с `--policy` в systemd-юните — оба легитимны, оба операторские. И сломало бы существующие тесты M2/M3, то есть меняло бы поведение ради симметрии |
| **Слияние источников** (проектная политика «поверх» домашней) | Отвергнуто ещё в M2 и здесь не воскрешается: «откуда взялся этот allow» — вопрос, на который в security-конфиге обязан быть однострочный ответ |
| **Флаг `--trust-cwd` / opt-in доверие агентскому окружению** | Флаг живёт в argv, а argv на `agent-launched`-входе контролирует ровно та сторона, от которой мы защищаемся. Самоотменяющаяся мера |
| **Определять класс доверия эвристикой рантайма** (например, «stdin не TTY ⇒ запущен агентом») | Эвристика на границе принуждения — источник тихих провалов: оператор в CI получает `agent-launched`, агент в псевдотерминале — `operator-launched`. Класс задаётся явно точкой входа |
| **Оставить как есть, дописав абзац в README** | Ровно то состояние, что смок 2026-08-10 признал непонятным: правило в комментарии одного файла не распространяется на новый вход и не проверяется тестом |

## Когда пересматриваем

- **Появится новый вход** — класс доверия обязателен в момент его добавления; вход без класса
  просто не собирается (таблица в `source.ts` исчерпывающая по типу `EntryPoint`). Правка этого
  ADR — часть такой задачи.
- **Партнёр попросит проектные политики для `connect`** (например, «в этом репозитории строже»).
  Ответ по умолчанию — нет: канал остаётся агент-контролируемым. Допустимая форма — операторский
  реестр разрешённых проектных путей в каталоге состояния (плоскость решает, какие проектные файлы
  вообще существуют), и это отдельное решение с отдельным ADR.
- **`connect` перестанет запускаться конфигом агента** (например, появится операторский демон,
  порождающий stdio-сессии) — класс входа меняется вместе с механизмом запуска.
- **M5 добавит провенанс решения** (`policyHash`/`grantsHash` в `DecisionInfo`): тогда «какая
  политика принуждалась» станет фактом записи, а не выводом из этой таблицы. Таблица останется
  правилом выбора, но перестанет быть единственным способом ответить на вопрос постфактум.

## Последствия

- (+) Асимметрия `connect`/`serve` перестаёт быть случайной: она выведена из класса доверия,
  задокументирована и покрыта тестом для каждого входа.
- (+) `policy show --entry-point` даёт оператору прямой ответ вместо чтения исходников — то, чего
  не хватило на смоке 2026-08-10.
- (+) Новый вход (`ui`) получил источник политики по правилу, а не по прецеденту.
- (−) Двухклассовое правило нужно знать: «политика зависит от того, кто запустил процесс» —
  неочевидно, пока не объяснено. Смягчение — заметки в stderr, `policy show --entry-point`,
  раздел в README.
- (−) Один и тот же хост может принуждать разные политики в `connect`- и `serve`-сессиях, если
  оператор держит проектный файл. Это следствие решения, а не дефект; UI показывает обе строки.
- Закрывает бэклог-пункт ROADMAP «Несимметричный источник политики у `connect` и `serve`».

## Связанные решения

- ADR-0004 — Admin UI; `ui` относится к `operator-launched` и показывает эффективную политику,
  не редактируя её.
- Решение M2 «первый найденный источник побеждает, слияния нет» — сохраняется без изменений.
