# ADR-0015: Пул серверов агента за одним адресом — мультиплексор перед односерверными сессиями

- **Статус**: принято (2026-09-20, решения владельца PE1–PE12)
- **Область**: чистое ядро `src/pool/**`; маршрут пула агентского фронта `serve` (фаза 3);
  `connect --url` — stdio-мост к удалённому сервису (фаза 2); генератор конфига клиента (фаза 4).
- **Поправляет**: [ADR-0002](0002-http-dual-version.md) §4 («negotiation сквозная») для адреса пула;
  формулировку инварианта байт-идентичности (`src/proxy/tool-catalog.ts`); пересматривает решение M3
  «адрес на пару агент+сервер, агрегации нет» (строка ROADMAP «Агрегация виртуальных серверов»).
- **Основание**: PRD `.claude/prds/agent-pool-endpoint.prd.md` (2026-09-20), фазы 1–6.

## Контекст

Владелец собирает в сервисе пул MCP-серверов для конкретного агента: регистрирует серверы, выдаёт
гранты лично или через группу. После этого ту же работу приходится повторить второй раз — в конфиге
клиента агента: на каждый выданный сервер своя запись `mcpServers` с тем же токеном и адресом
`/agents/<агент>/servers/<сервер>`, собранным руками. Грант не подключает: выдали ещё один сервер —
конфиг клиента правится снова; отозвали — в конфиге остаётся мёртвая запись. Источником истины о
доступе становится конфиг клиента, а не плоскость, ради которой её ставили.

Решение M3 отвергло агрегацию с прямо записанным условием возврата: «ломает байт-идентичность и
„один исход на id"; **вернуться, если попросят партнёры**» (ROADMAP). Попросил владелец. Основания
пересмотра изменились с тех пор сами:

- байт-идентичность уже условная — прокси пересобирает `tools/list`, `resources/list`,
  `prompts/list`, когда грант что-то скрывает (`src/proxy/tools-filter.ts`,
  `src/agents/method-grants.ts`), и инвариант давно сформулирован как «для потока, который политика
  не тронула»;
- «один исход на id» не требует переписывания клиентских id: у клиента одно пространство id, каждый
  его вызов уходит ровно в один upstream;
- спека сама называет приём: ревизия 2026-07-28, раздел Tools — «Clients or proxies that aggregate
  tools from multiple servers … SHOULD implement a disambiguation strategy such as prefixing tool
  names with a server identifier»; там же `tools/list` «MAY vary by the authorization presented on
  the request», но «MUST NOT vary per-connection» — список пула как функция токена и грантов в это
  укладывается, а порядок слияния обязан быть детерминированным.

## Решения владельца

## Решение

1. **Мультиплексор перед сессиями, а не многосерверная сессия.** Адрес пула — слой, который
   раскладывает трафик одного агента по N **обычным** односерверным сессиям, каждая со своим
   gate'ом, карантином, очередью одобрений и провенансом. Ни `src/session/**`, ни `src/proxy/gate-*`,
   ни `src/policy/**`, ни `src/agents/**` не правятся: всё, что сегодня принуждается на паре
   «агент + сервер», продолжает принуждаться ровно там же и ровно столько же раз. Альтернатива —
   сессия, знающая про N upstream'ов, — потребовала бы переписать каждый из этих инвариантов, и
   именно её отверг M3.

2. **Кодек имён — единственное место префикса.** Префикс `<server>__` ставит плоскость при слиянии
   списков и **снимает** его до того, как кадр уйдёт в дочернюю сессию. Разбор — по первому `__`:
   имя сервера в реестре `[a-z0-9][a-z0-9-]{0,63}` (`src/registry/constants.ts`) не содержит `_`,
   поэтому разбиение однозначно, а враждебный сервер, назвавший свой тулз `other__drop`, получает
   `a__other__drop` и декодируется обратно в **свой** сервер `a`. Следствие, которое и делает п. 1
   возможным: `parseToolCallParams`, `Mcp-Name` (`extractPerMessageHeaders` считается от уже
   переписанных байтов), политика, инвентарь и журнал видят **голое** имя тулза — то же, что в
   посерверном режиме.

3. **Id клиента не переписываются.** Ответ дочерней сессии корреспондируется по id и по серверу:
   ответ с id, который в полёте у другого сервера, **отбрасывается** и журналируется, а не
   подставляется агенту. Собственные запросы плоскости к upstream'ам (fan-out `tools/list`,
   `initialize`) живут в отдельном пространстве id с зарезервированным строковым префиксом, поэтому
   не могут столкнуться с клиентскими и никогда не форвардятся агенту. Переполнение таблицы
   корреляции — отказ по новому запросу (fail-closed), а не вытеснение старого: вытеснение означало
   бы потерянный ответ, то есть нарушенный «ровно один исход на id».

4. **На `initialize` отвечает плоскость (PE12).** Версия — запрошенная клиентом, если она есть в
   `SESSIONFUL_PROTOCOL_VERSIONS`, иначе последняя поддерживаемая; `serverInfo.name = 'mcpcut'`;
   capabilities — `tools.listChanged` и `prompts.listChanged`, и ничего больше (ни `resources`, ни
   `logging`, ни `completions`, ни `instructions`). К каждому upstream плоскость открывает
   **собственный** `initialize` с `capabilities: {}` — это несущая защита PE3: исправный сервер,
   которому не объявили ни sampling, ни elicitation, ни roots, их и не пришлёт; пришедшее всё равно
   отбрасывается с записью. Это и есть поправка к ADR-0002 §4: «форвардит и не подменяет» остаётся
   верным для посерверных адресов и не действует для адреса пула.

5. **Длинные имена (PE2).** Порог «скрыть» — 64 символа: предел OpenAI, и одно невалидное имя у
   части API ломает весь запрос агента, поэтому цена молчаливого скрытия ниже цены отказа. Порог
   «предупредить» — 47: Cursor допускает 60 на «сервер + тулз», а Claude Code добавит сверху свои
   13 символов `mcp__mcpcut__`. Скрытый тулз не исчезает — он остаётся доступным по посерверному
   адресу (PE4), и карточка сервера называет обе величины.

6. **Дубликат имени внутри одного сервера — отказ по серверу.** Сервер, приславший два тулза с
   одинаковым именем, выпадает из списка пула целиком, а не «последним победившим»: выбирать между
   двумя одинаково названными поверхностями плоскость не вправе, а тихий выбор одной из них — ровно
   та подмена, от которой карантин и защищает. Запись, у которой нет читаемого имени, отбрасывается
   со счётом (та же дисциплина, что у `droppedUnreadable` в `agents/method-grants.ts`: allowlist,
   принимающий непроверяемое, — не allowlist).

7. **Порядок слияния детерминирован.** Серверы — по имени (`compareAsText`, никогда
   `localeCompare`), записи внутри сервера — в порядке, в котором их прислал сервер. Это прямое
   требование спеки «`tools/list` MUST NOT vary per-connection»: два соединения одного агента с
   одними грантами обязаны увидеть один и тот же список в одном и том же порядке.

8. **Журнал.** Дочерние сессии пишут ровно то же, что сегодня: `serverName`, голое `toolName`,
   решение, провенанс. Связку «сессия агента ↔ N дочерних сессий» даёт отдельная запись `kind:'pool'`
   (фаза 3). Исходный кадр агента отдельно не хранится (PE11): преобразование детерминировано и
   состоит ровно в том, чтобы приписать или снять `<server>__`, так что запись дочерней сессии
   восстанавливает его однозначно, а поиск по имени тулза работает одинаково в обоих режимах.

9. **Уточнение байт-идентичности.** Инвариант «поток, который политика не тронула, доходит байт в
   байт» действует **в посерверном режиме**. В пуле плоскость меняет по смыслу ровно три вещи: слитые
   `tools/list`/`prompts/list`, поле `params.name` у `tools/call`/`prompts/get` и ответ на
   `initialize`. Всё остальное — аргументы вызова, результаты, уведомления о прогрессе, отмены,
   неизвестные и вендорские поля — сохраняется **пополе**: кадр разбирается, нужное поле заменяется,
   остаток переносится spread'ом, как это уже делает `proxy/tools-filter.ts` для отфильтрованных
   списков.

   Точная формулировка важна, поэтому: у изменённого кадра это **сохранение полей, а не байтов**.
   Кадр проходит `JSON.parse` → `JSON.stringify`, и этот круг теряет то, что теряет JSON в любом
   рантайме: целые за пределами `Number.MAX_SAFE_INTEGER` округляются, `-0` становится `0`,
   неканоническая запись числа нормализуется (`1.50` → `1.5`), дубликат ключа схлопывается в
   последний. Значит `tools/call` с `arguments: { orderId: 9007199254740993 }` уйдёт наверх с
   `...992`, и молча. Механизм ровно тот же, что у посерверной фильтрации списков (она пересобирает
   ответ так же и столько же теряет), то есть пул новой потери не вносит — но **кадры, которые пул
   пересобирает, шире**: там был только `result` списка, здесь ещё и каждый `tools/call`. Если такая
   точность когда-нибудь понадобится, чинится это не здесь, а переписыванием одного поля в байтах,
   без круга через JSON, — и это отдельное решение.

10. **Фазы 2, 4 и 6 (PE8–PE10).** Мост `connect --url` отказывает по открытому `http` до
    не-loopback адреса без явного `--allow-http`, и генератор конфига ставит этот флаг сам, когда
    сервис настроен на `http`, — согласие видно в конфиге, а не спрятано в предупреждении (PE8).
    Генератор подставляет точную версию работающего сервиса, не `@latest`: процесс держит токен
    агента (PE9). Форма `npx`-записи ждёт решения об адресе публичного репозитория; до публикации
    конфиг показывает `"command": "mcpcut"` (PE10).

11. **Размер каталога ограничен, написание имени — нет (ревью безопасности, 2026-09-21).** Слияние
    строит один кадр синхронно, а Node однопоточен, поэтому `tools/list` от одного сервера без
    потолка застопорил бы сессии всех остальных агентов в процессе. Потолки — на один ответ, не
    частотные: 2000 записей на сервер (столько же, сколько держит инвентарь карантина), 64 КиБ на
    запись, 8 МиБ на весь каталог; лишнее **отбрасывается со счётом** по серверу, как нечитаемые
    записи, а не обрывает список молча.

    А вот **имя тулза плоскость не переписывает никогда** — ни в списке, ни на маршруте. Оно и есть
    адрес: поправь его, и `tools/call` уедет не туда или никуда. Поэтому невидимые и bidi-символы в
    имени от сервера доходят до агента как есть, а чистка живёт там, где имя **показывают** (аудит
    H2, `src/ui/display-name.ts`) — из пула этот модуль и недоступен по архитектурному правилу.
    Спуфинг в слитом списке это ограничивает само построение: тулзовую половину имени выбирает
    сервер, а **серверную — оператор при регистрации**, и она ASCII по `REGISTRY_SERVER_NAME_PATTERN`,
    так что подделать в каталоге можно что угодно, кроме того, чьё это. Единственное место, где
    плоскость имя всё же правит, — **текст ошибки** неизвестной цели: он никого не адресует, его
    читает человек, и из него вырезаются и управляющие, и bidi, и нулевой ширины.

    Дубликат имени внутри сервера (§6) сравнивается в NFC: два написания одного имени выглядят
    одинаково, и считать их разными значило бы вернуть ту самую двусмысленность, которую §6 отвергает.
    Предел длины имени на **маршруте** (в отличие от списка, где длинные скрыты порогами §5) сюда не
    входит — это предел размера кадра, и он в фазе 3 вместе с таймаутами.

## Что отвергнуто

- **Запись в конфиг клиента от имени плоскости.** Плоскость показывает готовый блок, но не правит
  чужие файлы: конфиг агента принадлежит тому, кто агента запускает.
- **Многосерверная сессия** (`createSession` с массивом upstream'ов). Отвергнута в M3 и отвергается
  снова: она размножает не код мультиплексора, а инварианты принуждения.
- **Трансляция моделей sessionful↔stateless ради пула.** Остаётся отдельным решением ADR-0002;
  stateless-агент — вторая волна (PE3), а не побочный эффект этой работы.
- **Отдельная сущность «пул» со своим токеном** (PE1). Общий токен на несколько агентов уничтожил бы
  атрибуцию журнала — та же причина, по которой в ADR-0010 нет «ключа группы».
- **`mcp-remote` и подобные сторонние мосты** вместо `connect --url`: прод-зависимостей две
  (ADR-0001), а мост обязан уметь то, чего у чужого нет, — отказ по открытому `http` (PE8) и
  одинаковое поведение на всех трёх развёртываниях.
- **Имя агента в адресе пула** (PE5): агента определяет токен; имя в пути добавило бы второй
  источник истины и ничего не проверяло бы сверх токена.

## Последствия

- Агентский фронт `serve` получает второй маршрут с принципиально другой формой: не «пара
  агент+сервер», а «один агент, N дочерних сессий». Учёт этих сессий в `MAX_CONCURRENT_SESSIONS` и
  их таймауты — часть фазы 3, и без них маршрут не включается.
- Список тулзов пула — функция токена и грантов, значит `list_changed` становится наблюдаемым
  событием: изменение гранта обязано доходить до подключённого агента (фаза 3).
- Цена лени (PE7): первый `tools/list` в пуле из N stdio-серверов поднимает N процессов и ждёт N
  ответов. Сервер, не ответивший вовремя, выпадает из списка (PE6), а не задерживает его.
- Неизвестная цель (`<server>` вне пула или имя без разделителя) отвечает одним и тем же текстом:
  агенту не сообщается, какие серверы существуют за пределами его пула.

## Поправка 2026-09-22 (фаза 3 — маршрут пула во фронте)

Фаза 3 реализована. Шесть решений пришлось принять по ходу; все они уточняют, а не отменяют PE1–PE12.

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| **P1** | POST-конвейер фронта держал **одну** заявку на сессию, вторая → 409 | сессия может объявить корреляцию ответов по id (`OpenedSession.correlate`), и тогда фронт держит N заявок и отдаёт каждой её ответ | §3 описал корреляцию **внутри** мультиплексора и не заметил, что фронт всё ещё спаривает ответы позиционно («ответ — следующее сообщение сессии»). Мост (`src/bridge/pump.ts`) шлёт POST'ы не дожидаясь предыдущего ответа, а `tools/call` с одобрением держит свой на минуты: без корреляции пул из N серверов отвечал бы 409 на всё, кроме первого вызова, то есть параллелизм, ради которого пул и существует, был бы недостижим. Включается **посессионно и опционально** — посерверные адреса свой путь не меняют |
| **P2** | что считать сигналом «каталог изменился» | отпечаток **всей** эффективной матрицы (`grantsHashOf`), не список серверов | видимый каталог фильтруется грантами, значит сужение тулзов внутри сервера меняет его так же, как удаление сервера. Тот же отпечаток уже стоит в провенансе решений — «что изменилось» и «что записано» смотрят на одно |
| **P3** | вотч пула сам поднимает новый сервер? | **нет**: закрывает ушедшие, шлёт `list_changed`, поднимает — следующий `tools/list` | буквальное следование PE7 и одно место, которое открывает дочерние сессии, вместо двух |
| **P4** | зависший upstream на fan-out | сервер **отцепляется** (запись `detach`, причина `fanout-timeout`), список собирается из ответивших | оставить заявку висеть — копить записи корреляции до потолка; отцепить — освободить их и дать честный повод перечитать список |
| **P5** | потолок | дочерние сессии учитываются в `MAX_CONCURRENT_SESSIONS` фронта (`extraSessions`) **и** отдельным `MAX_POOL_CHILD_SESSIONS` на один пул | без первого один агент обходит потолок процесса; без второго один агент с широкими грантами съедает его целиком |
| **P6** | `cursor` в `tools/list` от агента | `-32602` | пул курсоров не выдаёт (страницы upstream'ов дренирует сам), значит курсор в запросе — путаница или подделка |

Сверх плана понадобилось:

- **Плоскость сама здоровается с каждым upstream'ом** (`src/pool/handshake.ts`). Пул отвечает на
  `initialize` агента сам (PE12), поэтому до сервера не доходит ни один клиентский handshake — и
  сервер, следующий спеке, отказал бы на всё дальнейшее. Именно здесь и работает PE3: плоскость
  объявляет `capabilities: {}`, поэтому сервер не инициирует sampling/elicitation/roots. Handshake
  выполняется **до** того, как дочерняя сессия становится маршрутизируемой, — иначе `tools/call`
  успел бы уехать в неинициализированный сервер. Отказ = `attach-refused` с причиной
  `handshake-failed`, то есть PE6.
- **Следствие для существующих серверов:** upstream, отвечающий на `initialize` ревизией
  **2026-07-28** (та, что handshake отменила), в пул не попадает — плоскость не может понять, какая
  дисциплина применима, и открывает пул без него. На посерверном адресе такой сервер работает как
  раньше (там плоскость handshake пересылает, а не ведёт). Все stdio-фикстуры репозитория до фазы 3
  отвечали именно так, поэтому появилась `tests/fixtures/pool-server.mjs`. **Вопрос владельцу
  остаётся открытым:** считать ли это приемлемым (сегодняшнее поведение) или пул должен принимать
  любую названную ревизию.
- **Дочерняя сессия открывается на свежем чтении агента**, а не на записи, с которой открылся пул:
  лень PE7 означает, что между открытием пула и подъёмом сервера проходит время, и за него агенту
  могли выдать именно этот сервер. Устаревшая запись дала бы дочерней сессии матрицу, в которой её
  сервера нет, и её gate отказывал бы во всём до первого опроса собственного вотча. Это же и
  fail-closed направление: отозванный в этом окне грант не должен родить живую дочернюю сессию.
- **Кадры пула отдаются без завершающего `\n`.** Часть синтезаторов (`proxy/synthesize.ts`) общая
  со stdio-прокси и добавляет перевод строки для своего провода; сообщение с ним нельзя оформить в
  кадр для stdio-клиента вовсе — агент за мостом не получал **ничего**. Нормализовано в одном месте
  (`send` мультиплексора), потому что обрамление принадлежит транспорту.
- **Новые коды и словарь:** `-32005` «сервер ушёл из пула», `-32006` «пул держит слишком много
  заявок» (различать обязательно: первый агент может повторить против повторно выданного сервера,
  второй — просто позже), событие журнала `members-changed`, причины дропа `name-too-long`,
  `duplicate-id`, `at-capacity`, `reserved-id`, `handshake-failed`.

Ревью фазы 3 (TS + security) нашли **одну общую первопричину** и она закрыта: `dropServer` звался
только из `onMembershipChanged`, поэтому уход дочерней сессии по любой другой причине (её собственный
конец, таймаут fan-out, неудачная запись) оставлял заявку агента без ответа **и** оставлял в
корреляторе запись, ключёванную **именем сервера**. Второе опаснее первого: следующая дочерняя сессия
того же имени — которая запроса не получала — могла эту запись закрыть чем угодно, то есть сервер,
уронивший соединение после получения чувствительного вызова и переподключившийся, вручал агенту
**сфабрикованный** результат как настоящий. Ровно та подстановка, ради предотвращения которой
`correlator.ts` и существует. Закрыто двумя замками: `releaseServer` на **каждом** уходе (проводится
через событие `detach` самого реестра дочерних, а не через одну ветку) и проверка в `children.ts`, что
кадр пришёл от **текущего экземпляра**, а не от предшественника. Оба замка проверены тестами, которые
краснеют при снятии любого из них.

Там же закрыт HIGH: дочерние сессии обходили резервирование слота фронтом — `extraSessions` читается
только при открытии сессии верхнего уровня, а пул растёт позже, поэтому агент с 32 грантами занимал
33 слота из 64 одним `tools/list`, и 32 из них не проходили никакой проверки. Теперь потолок
спрашивается **перед каждой** дочерней сессией и учитывает открытия в полёте (иначе N параллельных
открытий все проходят потолок, в который влезает одно).

Осознанно **не** закрыто в фазе 3 и записано в ROADMAP: уведомления от дочерних сессий отдаются
агенту без скоупа по серверу — `progressToken` выбирает агент, и проверка его принадлежности требует
второй таблицы соответствия. Ответы скоупятся коррелятором, запросы от сервера дропаются (PE3),
поэтому потолок ущерба — искажение информационного трафика.

Что фаза 3 **не** меняла: ни один модуль принуждения, провенанс, форму записи решения, поведение
посерверного адреса (его тесты прошли без единой правки) и ограничение «одна заявка» у посерверных
сессий.

Фаза 4 реализована: `agent create` во всех трёх поверхностях показывает рядом с токеном готовый блок

| # | Вопрос | Решение | Почему |

Закреплено тестами, а не только словами:

- **`--allow-http` в блоке ≡ отказ моста без него.** `needsAllowHttp` **вызывает** `checkBridgeScheme`,
  а тест-паритет идёт по таблице адресов, включая `http://127.evil.com:8090` (CRITICAL фазы 2): если
  правка `isLoopbackHost` сдвинет одно, сдвинется и другое.
- **Блок одинаков байт-в-байт** в CLI и на веб-странице при одном адресе и токене (оба теста
  сравнивают с выводом генератора).
- **Токен — только там, где ему место:** stdout `agent create` (две строки — `token:` и `env`), ответ
  веба на create (ровно один HTTP-ответ транскрипта), нигде в stderr, журнале, `/agents` и втором ответе.
- **Маска токена в «эквивалентной команде» консоли не нужна**: токен рождается в stdout, а не в argv
  (`display ≡ argv`, в argv нет `mcpj_`) — тест держит, что так и останется.
- **Адрес в удалённой консоли — серверный**: команда исполняется демоном `ui` хоста, и блок называет,
  куда звонить агенту, а не откуда подключён администратор (сквозной тест консольного API).

Форма запуска — `"command": "mcpcut"` (PE10) через одну константу `CLIENT_CONFIG_LAUNCHER`; npx-форма
с точной версией (PE9) реализована и протестирована, фаза 6 переключит константу.

**Верификация закрытий фазы 3** (снятием замков): `releaseServer` на каждом `detach` и проверка
текущего экземпляра в `children.ts` **не были закреплены тестами по отдельности** — модульные тесты
мультиплексора повторяют проводку `detach → releaseServer` в своём харнессе, а тест «поздний кадр
предшественника» держался и первым замком. Добавлены два теста, краснеющих без своего замка:
«сервер умирает посреди вызова» через настоящий фронт и «предшественник не отвечает на вызов,
живой у преемника». Резерв слота ребёнка с учётом открытий в полёте был закреплён.

**Что показал смок** (`docs/smoke-agent-pool.md`):

- Все четыре клиента говорят **sessionful**; SDK v2 в режиме `auto` пробует stateless, получает
  `pool-sessionful-only` и сам откатывается к `initialize` (`2025-11-25`).
- Реальные серверы (`server-everything` stdio и HTTP, `-memory`, `-sequential-thinking` 2026.8.31)
  отвечают на рукопожатие плоскости `2025-11-25` — `2026-07-28`-only среди них нет.
- `list_changed` доходит до клиента за 1.8–1.9 с после записи гранта/группы; блок не менялся.
- TLS-прокси (Caddy) и долгий вызов под `require-approval` (одобрение на 43-й секунде) — работают.
- **Находка владельцу (Ф2):** пул поднимает детей параллельно, и 10-секундный бюджет считается от
  запуска процесса; несколько `npx -y` на 2 CPU не укладываются, и такие серверы выпадают из первого
  списка. README советует регистрировать бинарь; изменение бюджета или «частичный список +
  `list_changed` при позднем подключении» — решение владельца (ROADMAP).

**Остаточные риски:** `list_changed` членов не ограничены по частоте (член может будить агента
перечитывать список; каждый подключившийся сервер уже шлёт свой при старте); уведомление прогресса
без токена не пересылается вовсе — клиент, не давший токена, прогресса и не ждёт.

## Когда пересматриваем

- **Клиенты массово переходят на stateless (2026-07-28).** Тогда в пуле исчезает `initialize` (п. 4
  теряет предмет), появляются `server/discover` и `subscriptions/listen`, и порядок волн PE3 нужно
  перестроить. Первый сигнал даст смок моста фазы 2 живым клиентом.
- **Ресурсы понадобятся в пуле.** У URI нет места для префикса, который не менял бы его смысл, —
  это отдельное решение, а не дополнение п. 2.
- **Жалобы на число тулзов в пуле** (у клиентов есть и предел количества, не только длины). Тогда
  пул нужен с фильтром по серверу на стороне агента, а не только с порогами длины.
- **Понадобится отличать пул в журнале тоньше, чем связкой сессий** — тогда правится провенанс
  (ADR-0007), а не это решение.
