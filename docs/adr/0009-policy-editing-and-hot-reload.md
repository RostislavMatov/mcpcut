# ADR-0009: Политика редактируется из UI и CLI — файл остаётся файлом; горячая перезагрузка правил

- **Статус**: принято (2026-08-25, заход «правила тулзов из карточки сервера», волна 0); **поправка
  2026-08-26** — цель записи = файл, который загрузил сам вход (см. блок «Поправка 2026-08-26»
  в §1 и правку строки таблицы отвергнутого)
- **Область** (целевая — кода правки и reload на момент принятия нет): новые модули
  `src/policy/edit/**` (чистая правка + запись файла), `src/policy/reload.ts` (провайдер политики
  с горячей перезагрузкой), `src/policy/effective.ts` (эффективный исход + источник),
  `src/journal/policy-edit-record.ts` (новая категория записей `policy-edit`); потребители
  политики в прокси — `src/proxy/wire-policy.ts`, `gate-decide-input.ts`, `gate-core.ts`,
  `gate-decision-writer.ts`, `tool-catalog.ts`; точки загрузки `src/cli/connect-policy.ts`,
  `wrap-cmd.ts`, `serve-cmd.ts`; `src/ui/authz.ts` (новая строка таблицы маршрутов),
  `src/ui/pages/servers*.ts`, `src/cli/ui-wiring.ts`, `src/cli/policy-cmd.ts` (`policy set`).
  Схема политики (`src/policy/schema.ts`) и порядок резолва источников (`src/policy/source.ts`,
  ADR-0005) **не меняются**.
- **Основание**: `.claude/plans/policy-tool-rules-ui.plan.md` — запрос владельца 2026-08-25
  («в карточке сервера нужна возможность включения/выключения тулза и кнопка добавления тулза в
  список на подтверждение») и блок «Решения владельца (нормативны, 2026-08-25)» — решения
  **O1–O6**. Этот ADR **оформляет** принятые решения и не пересматривает их. Он снимает границу
  M3 «`policy.json` — единственный hand-edited файл», на которую ссылаются ADR-0005 (раздел
  «Следствие для UI»), план M4 (`admin-ui-approvals.plan.md`, таблица «Границы») и PRD хранилища
  (`storage-architecture-sqlite.prd.md`, «Won't»); во все три внесены поправки-ссылки.

## Контекст

С M3 действовало правило: **`policy.json` — единственный файл плоскости, который правит человек
руками**. Всё остальное состояние — реестр, вольт, матрица грантов, инвентарь, очередь — меняется
только через CLI (а с M4 — и через UI), потому что опечатка в любом из них есть проблема
безопасности, а не синтаксиса. Политике сделали исключение по трём причинам: (1) она — граница
безопасности, и ручная правка с диффом в редакторе была самым честным «экраном подтверждения»
из доступных; (2) в M2–M3 не существовало ни одной поверхности, с которой её можно было бы
править атрибутируемо; (3) ADR-0004 отверг кастомные роли админов как «второй язык политик рядом
с `policy.json`» — и тем самым закрепил, что язык политик один и живёт в одном файле.

Правило переехало в три документа, где стало **границей**: ADR-0005 («UI политику не редактирует»),
план M4 («Политика как объект редактирования в UI — не делаем»), PRD хранилища M4.5 («замена
`policy.json` — Won't; редактирование через БД/UI — отдельный продуктовый вопрос»). Обещанная
ADR-0005 панель «эффективная политика и её источник» при этом так и не была построена:
процесс `ui` политику не читает вовсе.

2026-08-25 владелец попросил per-tool контролы в карточке сервера на `/servers`: выключить тулз,
включить, поставить на подтверждение. Это ровно правка политики — `servers.<name>.tools[<tool>]`
(`src/policy/schema.ts`). Ответить «правьте файл руками» значило бы оставить оператора с текстовым
редактором ровно там, где он смотрит на список тулзов; ответить «правим, но до перезапуска» —
оставить работающих `connect`-агентов на старой политике на неопределённое время, причём
неотличимо для оператора. Владелец выбрал полноценное редактирование с горячей перезагрузкой (O1).

Существенно, что **модель уже есть** и не меняется: три исхода `allow` / `deny` /
`require-approval`, ключ — точное имя или один trailing `*`, точный ключ побеждает prefix
(`src/policy/match.ts`); `deny` уже прячет тулз из `tools/list` через фильтр каталога;
`decide()` уже называет источник каждого решения (`PolicyDecision.rule`). Заход добавляет **путь
записи** и **путь перечитывания** — не второй язык и не вторую интерпретацию.

## Решение

### Решения владельца (нормативны, 2026-08-25)

> - **O1 — граница снята**: политика редактируется из UI полноценно, с hot reload (не «до
>   перезапуска»). Показ эффективной политики — обязательная часть.
> - **O2 — семантика правила**: три состояния (`allow` / `require-approval` / `deny`) + сброс
>   явного правила.
> - **O3 — сбой reload**: прокси держит последнюю валидную политику, пишет громкую диагностику в
>   stderr и запись в журнал; UI показывает баннер «файл на диске невалиден, действует версия
>   `<hash>`». UI невалидный файл записать не может (валидация до записи).
> - **O4 — политики нет (режим «только журнал»)**: контролы неактивны с подсказкой «политики нет —
>   enforcement выключен»; создание `policy.json` из UI — отдельное явное действие, **не в этом
>   заходе**.
> - **O5 — журнал правок**: запись `kind: 'policy-edit'` + строка аудита в stderr.
> - **O6 — CLI-паритет**: `policy set` в этом заходе.
> - Роль для записи правил: **owner** (политика — граница безопасности; уровень
>   `servers/add|edit|remove`). Не спрашивалось — следует из ADR-0004.

### 1. Файл остаётся файлом; пишется ровно один путь — `<journalDir>/policy.json`

`policy.json` остаётся источником истины и остаётся hand-editable: UI и CLI — ещё два писателя
того же файла, а не замена ему. Хранилище политики в `state.db` **не** заводится (см. отвергнутое).

Записывается **только** `<journalDir>/policy.json` — тот источник, который читает
`agent-launched`-вход `connect` (ADR-0005), и последний кандидат для `operator-launched`-входов
(`wrap`/`serve`). Путь фиксирован композицией процесса (`join(journalDir, POLICY_FILE_NAME)`) и
**никогда не выводится из запроса**. Проектный файл, `--policy` и `$MCP_JOURNAL_POLICY` остаются
только для чтения: если для операторского входа первым резолвится другой файл, UI **показывает** это
явно (панель источников — долг ADR-0005, закрывается этим заходом: «`serve`/`wrap` load `<путь>`
first — edits here affect `connect` only»), но не пишет туда.

Редактируется только **точное** per-tool правило: `setToolRule(policy, server, tool, rule | null)`
возвращает новую политику (иммутабельно), `null` удаляет точный ключ (O2 — «сброс»). Точный ключ
перекрывает любой wildcard, поэтому кнопка в карточке всегда побеждает `foo*`, а сброс возвращает
исход к тому, что дают wildcard/дефолты. `defaultDecision`, `classDefaults`, wildcard-правила,
кванты approval/journal — по-прежнему ручная правка файла; UI их показывает как источник исхода.

> **Поправка 2026-08-26 (решение владельца).** Правило «пишется ровно один путь —
> `<journalDir>/policy.json`» **заменено**: **UI и `policy set` правят тот файл, который
> загрузил сам вход**, и карточка явно говорит, на кого этот файл действует.
>
> **Почему прежнее правило было неверным.** Владелец нашёл это на своей живой установке:
> `<journalDir>/policy.json` там **не существует**, а плоскость принуждает
> `<repo>/.mcp-journal/policy.json` — проектный файл, который реально загружают `ui`, `wrap` и
> `serve` (все три — operator-launched, четырёхисточниковый порядок ADR-0005). Цель записи была
> жёстко привязана к `<journalDir>/policy.json`, и из того же пути вычислялось «есть ли
> политика». Итог: карточка сообщала «политики нет — enforcement выключен» и держала все контролы
> неактивными, **пока политика принуждалась**. Это не ошибка настройки, а дефект дизайна: файл,
> который показывают, обязан быть тем же файлом, который правят, и тем же, который загрузил этот
> процесс.
>
> **Новое правило цели.** Цель = путь, который для ЭТОГО процесса дают
> `resolvePolicySource({entryPoint:'ui', journalDir, env, cwd})` + `loadPolicy` — первый
> резолвящийся кандидат операторского порядка (явный `--policy`/`$MCP_JOURNAL_POLICY` считается
> целью и когда файла нет: вход привязан именно к этому пути). Если не найдено ничего, состояние
> остаётся `absent` (O4 в силе: контролы неактивны, файл **не** создаётся), а показываемый
> «будущий» путь — `<journalDir>/policy.json`. Путь по-прежнему **фиксируется композицией
> процесса**: `env`/`cwd` берутся из операторской оболочки (тот же класс доверия, что ADR-0005 даёт
> `ui`/`wrap`/`serve`), ни одно поле запроса пути не касается — пункт 2 модели угроз в силе.
>
> **Читатели — вычисляются и показываются, не угадываются.** У резолвнутой цели считается, кто её
> читает: `connect` (agent-launched) читает только `<journalDir>/.mcp-journal/policy.json`, затем
> `<journalDir>/policy.json`; операторские входы — четырёхисточниковый порядок. Три формулировки
> (`describePolicyReaders`, одна на UI и CLI): (a) цель совпадает с файлом `connect` — «every entry
> point reads this file»; (b) цель — проектный/env/явный файл — «ui/wrap/serve read this file;
> connect sessions read `<путь>`», а когда у `connect` файла нет вовсе — «…connect sessions have no
> policy right now (journaling only) — rules here do not reach them»; (c) цель —
> `<journalDir>/policy.json`, а вложенный кандидат существует — «connect reads `<путь>` first —
> rules here reach ui/wrap/serve only».
>
> **Отказ `shadowed` снят.** Прежний отказ (находка 5a плана) блокировал правку ровно там, где она
> уместна: правка всегда доходит до входов, которые загрузили этот файл. То, что было отказом,
> стало **утверждением** на карточке и в выводе `policy set`. Отказы остаются только там, где
> запись нельзя атрибутировать или проверить: политики нет (O4), файл на диске не парсится (O3),
> конфликт CAS, невалидные имена, сбой записи.
>
> **Что этим заменено внутри ADR**: заголовок и текст §1 выше (в части «ровно один путь»), строка
> таблицы отвергнутого «Писать в проектный файл / `--policy` / `$MCP_JOURNAL_POLICY`» (её довод
> «писать туда, куда указала недоверенная сторона» не применим к operator-launched входу, чей
> `cwd`/`env` ADR-0005 признаёт доверенными; агент-контролируемым каналом остаётся только
> `connect`, который сюда не пишет) и обещание §6 CLI печатать «`<journalDir>/policy.json`».
> `sourcePath` в записи `policy-edit` теперь несёт фактический путь правки — вопрос «какой файл
> изменили» отвечается записью, а не выводом из умолчания. Порядок резолва ADR-0005 и таблица
> «вход × класс доверия» **не меняются**.

### 2. Валидация до записи; CAS по `policyHashOf`; атомарная запись

- **«Что нельзя загрузить, нельзя записать».** Результат правки прогоняется через тот же
  `parsePolicy`, что и загрузка; имена — по `serverNameSchema`/`TOOL_RULE_NAME_PATTERN` без `*`;
  лимиты `MAX_TOOL_RULES_PER_SERVER`/`MAX_SERVERS_IN_POLICY` — ошибка, не тихое усечение. UI и CLI
  физически не способны оставить на диске файл, который прокси не загрузит (O3, вторая половина).
- **CAS по каноническому hash.** `policyHashOf` (`src/policy/provenance.ts`, M5) — hash
  эффективного объекта: переформатирование файла его не меняет, любая правка правила — меняет.
  Форма несёт hash, с которым рендерилась; перед записью файл перечитывается и сравнивается;
  расхождение (в том числе «файл исчез», когда ожидался загруженный) — конфликт: HTTP `409`,
  «политика изменилась на диске — обновите страницу». Так проигрывает, а не молча затирает,
  ручная правка в редакторе, соревнующаяся с кликом.
- **Атомарность.** Сериализация (2 пробела, `\n` в конце) → временный файл в том же каталоге →
  `rename`. Читатель никогда не видит половину файла; внутри процесса записи сериализуются
  очередью, между процессами — CAS.
- Каждая запись возвращает `{hashBefore, hashAfter}` — это и содержимое журнальной записи, и то,
  что печатает `policy set`.

### 3. Горячая перезагрузка: `stat` с кулдауном перед решением, не `fs.watch`

Три потребителя политики в прокси — `decide` в гейте, фильтр каталога `tools/list`, писатель
провенанса решения — получают вместо значения **провайдер** `current(): Policy`. `current()`
синхронный (гейт — синхронный код на горячем пути). Перед решением провайдер не чаще
`POLICY_RECHECK_MIN_MS` (250 мс) делает `stat` файла; изменились `mtime`/`size` — перечитывает и
парсит; валидно — подменяет и сообщает `onReload({hashBefore, hashAfter})`.

`policyHash` в провенансе решения (M5) считается **на каждое решение** из текущей политики — в
коде M5 он считался один раз при создании писателя, и это ровно та точка, где hash «протух бы»
после reload. Запись решения обязана нести hash той политики, которая его приняла.

**Что перезагружается**: всё, что читают `decide()` и каталог — `servers.*`, `classDefaults`,
`defaultDecision`, `toolsList.filter`, `quarantine.onQuarantined`.

**Что НЕ перезагружается** (находка 4 плана): конфигурация, зашитая при wiring —
`approval.timeoutMs`, `grantTtlMs`, `journal.failClosed`, `quarantine.enabled`. Очередь, вейтер и
инвентарь создаются с этими значениями, и подменять их на лету значило бы пересобирать
работающие объекты под живыми сессиями. Эти поля — до перезапуска; частичность reload **явно**
названа здесь, в `policy show` («hot reload: rules yes · wiring config no») и в README. Скрытая
частичность была бы хуже отсутствия reload.

Ручная правка файла подхватывается тем же механизмом, что и правка из UI: провайдеру всё равно,
кто изменил файл.

### 4. Сбой reload: последняя валидная остаётся, диагностика громкая (O3)

Невалидный, нечитаемый или **исчезнувший** файл → прокси продолжает работать на последней
валидной политике; `onError` — один раз на версию файла (не на каждый вызов), с диагностикой в
stderr через `guardDiagnostics` и записью в журнал по пути прочей диагностики. UI показывает
баннер «файл на диске невалиден, действует версия `<hash>`» и блокирует кнопки.

Исчезновение файла — тоже ошибка версии, а не переход в «journaling-only»: выключить enforcement
удалением файла у работающего прокси — не режим, который поддерживается молча. Ошибка reload
**никогда не ослабляет** принуждение: ни allow-all, ни «политики нет». Отвергнут и обратный ход —
fail-closed deny-all (см. таблицу): он превращал бы опечатку в редакторе в отказ всем агентам
сразу, тогда как последняя валидная политика — это ровно та, которую оператор уже одобрил.

### 5. Каждая правка атрибутирована: `kind: 'policy-edit'` в доказательном журнале (O5)

`{kind:'policy-edit', actor:{adminName, role, via:'ui'|'cli'}, serverName, toolName, rule |
null, policyHashBefore, policyHashAfter, sourcePath}`, `sessionId` — зарезервированный
`plane_policy` (по образцу `plane_probe`, ADR-0008). Запись связывает hash-до и hash-после с
именем админа: в связке с `policyHash` в каждом решении (M5) это даёт ответ «какая политика
действовала и кто её сделал такой» из самого журнала, без внешнего git-лога.

Запись идёт **существующим** путём — тот же батч-писатель, то же звено хеш-цепочки, та же
подписанная глава (ADR-0007); второй писатель в `journal.db` из процесса `ui`/CLI уже легален
(пробы). Reload сам по себе **не** журналируется как действие — это не действие субъекта;
факт правки уже записан тем, кто правил, а провенанс решения несёт актуальный hash. Записи
`policy-edit` обязаны быть отделимы от агентского трафика в поиске UI-журнала и в экспорте
отчёта — тот же инвариант, что у проб. Как и для `probe` (урок M5.5): на каждый потребитель
журнала (verify, `export --report`, `verify --report`, summary, search, UI-журнал) тест пишется
**до** введения kind.

Плюс строка аудита в stderr процесса `ui`/CLI — как у прочих изменений сторов из UI (ADR-0004).

### 6. Права: запись правил — `owner`; чтение — как у `/servers`

| Маршрут | Минимальная роль |
|---|---|
| `POST /servers/:name/tools/:tool/rule` | `owner` |

Политика — граница безопасности; правка правила равна по последствиям регистрации сервера
(`POST /servers/{add,edit,remove}` — `owner`). Матричный тест authz сам потребует строку. Показ
эффективного исхода и источника — на `GET /servers`, роль не меняется (`viewer`).

**CLI-паритет обязателен** (O6, урок поправки ADR-0004 от 2026-08-18): `policy set <server>
<tool> allow|deny|require-approval|clear` под `MCP_ADMIN_TOKEN` с ролью `owner` — иначе таблица
маршрутов обходится через терминал. Тот же `setToolRule` + та же запись файла + та же запись
журнала (`via:'cli'`); печатает `hash-до → hash-после` и эффективный исход после правки.

### 7. Эффективный исход показывается через `decide()`, не через вторую интерпретацию

Карточка показывает у каждого тулза исход и его источник (`explicit` / `wildcard` /
`server-default` / `class-default` / `global-default` / `quarantine` / `surface-changed`).
Источник — тонкая обёртка над `decide()` (`src/policy/effective.ts`), разбирающая
`PolicyDecision.rule`; никакой параллельной логики матчинга в UI. Иначе UI рано или поздно показал
бы не то, что принуждает гейт.

Режим «только журнал» (O4): политики нет — кнопки неактивны с подсказкой «no policy — enforcement
off». Создание файла из UI — отдельное явное действие, не в этом заходе.

## Модель угроз — запись файла политики из HTTP-обработчика

**Было**: единственный писатель `policy.json` — человек с правами на файл, через редактор; UI
читал состояние и менял сторы, но не политику.
**Стало**: HTTP-обработчик процесса `ui` (и CLI под админ-токеном) **пишет файл, который
определяет принуждение** для всех прокси на хосте — и они подхватывают его без перезапуска.

Что это открывает и чем закрыто:

1. **Подмена политики через браузер (CSRF/confused deputy).** Владелец правила — `owner`;
   маршрут — POST со всеми мерами ADR-0004: `__Host-`-cookie, CSRF-токен, проверка `Origin`.
   Вкладка чужого сайта не может ни прочитать hash, ни собрать валидный POST.
2. **Path traversal / запись не туда.** Путь файла зафиксирован при композиции процесса и не
   зависит ни от одного поля запроса; из запроса берутся только `server`, `tool`, `rule`,
   `expected_hash` — и все проходят строгие паттерны схемы (`serverNameSchema`,
   `TOOL_RULE_NAME_PATTERN` без `*`, перечисление исходов). Имя тулза с `/`, `..`, `*` или
   управляющими символами отвергается на входе, а не «экранируется».
3. **Порча файла, ломающая всех агентов.** Валидация до записи (`parsePolicy`) + атомарный
   `rename`: на диске никогда не оказывается ни невалидная политика, ни половина файла.
4. **Гонка с ручной правкой.** CAS по `policyHashOf`: клик, сделанный по устаревшей странице,
   не затирает то, что оператор только что вписал в редакторе; проигравший видит `409`.
5. **Ослабление принуждения через сбой reload.** Битый/исчезнувший файл — последняя валидная
   политика + громкая диагностика; ни при каком исходе reload прокси не переходит в allow-all и
   не теряет enforcement. «Испортить файл, чтобы всё разрешилось» — не работает.
6. **Бесследная правка.** Каждая запись — `policy-edit` в подписанной цепочке с именем админа и
   парой hash; провенанс каждого решения несёт hash действовавшей политики. Правка, сделанная
   в обход (редактором), видна как reload без записи `policy-edit` — то есть как ручная правка,
   которой она и является.
7. **Reload на горячем пути как DoS.** `stat` не чаще 250 мс, `current()` синхронный, парсинг —
   только при изменении `mtime`/`size`; бенч волны 2 — p95 решения не хуже базовой линии.

**Граница доверия uid не меняется** (ADR-0003, ADR-0004): процесс под тем же uid и без UI может
переписать `policy.json`; hot reload делает такую подмену **быстрее** ощутимой прокси (раньше —
до перезапуска), но не даёт нового канала атакующему, уже получившему uid. Это разговор о том, что
делает сама плоскость по действию админа, а не о новой поверхности за границей.

**Что этими мерами НЕ закрыто**: `owner` с валидным токеном может через UI разрешить что угодно —
ровно как раньше мог редактором; журнал делает это видимым, а не невозможным. Между
`rename` и следующим `stat` окно до 250 мс, в котором прокси принимает решение по предыдущей
политике — принятая цена кулдауна, а не дефект; для оператора это неотличимо от того, что клик
пришёлся на 250 мс позже.

## Что отвергнуто и почему

| Вариант | Почему нет |
|---|---|
| **Оставить границу M3** («правьте файл руками», UI только показывает) | Оставляет оператора с редактором ровно там, где он смотрит на список тулзов; атрибуции правки нет вовсе (git-лог файла — вне плоскости). Отвергнуто владельцем (O1) |
| **Редактирование «до перезапуска»** (запись есть, reload нет) | Работающие `connect`-агенты остаются на старой политике на неопределённое время, и оператор этого не видит: кнопка «deny» выглядит сработавшей, а тулз всё ещё вызывается. Хуже, чем честное «правьте руками». Отвергнуто владельцем (O1) |
| **`fs.watch` / `fs.watchFile`** | Непредсказуем между ФС (сетевые диски, macOS/Linux различия, `rename` vs `inotify`-события), держит дескриптор/поток на каждый процесс прокси, даёт всплески событий на одну запись. `stat` перед решением с кулдауном — предсказуем на любой ФС, ноль ресурсов в простое, и проверяется тестом с инжектируемым `stat` |
| ~~**Писать в проектный файл / `--policy` / `$MCP_JOURNAL_POLICY`**~~ — **отменено поправкой 2026-08-26** | Довод был: «писать туда, куда указала недоверенная сторона». Он неверен для operator-launched входа: его `cwd`/`env` ADR-0005 признаёт доверенными ровно настолько, насколько сам запуск; агент-контролируемый канал — только `connect`, а он не пишет вовсе. Живая установка владельца показала цену ошибки: правился бы файл, который не читает никто. Теперь правится тот файл, который загрузил сам вход, и карточка называет его читателей |
| **Автосоздание `policy.json` при первом клике**, когда его нет | Клик по одному тулзу включал бы enforcement для **всех** серверов и агентов хоста с дефолтами, которых оператор не видел — переход из режима A в режим B не может быть побочным эффектом. Создание файла — отдельное явное действие (O4), следующий заход |
| **Fail-closed deny-all при битом reload** | Опечатка в редакторе → отказ всем агентам сразу, включая тех, у кого был `allow`; последняя валидная политика — та, которую оператор уже одобрил, и держать её при громкой диагностике безопаснее и честнее. Fail-closed остаётся там, где он есть — журнал (`journal.failClosed`) и старт без валидной политики (`load.ts`: явно названный файл обязан загрузиться). Отвергнуто владельцем (O3) |
| **Второе хранилище политики в `state.db`** (таблица правил, файл — экспорт) | Второй язык политик рядом с `policy.json` — ровно то, за что ADR-0004 отверг кастомные роли админов. Два источника истины о принуждении = вопрос «откуда взялся этот allow» без однострочного ответа (решение M2 о слиянии). Файл остаётся файлом, UI — ещё один его писатель |
| **Слить reload с записью** (UI пушит новую политику прокси по IPC) | Требует канала `ui` ↔ каждый прокси; `connect`-процессы запускаются агентом и не знают о `ui`. Файл + `stat` покрывают и UI, и CLI, и редактор одним механизмом |
| **Журналировать каждый reload как действие** | Reload — не действие субъекта: у него нет актора. Факт правки уже записан тем, кто правил; провенанс каждого решения несёт актуальный `policyHash`. В журнал идёт только **ошибка** reload |
| **Правило из UI для wildcard / defaults / классов** | Запрос — per-tool; редактор для остальных полей — отдельная поверхность с отдельной моделью ошибок. UI показывает эти источники, правятся они файлом |
| **Роль `operator` для записи правил** | Политика — граница безопасности того же уровня, что регистрация сервера (`owner`); `operator` решает в рамках политики (одобрения, карантин), а не меняет её |

## Последствия

- (+) Оператор ставит `allow`/`deny`/`require-approval` там, где видит тулз; работающие агенты
  подхватывают правило без перезапуска, включая `tools/list` (deny прячет тулз).
- (+) Впервые появляется атрибуция правок политики в доказательной цепочке: пара hash + имя
  админа; вместе с `policyHash` в решениях журнал отвечает «какая политика действовала и кто её
  такой сделал».
- (+) Панель источников политики — долг ADR-0005 — наконец построена.
- (+) Файл остаётся источником истины и остаётся hand-editable; ручная правка подхватывается тем
  же механизмом, что и правка из UI; ни второго стора, ни второго языка.
- (−) **HTTP-обработчик пишет файл, определяющий принуждение** — главная цена; закрыта
  owner-only, CSRF/Origin, фиксированным путём, строгими паттернами, валидацией до записи, CAS,
  атомарностью и обязательным security-ревью волны 4.
- (−) Reload частичный: таймауты, TTL грантов, `journal.failClosed`, `quarantine.enabled` — до
  перезапуска. Частичность названа в трёх местах (ADR, `policy show`, README), но её нужно знать.
- (−) На горячем пути гейта появляется `stat` (не чаще 250 мс) и вычисление `policyHashOf` на
  каждое решение вместо одного раза — бенч обязателен.
- (−) Окно до 250 мс между записью и подхватом — решение в этом окне идёт по предыдущей политике.
- (−) Журнал получает ещё одну служебную категорию записей (`policy-edit`); отделимость от
  агентского трафика — обязательство, а не удобство.

**Требования к тестам** (нормативная часть, без них решение остаётся прозой):

1. Парити записи: файл, записанный `writePolicyFile`, загружается `loadPolicy` и даёт тот же
   `policyHashOf`, что объект до сериализации.
2. Невалидную политику записать невозможно (лимиты, `*` в имени, неизвестный исход, чужой
   `expected_hash`) — на диске остаётся прежний файл байт-в-байт.
3. CAS: два писателя с одним `expectedHash` — ровно один побеждает, второй получает конфликт.
4. Живой `connect`: правка файла на лету меняет исход **следующего** вызова и содержимое
   следующего `tools/list` без перезапуска; `policyHash` в записи решения равен hash новой
   политики.
5. Битый / исчезнувший файл: прокси продолжает на последней валидной политике, исход не меняется,
   диагностика — ровно одна на версию файла.
6. Матричный тест authz покрывает `POST /servers/:name/tools/:tool/rule` (`owner`); `policy set`
   требует ту же роль через `MCP_ADMIN_TOKEN`.
7. Записи `policy-edit` проходят verify цепочки, `export --report`/`verify --report`, попадают в
   поиск и UI-журнал и отделимы от агентского трафика — тесты написаны до введения kind.
8. Путь записи не зависит от запроса: любой `server`/`tool` вне паттерна отвергается до обращения к
   файловой системе.

## Когда пересматриваем

- **Партнёр попросит править `defaultDecision`/`classDefaults`/wildcard из UI** — это полный
  редактор политики с собственной моделью подтверждения (дифф до записи, как у карантина); отдельный
  заход и правка этого ADR, не тихое расширение обработчика.
- **Создание `policy.json` из UI** (переход из режима A в режим B) — отдельное явное действие
  (O4), с ответом на вопрос «с какими дефолтами и что увидит оператор до включения».
- **Появится необходимость перезагружать wiring-конфиг** (таймауты, TTL, `failClosed`,
  `quarantine.enabled`) — это пересборка живых объектов под сессиями; решается отдельно, с
  ответом «что происходит с заявками в очереди в момент смены таймаута».
- **`stat`-кулдаун окажется узким местом** (бенч волны 2 или пилот): рассматривать
  `fs.watch` как **дополнение** к `stat`, не замену — с тем же fallback.
- **Правил для `resources/*`/`prompts/*`** (бэклог M5): модель матчинга расширяется — вместе с
  ней и `setToolRule`.
- **Не-localhost развёртывание**: HTTP-запись файла принуждения через сеть — пересмотр вместе с
  моделью угроз ADR-0004.
- **Групповые операции** («deny все тулзы сервера») — сегодня это `defaultDecision` сервера в
  файле; если пилот покажет спрос, это правка этого ADR (массовое действие в UI — тот же вопрос
  fatigue, что и batch-approve в плане M4).

## Связанные решения

- **ADR-0005** — источник политики по классу доверия входа. Порядок резолва **не меняется**;
  этот ADR снимает фразу «UI политику не редактирует — `policy.json` остаётся единственным
  hand-edited файлом» и закрывает долг панели источников. С поправки 2026-08-26 правится тот
  источник операторского порядка, который резолвится для процесса правки, и показывается, кто
  его читает (`connect` — отдельной строкой). В ADR-0005 внесена поправка-ссылка.
- **ADR-0004** — Admin UI: новая строка таблицы «маршрут × минимальная роль» (`owner`), те же
  CSRF/Origin/`__Host-`-cookie на POST, тот же принцип атрибуции `actor` + `adminName`. Отказ от
  «второго языка политик» (кастомные роли) применён здесь к второму хранилищу политики.
- **ADR-0007** — доказательный журнал: `policy-edit` идёт существующим путём записи (звено цепочки,
  подписанная глава), обязана быть отделима в отчёте; `policyHash` провенанса решения теперь
  считается на каждое решение. Журнал остаётся «tamper-evident **with an external anchor**».
- **ADR-0008** — образец служебной категории записей (`probe`, `sessionId` `plane_probe`) и второго
  писателя `journal.db` из процесса `ui`; урок «тесты на потребителей журнала до введения kind».
- **ADR-0006** — хранилище: политика в `state.db` **не** переезжает — подтверждение решения
  M4.5 «`policy.json` не переезжает», теперь с новым обоснованием.
- **ADR-0003** — граница доверия «учётная запись ОС»: hot reload не сдвигает её.
- **ADR-0001** — граница зависимостей: ни запись, ни reload не добавляют прод-зависимостей
  (`node:fs`, `zod` для валидации).
- **План** `.claude/plans/policy-tool-rules-ui.plan.md` — решения владельца **O1–O6**
  (2026-08-25), находки из кода 1–10, волны 0–6; поправки-ссылки: план M4
  `.claude/plans/admin-ui-approvals.plan.md` (таблица «Границы»), PRD хранилища
  `.claude/prds/storage-architecture-sqlite.prd.md` («Won't»), `README.md` (таблица файлов
  состояния и раздел «Policies»).
