# Architecture Decision Records

Решения, определяющие форму кода. Каждое ADR отвечает на «почему так, а не иначе» и называет
условия, при которых решение пересматривается. Правка решения — правка его ADR, а не тихое
изменение кода: несколько ADR прямо запрещают отдельные обратные ходы (например,
`Referrer-Policy: no-referrer` в ADR-0004).

## Как пользоваться

- **Перед изменением архитектуры** — найти ADR, который это решение уже описывает, и проверить
  раздел «когда пересматриваем». Если условия пересмотра не наступили, а изменение всё же нужно —
  это новый ADR, а не правка кода.
- **Новый вход, новый маршрут, новая зависимость** — три случая, где ADR обязателен: ADR-0005
  требует класс доверия для каждого нового входа, ADR-0004 — запись в authz-таблице для каждого
  нового маршрута, ADR-0001 — отдельное решение для каждой новой прод-зависимости.
- **Статусы**: `предложено` → `принято` → `устарело` | `заменено ADR-NNNN` (замена всегда со
  ссылкой на заменяющее решение).

## Механическая охрана

Часть инвариантов из ADR проверяется тестами, а не дисциплиной — `tests/architecture/imports.test.ts`:
транспорт не знает JSON-RPC (ADR-0001, ADR-0002), `src/net/**` не тянет ничего кроме платформы,
UI не импортирует `proxy/**`, `transport/**` и путь к значениям вольта, и никто вне UI и трёх
CLI-файлов не импортирует `src/ui/**` (ADR-0004). Матричный тест authz перебирает все маршруты
против всех ролей.
