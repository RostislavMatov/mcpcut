# ADR-0004: Admin UI — отдельный процесс, ноль зависимостей, именные админы с фиксированными ролями

- **Статус**: принято (2026-08-11, Волна 0 M4)
- **Область**: `src/ui/**`, `src/admin/**`, `src/cli/ui-cmd.ts`, `src/cli/admin-cmd.ts`
- **Основание**: `.claude/plans/admin-ui-approvals.plan.md` (§1, §2, §6, «Границы», «Риски»);
  решение 2026-08-11 о пересмотре границы MVP (мультиадминство вошло в MVP)

## Контекст

M4 даёт контрольной плоскости человеческий интерфейс: очередь одобрений в реальном времени,
карантин со структурным диффом `inputSchema`, матрица прав агентов, реестр серверов, имена
секретов вольта, браузер журнала. Гейт milestone — **человек одобряет write-операцию из UI, и
агент получает ответ в пределах своего клиентского таймаута** (`approval.timeoutMs`, 60 с).

Три обстоятельства задают рамку решения:

1. Основной сценарий M3 — `connect` (stdio), запускаемый конфигом агента. В нём `serve` **не
   запущен вообще**. Очередь одобрений уже кросс-процессная (`approvals/pending|resolved` +
   межпроцессный лок `src/lockfile.ts`).
2. Продукт хранит чужие секреты и решает, что агенту можно. Артефакт будут смотреть на аудите:
   каждая транзитивная зависимость — часть этой поверхности (ADR-0001: ровно два прод-пакета).
3. Интерфейс живёт в браузере, а браузер — это confused deputy: любая открытая вкладка умеет
   слать POST на `127.0.0.1:8091`, и этим POST одобряется изменяющая операция агента.

## Решение 1 — UI это отдельный процесс `mcp-journal ui`, не часть `serve`

Новая команда `mcp-journal ui [--port 8091] [--host 127.0.0.1] [--behind-tls]`: собственный
`node:http`-сервер, собственный порт, собственная аутентификация. Всё состояние читается и
пишется через те же файловые сторы (`registry.json`, `agents.json`, `admins.json`, `vault.enc`,
`tool-inventory.json`, `approvals/`, `*.jsonl`) с существующим межпроцессным локом.

> **Поправка 2026-08-16 (хранилище).** Файловые сторы, названные здесь и ниже по тексту, в M4.5
> заменены на SQLite (ADR-0006): состояние — `state.db`, журнал — `journal.db`. Решение этого ADR
> не менялось — UI по-прежнему не имеет своего хранилища и ходит в те же сторы, что и CLI, — но
> имена `admins.json`, `registry.json`, `agents.json`, `tool-inventory.json` и каталог
> `approvals/` читать следует как исторические: сегодня это таблицы в `state.db`. Текст решения
> оставлен как есть намеренно: ADR фиксирует решение на момент принятия.

Обоснование:

1. **Главное**: если очередь одобрений живёт внутри `serve`, оператор `connect`-сценария остаётся
   без UI. Файловая очередь уже кросс-процессная — значит UI обязан быть отдельным входом, а не
   надстройкой над агентским фронтом.
2. **Разные домены доверия**: `serve` аутентифицирует **агентов** Bearer-токенами и обслуживает
   машинный трафик; UI аутентифицирует **человека** cookie-сессией и живёт в браузере (CSRF, CSP,
   clickjacking, `Origin`/`Host`). Один порт и один обработчик — это одна ошибка маршрутизации
   между «агент с токеном» и «админ с cookie».
3. **Механизма не требуется**: консистентность между процессами решена в M3 («через существующие
   файловые сторы»), новых точек правды UI не вводит.

**Что отвергнуто и почему**

| Вариант | Почему нет |
|---|---|
| Смонтировать UI в `serve` под префиксом (`/_admin`) | Ломает (1): без `serve` нет UI. И смешивает два домена доверия на одном обработчике — cookie-аутентификация оказывается в одном роутере с Bearer-аутентификацией агентов |
| UI как статический клиент к API `serve` | То же самое плюс CORS-поверхность и второй способ дотянуться до сторов |
| Демон-«всё в одном» (`serve` + UI + watcher одним процессом по умолчанию) | Отказ одного контура роняет второй; агентский фронт обязан переживать падение операторского |

**Когда пересматриваем**: если появится развёртывание, где два порта неприемлемы (например,
партнёр даёт ровно один ingress). Тогда объединение делается **обратным** способом — общий
reverse-proxy снаружи, а не общий обработчик внутри; правка этого ADR обязательна.

## Решение 2 — стек без зависимостей: `node:http` + server-rendered HTML + ~150 строк vanilla JS

UI собирается из `node:http`, серверно отрендеренного HTML (экранирующий tagged template
`src/ui/html.ts` — единственный путь к разметке), CSS и ~150 строк рукописного JS: `EventSource`
для SSE (`GET /events`) и `fetch` для POST-действий. Зависимости проекта остаются ровно две:
`ulid`, `zod`. Статические ассеты встраиваются в TS-модули строками (`src/ui/assets/app-js.ts`,
`app-css.ts`): `tsc` не копирует не-`.ts` файлы в `dist/`, а трогать build-скрипт ради двух
файлов — лишний риск; побочная выгода — предвычисленный sha256 ассета доступен и для `ETag`, и
для CSP-хеша.

Объём задачи — 5 страниц и ~10 действий, из которых весь state приходит из файлов на диске.
Server-rendered HTML + SSE закрывает его целиком.

**Что отвергнуто и почему**

| Вариант | Цена | Почему нет |
|---|---|---|
| htmx (1 зависимость, без транзитивных) | Вендорить JS всё равно придётся — CSP запрещает CDN | Весь выигрыш — ~60 строк нашего `fetch`-кода. Отклонено по YAGNI |
| React/Vue SPA | Сотни транзитивных пакетов + build-шаг, которого в проекте нет (`npm run build` = `tsc`) | Supply chain того самого артефакта, который партнёр проверяет на аудите; state всё равно с диска |
| Шаблонизатор (ejs/eta) | 1 зависимость + свои правила экранирования | Свой `html`-шаблон даёт экранирование **по умолчанию** и проверяется нашим fuzz-тестом; чужие правила пришлось бы аудировать |
| Бандлер/минификатор ассетов | build-шаг, source maps, версии | Два файла общим объёмом в единицы килобайт |

**Когда пересматриваем**: (а) после пилотов (M6), если UI вырастет в интерактивности —
**отдельным ADR**, не тихим добавлением зависимости; (б) раньше, если бюджет «по файлу на
страницу, < 400 строк, функции < 50» перестаёт держаться — это объективный сигнал, что
рукописный слой перерос себя. Накопление «ещё 300 строк JS» без ADR — нарушение решения.

## Решение 3 — аутентификация: именные админы, персональные токены, три фиксированные роли

Админов произвольное число, каждый — именная запись в `<journalDir>/admins.json` (0600, поверх
`createJsonStore` + существующий лок):
`{name, role, tokenHash, createdAt, rotatedAt?, revokedAt?}`.

- **Токен** персональный: 32 случайных байта (`randomBytes`), хранится **только** sha256, сверка
  через `timingSafeEqual` — та же машинерия, что у агентских токенов (общий `src/security/token.ts`,
  выделяется в Волне 0, Task 2). Значение токена печатается ровно один раз при выпуске и нигде
  не персистится.
- **Роли фиксированные, ровно три**:

| Роль | Может |
|---|---|
| `owner` | всё, включая управление админами (add/remove/rotate/role), реестром серверов и вольтом (имена+даты) |
| `operator` | очередь одобрений (approve/deny), карантин, матрица прав агентов — create/grant/ungrant/revoke (выпуск агентских ключей с ограниченным набором MCP) |
| `viewer` | только просмотр: журнал, очередь, реестр, матрица прав — **ни одного** POST-действия |

- **CLI**: `admin add <name> --role owner|operator|viewer`, `admin list` (имя/роль/даты, без
  хешей), `admin remove`, `admin rotate`, `admin role`. Первый запуск `ui` без `admins.json`
  создаёт `owner` и печатает bootstrap-URL **только в stderr**, один раз. Удаление последнего
  `owner` отклоняется — систему нельзя запереть.
- **Сессии**: `/login` меняет токен на сессионную cookie (`HttpOnly`, `SameSite=Strict`,
  `Path=/`, `Secure` при `--behind-tls`). Сессии живут **в памяти процесса** и несут
  `{adminName, role}`: перезапуск = повторный логин, секреты сессий не персистятся, у
  бэкапа каталога состояния нет материала для угона сессии. TTL + кап числа сессий.
  `remove`/`rotate`/смена роли немедленно убивают живые сессии **именно этого** админа.
- **CSRF**: `SameSite=Strict` + double-submit-токен в каждой форме и каждом `fetch`; все действия
  только POST; `Origin` и `Host` валидируются до аутентификации (`src/net/origin-host.ts`).
- **Rate-limit** на `/login` (константы в `src/ui/constants.ts`); неверный и несуществующий токен
  дают **байт-идентичный** ответ (нет оракула существования — паттерн `transport/http/auth.ts`).
- **Атрибуция**: каждая резолюция и каждое изменение сторов из UI несут `actor: 'ui'` +
  `adminName` — в журнал, в resolved-файл очереди и в `approvals list`. Это опора аудит-экспорта M5.

**Что отвергнуто и почему**

| Вариант | Почему нет | Когда пересматриваем |
|---|---|---|
| «localhost = доверяем», без аутентификации вовсе | Браузер — confused deputy: любая вкладка шлёт POST на `127.0.0.1:8091` и одобряет write-операцию агента. Неприемлемо в продукте, чья функция — контроль доступа | Никогда |
| Пароль + scrypt/argon2 | 32 случайных байта сильнее любого выбранного человеком пароля и ротируются одной командой; argon2 — новая зависимость (ADR-0001); интерактивный ввод ломает автозапуск | Только вместе с SSO-веткой, где пароль всё равно не наш |
| Один общий admin-токен (без имён) | Резолюция без имени решившего не годится под аудит-экспорт M5; ревок одного человека означал бы ротацию для всех | Не пересматривается — это решение 2026-08-11, обратный ход = потеря атрибуции |
| Кастомные роли / гранулярный RBAC | Нет подтверждённого запроса; произвольные роли — это второй язык политик рядом с `policy.json` | После первого же разговора с партнёром (открытый вопрос плана): если попросят — задача M5/после пилотов |
| Скоуп «админ видит только часть серверов» | То же — спроса нет; скоуп требует пересборки каждой выдачи и каждого фильтра журнала | После пилотов, кандидат M5 |
| SSO/SAML/OIDC | Вне границы MVP (PRD); тянет IdP-зависимость в self-hosted продукт и ломает метрику онбординга «10 минут» | После пилотов, отдельным ADR. Это же снимает ограничение «токен передаваем» (см. модель угроз) |
| Персистентные сессии (файл/БД) | Ещё один стор с секретным материалом на диске; выигрыш — не логиниться после рестарта | Если партнёры покажут, что рестарт `ui` частый сценарий |
| mTLS клиентскими сертификатами | Криптографически сильнее токена, но выдача и распространение сертификатов — операционный проект сам по себе; для self-hosted-старта это блокер онбординга | Вместе с SSO-веткой |

## Решение 4 — авторизация deny-by-default: таблица «маршрут × минимальная роль»

Единая таблица в `src/ui/authz.ts`; проверка роли выполняется **до** обработчика. **Маршрут, не
внесённый в таблицу, недоступен никому** — забыть проверку структурно нельзя. Матричный тест
перебирает все зарегистрированные маршруты против всех трёх ролей и «без сессии».

| Маршрут | Минимальная роль |
|---|---|
| `GET /login`, `POST /login`, `GET /assets/*` | без сессии (публично; `/login` под rate-limit) |
| `POST /logout` | `viewer` |
| `GET /` (очередь), `/quarantine`, `/servers`, `/agents`, `/journal` | `viewer` |
| `GET /api/approvals`, `GET /events` (SSE) | `viewer` |
| `POST /approvals/:id/{approve,deny}` | `operator` |
| `POST /quarantine/{approve,reject}` | `operator` |
| `POST /agents/{create,grant,ungrant,revoke}` | `operator` |
| `GET /vault` (только имена и даты) | `owner` |
| `POST /servers/{add,remove}` | `owner` |
| `GET /admins`, `POST /admins/{add,remove,rotate,role}` | `owner` |
| всё остальное | **никто** (deny-by-default) |

Таблица нормативна: расширение набора маршрутов без записи в ней даёт 403 и красный матричный
тест. Изменение уровней в таблице — правка этого ADR.

> **Поправка 2026-08-26 (слёт учётки в браузере).** Таблица и пороги ролей не меняются — меняется
> ФОРМА отказа в одном случае. Запрос, **предъявивший** сессионную cookie, которая больше не
> резолвится (TTL, `rotate`, `remove`, смена роли, подделка), получает: cookie очищается
> (`Max-Age=0`) и ответ — `303 → /login` **навигации** (набранный URL, ссылка, а также форма
> выхода в шапке: это настоящий `<form method="post">`, а не скриптовое действие) либо
> `401 {"error":"session-expired"}` **скрипту страницы**, который представляется заголовком
> `x-requested-with: fetch`. Разводится по тому, КТО спросил, а не по методу: `fetch` прозрачно
> проходит редирект, и на `303` скрипт получил бы страницу входа под `200` — мёртвое действие
> отчиталось бы об успехе; а на нативном POST `401` показал бы оператору JSON-блоб ровно в тот
> момент, когда он попросил себя разлогинить. Заголовок влияет только на ФОРМУ отказа, не на
> допуск, поэтому подделывать его нечего. Оракула существования это не
> создаёт: ответ **одинаков** для маршрута из таблицы и для отсутствующего, а анонимный вызов
> **без** cookie по-прежнему получает единообразный 403 везде, кроме `GET /` (как и было).
> Публичная поверхность (`/login`, `/assets/*`) исключена — браузер шлёт мёртвую cookie и к стилям
> самой страницы входа. Причина та же, что у смоковой находки M4 про голый 403 на посадочной
> странице: оператору, который был в системе минуту назад, JSON-отказ читается как «плоскость
> сломалась». Клиентский скрипт зеркалит это: `401` (или ответ, прошедший редирект на `/login`) →
> `location.replace('/login')`; оставшийся 403 в тосте назван словами («роль не позволяет, либо
> страница устарела — перезагрузите»), потому что дальнейший шаг оператора в этих двух случаях
> разный.

> **Поправка 2026-08-27 (тот же ответ без cookie).** Поправка выше чинила только тот запрос, что
> ПРЕДЪЯВИЛ мёртвую cookie; вызов **без** cookie по-прежнему получал `403 {"error":"forbidden"}`
> везде, кроме `GET /` — а туда попадает ровно тот же оператор: cookie уже вычищена предыдущим
> отказом, и закладка, «Назад» или вкладка на `/servers` снова показывают JSON-блоб. Теперь
> «не залогинен» отвечается ОДИНАКОВО в обоих случаях: `303 → /login` навигации, `401
> {"error":"session-expired"}` скрипту (тот же байт-в-байт ответ — мёртвая cookie и её отсутствие
> снаружи неразличимы), `Max-Age=0` добавляется только если cookie была предъявлена. Исключение
> для `GET /` растворилось в общем правиле и убрано.
>
> Оракул закрыт по-прежнему тем, что ответ **не зависит от пути**: `/vault` (owner-only) и
> `/nope` (нет в таблице) анонимному отвечают одинаково, так что перечислить маршруты нельзя —
> ответ сообщает лишь «ты не вошёл», что вызывающий и так знает. Единообразный `403` остаётся там,
> где различие пути было бы утечкой: **вошедшему** ниже порога роли и на маршрут вне таблицы —
> один и тот же байт-в-байт отказ. POST без `Origin` отбивается раньше и не меняется.

**Что отвергнуто и почему**: (а) проверка роли внутри каждого обработчика — ровно тот способ, при
котором новый маршрут молча оказывается открытым; (б) allow-by-default с «чёрным списком»
привилегированных маршрутов — инвертирует цену ошибки; (в) вывод прав из UI-навигации («нет
ссылки — нет доступа») — не защита, а косметика.

**Когда пересматриваем**: при появлении скоупа по серверам (тогда «роль» перестаёт быть
одномерной и таблица становится «маршрут × роль × скоуп») — это уже другое решение и другой ADR.

## Модель угроз UI

### Против чего защищаемся

- **Браузер как confused deputy (CSRF)**. Любая открытая вкладка может слать POST на
  `127.0.0.1:8091`, и этим POST одобряется изменяющая операция агента. Контрмеры: cookie
  `SameSite=Strict`, double-submit CSRF-токен на каждом действии, все действия только POST,
  валидация `Origin`.
- **DNS rebinding**. Валидация `Host` (не только `Origin`) до аутентификации, общий модуль
  `src/net/origin-host.ts` для агентского фронта и UI; allowlist = bound host + localhost +
  явный `--allowed-host` (имя reverse-proxy).
- **XSS через контент, контролируемый MCP-сервером** — описание тулза, аргументы вызова, payload
  журнала, имена ресурсов. Это **основной** риск UI: враждебный сервер пишет разметку, оператор
  её открывает. Контрмеры: экранирующий по умолчанию tagged template как единственный путь к
  HTML; строгий CSP `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'
  data:; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`;
  `X-Content-Type-Options: nosniff`; `Referrer-Policy: same-origin`; fuzz-тест по всем точкам
  интерполяции (включая unicode/zero-width/homoglyph-нагрузки).

  **Правка 2026-08-12 (смок M4, `a094e47`)**: изначально здесь стояло `no-referrer` — и это
  оказалось неверно. По Fetch-спеке документ под `no-referrer` сериализует заголовок `Origin`
  своих form-POST как `null`, а наш собственный Origin-скрининг отвергает opaque origin (это
  CSRF-поверхность) — вход в UI из любого Chromium становился невозможен. Правильное значение —
  `same-origin`: URL сессии не утекает на чужой origin, свои запросы referrer сохраняют.
  **Ужесточать обратно до `no-referrer` нельзя**; запрет закреплён комментарием в
  `src/ui/security-headers.ts` и hardening-тестом. Урок шире одного заголовка: связку
  referrer-policy → `Origin` не эмулируют ни `node:http`-тесты, ни curl — браузерный смок
  обязателен для каждой браузерной поверхности.
- **Clickjacking** («невидимый iframe с кнопкой approve»): `frame-ancestors 'none'`.
- **Перебор токена**: rate-limit на `/login` + видимая оператору запись; неотличимые отказы.
- **Кража сессии из бэкапа/копии каталога**: сессии не персистятся вовсе.
- **Эскалация роли через забытую проверку**: deny-by-default authz-таблица + матричный тест.
- **Утечка значений секретов в браузер**: см. ниже, отдельный инвариант.

### Secrets-never-in-browser — слоевой инвариант, а не обещание

Вольт в UI показывается **только именами и датами**. Значения секретов не вводятся и не
отображаются: `vault set` читает значение со stdin именно для того, чтобы оно не попало ни в
argv, ни в историю оболочки; веб-форма вернула бы это обратно и добавила бы значение в память
браузера, в автозаполнение и в дамп вкладки.

Гарантия делается проверяемой, а не декларируемой, тестом графа импортов
(`tests/architecture/imports.test.ts`):

- `src/ui/**` **никогда** не импортирует `vault/resolve.ts` и не вызывает `readSecretValues`;
- `src/ui/**` не импортирует `src/proxy/**` и `src/transport/**` (кроме чистого
  `src/net/origin-host.ts`): UI — операторская поверхность, не трафиковая;
- ничто вне `src/ui/**` и `src/cli/ui-cmd.ts` не импортирует `src/ui/**`.

Плюс маркер-тесты: ни одно значение вольта и ни один admin-токен не встречаются ни в одном
HTTP-ответе UI, ни в SSE-потоке, ни в журнале, ни в логах.

### От чего НЕ защищаемся — названные ограничения

- **Токен можно передать другому человеку. Именная учётка — это атрибуция, а не криптографическая
  identity.** Стор админов доказывает, «под чьим токеном» произошло действие, но не «кто физически
  сидел за клавиатурой». Смягчение: персональные токены по умолчанию, `admin list` с датами
  выпуска и ротации, ревок и ротация в одно действие, практика «один человек — один токен» в
  README. Настоящее закрытие — SSO/IdP, после пилотов (Решение 3, таблица отвергнутого).
- **Компрометация хоста или того же uid.** Кто читает файлы пользователя — читает стор админов
  (`state.db`), `vault.key`, журнал. Это та же граница доверия, что зафиксирована в ADR-0003; UI её
  не понижает и не повышает.
- **Одобрение из shell агентом, работающим под тем же uid** (поправка 2026-08-16, по итогам
  ручного смока захода «укрепление UI + availability»). Это НЕ частный случай пункта выше:
  там граница доверия уже потеряна, а здесь гейтящийся агент под тем же uid — **штатная работа**,
  ровно та популяция, ради ограничения которой плоскость и существует. Таблица авторизации
  (Решение 4) была нормативна только для HTTP-маршрутов; путь `mcp-journal approvals approve`
  лежал вне её, и ничто не мешало агентскому процессу его вызвать (паритет ролей закрыт в M5,
  волна 2 — поправка ниже; сама возможность вызова под тем же uid осталась). Смок нашёл и усугубляющий фактор:
  синтезированная ошибка, которую получал загейченный агент, **содержала готовую команду
  самоодобрения с настоящим id** — инструкция по снятию блокировки доставлялась заблокированной
  стороне в канал, которому она доверяет по умолчанию. Команда и id из прозы убраны
  (`src/proxy/synthesize.ts`, инвариант закреплён тестом по всем `*Error`-билдерам), но это
  снимает подсказку, а не саму возможность. Настоящее закрытие — требовать для `approvals approve`
  контекста, которого агентский процесс структурно не может получить; такого контекста в M5 не
  нашлось — разрыв атрибуции закрыт, сама возможность самоодобрения осталась (поправка ниже).

  > **Поправка 2026-08-18 (M5, волна 2, задачи 2.3/2.5).** Одобрение из shell больше не анонимно:
  > `approvals approve|deny` требует персональный админ-токен в окружении (`MCP_ADMIN_TOKEN`),
  > сверка идёт через тот же `findAdminByToken` (хранится sha256, сравнение `timingSafeEqual`;
  > отозванный админ отвечает ровно как несуществующий), и резолюция несёт
  > `actor: 'cli:<adminName>'` вместо прежней константы `actor: 'cli'`. Решение владельца PRD — O3
  > плана M5 (`.claude/PRPs/plans/m5-tamper-evident-journal.plan.md`).
  >
  > **Токен здесь покупает атрибуцию, а не барьер.** Процесс под тем же uid читает и переменные
  > окружения оператора, и его файлы — это уже названная и принятая граница доверия (пункт
  > «Компрометация хоста или того же uid» выше, ADR-0003; тот же тезис — в «Ключевых дизайн-решениях»
  > плана M5, п. 4). Отсюда честное утверждение: журнал теперь фиксирует, **какой именной человек**
  > одобрил изменяющую операцию. И честное НЕ-утверждение: это не мешает процессу под тем же uid —
  > включая агента, которого запустил сам оператор, — одобрить вызов от своего имени, взяв токен
  > оператора из его же окружения.
  >
  > Следствие, которое ADR обязан назвать прямо: **гарантия human-in-the-loop против агента под тем
  > же uid — организационная, а не техническая.** Держится она на том, что оператор не отдаёт свой
  > токен процессу, который сам же гейтит. Технические кандидаты известны и в границу MVP не входят:
  > отдельный uid для одобряющей поверхности и внеполосный канал подтверждения (ROADMAP.md:34, 96 —
  > оба помечены «после пилотов»). Это кандидаты, а не обязательства.
  >
  > **Паритет ролей между поверхностями закрыт.** CLI-резолюция требует ту же минимальную роль, что
  > и HTTP-маршрут: `operator` (`viewer` не может одобрять ни с одной поверхности — Решение 3).
  > Порог вынесен в одну константу `APPROVAL_RESOLVE_MIN_ROLE` (`src/admin/authz.ts`), которую
  > читают и `ROUTE_TABLE`, и CLI, — иначе таблица Решения 4 обходилась бы через терминал.
  > `approvals list` остаётся без токена намеренно: чтение очереди — не событие авторизации.
  >
  > Что это меняет для аудит-отчёта (волны 4–5): резолюция называет человека, и отчёт вправе это
  > утверждать. Чего отчёт утверждать по-прежнему не вправе: что названный человек присутствовал и
  > осознанно принял решение. Текст отчёта обязан держать эту границу — переоценка гарантии здесь
  > становится переоценкой в документе, который читает аудитор.
  >
  > Цена перехода принята сознательно: ломается привычка «одобряю из shell без всякого токена», по
  > которой шли dogfood M2–M4; без валидного токена команда завершается ненулевым кодом и подсказкой,
  > как выпустить токен. Владелец PRD выбрал этот размен, чтобы ни одна резолюция в будущей
  > подписанной цепочке не осталась без субъекта.
- **Чтение статуса сервера, повлёкшее исполнение на хосте** (поправка 2026-08-24, M5.5 пункт 1,
  решения владельца O1–O8 — полный разбор в **ADR-0008**). Активная проба состояния подключения
  делает `GET /servers` маршрутом, который может заспавнить `stdio`-командную строку из реестра или
  обратиться к `http`-эндпоинту с учётками вольта. Минимальная роль строки таблицы Решения 4 не
  изменилась (`viewer`), **изменился её смысл**: право чтения приобрело побочный эффект исполнения.
  Прежняя рамка «плоскость исполняет чужую командную строку только по подтверждению человека»
  сохраняется лишь в части «что исполняется» (байт-в-байт подтверждённая запись реестра), но не в
  части «когда и сколько раз». Таблица маршрутов пополняется строкой `POST /servers/refresh` →
  `operator`. Компенсации, отвергнутые альтернативы и условия пересмотра — в ADR-0008; сюда они не
  дублируются.
- **Вредоносное расширение браузера или уже скомпрометированный браузер.** `HttpOnly` закрывает
  чтение cookie из страничного JS, но не расширение с доступом к вкладке.
- **Не-localhost bind без TLS.** Дефолт — `127.0.0.1`. Не-localhost только явным `--host`, с
  громким предупреждением в stderr; `--behind-tls` включает `Secure` на cookie. TLS — **терминацией
  снаружи** (reverse-proxy), внутрь продукта не заносится: это отдельный ADR-класс решения
  (сертификаты, ротация, ACME), которого MVP не берёт. README требует reverse-proxy явно.
- **Approval fatigue** — угроза не техническая, но реальная: UI делает «да» на один клик быстрее,
  чем осмысление. Контрмеры продуктовые: структурный дифф схемы и класс тулза прямо на карточке,
  запрет массовых действий для `write`/`destructive`, отдельная отметка «ожидание агента уже
  истекло — approve выдаст только грант на ретрай». Наблюдается в dogfood.

**Когда пересматриваем модель угроз**: при первом же не-localhost развёртывании у партнёра
(появляется сеть между браузером и плоскостью) и при появлении SSO (меняется всё, что здесь
сказано про токены и сессии).

## Последствия

- (+) UI работает в основном сценарии M3 — при незапущенном `serve`; это сквозной e2e-критерий
  (Task 18, сценарий 3).
- (+) Аудитоспособная поверхность зависимостей не меняется: по-прежнему два прод-пакета.
- (+) Именная атрибуция резолюций появляется до M5 — аудит-экспорту будет что экспортировать.
- (−) **Третий писатель в сторы** (CLI + `serve` + UI): узкие места межпроцессного лока
  обостряются. Смягчение — Task 2 (аварийное восстановление битого чужого лока); CAS-ревизия
  остаётся в бэклоге с честной формулировкой.
- (−) Рукописный UI-слой требует дисциплины по объёму (< 400 строк на файл); превышение — сигнал
  к пересмотру стека отдельным ADR, а не к тихому накоплению.
- (−) Сессии в памяти: рестарт `ui` разлогинивает всех.
- Security-ревью `ecc:security-reviewer` по `src/ui/**`, `src/admin/**`, `src/net/origin-host.ts`
  обязательно (Task 9 отдельно + Task 19): аутентификация, авторизация и обработка недоверенного
  ввода — три STOP-триггера сразу.

## Связанные решения

- ADR-0001 — граница зависимостей (два прод-пакета), которую это решение обязано сохранить.
- ADR-0003 — граница доверия «учётная запись ОС»; UI её наследует.
- ADR-0005 — источник политики по классу доверия входа; UI относится к `operator-launched` и
  показывает эффективную политику, но не пишет её.
- ADR-0008 — активная проба состояния сервера: правит модель угроз этого ADR (чтение может повлечь
  исполнение) и добавляет в таблицу Решения 4 маршрут `POST /servers/refresh`.
