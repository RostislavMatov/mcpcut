# ADR-0017: hosted mcpcut — установка на пользователя и режим арендатора

- **Статус**: принято (2026-09-27, решение владельца «полноценные учётки сейчас» и развилки HA1–HA12
  PRD `hosted-accounts.prd.md`, все — по предложению)
- **Область**: конфиг установки (`src/setup/schema.ts`, секция `tenant`), настройки режима
  (`src/tenant/*`), гейт записи реестра, агентов и групп, SSRF-страж исходящих запросов к upstream
  (`src/net/address-class.ts`, `src/net/upstream-guard.ts`, `src/transport/http/client*.ts`), замок
  stdio на старте (`src/upstream/prepare.ts`, `src/cli/serve-upstream.ts`, резиденты), сетевой фильтр
  удалённой консоли (`src/ui/console-run.ts`), `setup --tenant`.
- **Поправляет**: [ADR-0011](0011-open-source-release.md) — граница «без SaaS» и заморозка D4 сняты
  решением владельца 2026-09-27; [ADR-0014](0014-remote-console.md) — в режиме арендатора пол ролей по
  сети дополнен отказом путевых форм (T6); [ADR-0008](0008-server-probe-threat-model.md) — проба ходит
  через страж (T4).
- **Основание**: PRD `.claude/prds/hosted-accounts.prd.md`, план
  `.claude/PRPs/plans/tenant-mode.plan.md`, исследование рынка и кода 2026-09-27.

## Контекст

Владелец решил открыть на `mcpcut.com` личные учётки: у каждого свои ≤ 5 MCP-серверов и ≤ 5 агентов
(ROADMAP, намерение 2026-09-23; решение 2026-09-27). Продукт построен вокруг одной установки: серверы,
агенты, группы, политика, вольт, журнал и его цепочка — документы на установку, роли общие, ключ
подписи один. «Поле владельца» во всех сторах — около 150 файлов и высокий риск утечки между
пользователями; рынок знает, чем это кончается (Asana 2025, n8n-MCP 2026).

При этом владелец установки сегодня может: зарегистрировать stdio-сервер — то есть выполнить любую
команду на хосте; направить http-upstream на `127.0.0.1`, `169.254.169.254` или внутреннее имя — и
проба сходит туда сама (ADR-0008); завести до 200 серверов и агентов. Для своей установки это норма.
Для установки, отданной незнакомому человеку, — нет (урок Smithery 2025: сборка чужого кода у себя →
RCE на 3000+ серверах).

## Решение

| # | Решение | Почему |
|---|---|---|
| **T1** | Hosted = **установка на пользователя**: свой каталог данных, свои `ui` и `serve`, свой вольт, ключ подписи и журнал, поддомен `<login>.mcpcut.com`. Поле владельца в общих сторах отвергнуто | изоляция данных уже полная на границе установки (`src/config.ts`, `src/setup/data-dir.ts`); ядро продукта не узнаёт о других пользователях; отчёт пользователя подписан его ключом и не содержит чужих записей |
| **T2** | Секция **`tenant`** в `config.json` включает режим арендатора. Нет секции — поведение прежнее байт в байт; есть (даже пустая) — отсутствующие поля берут **строгие** значения. Пишет её только `setup` (`--tenant` — явный пресет) | один переключатель, который видно в файле; арендатор его не снимет: `setup` вне allowlist удалённой консоли, shell ему не дают |
| **T3** | **stdio запрещён**: отказ на записи в реестр (стор — единственный писатель: CLI, веб, TUI, удалённая консоль) и **замок на старте** в `connect`/пробе/`serve`; резидентами stdio не становятся | запись могла появиться до включения режима; супервизор резидентов не должен крутить отказ |
| **T4** | **Только публичные `https`-upstream**: схема проверяется на записи, адрес — при каждом подключении. Проверка живёт **внутри `lookup` сокета** (одна резолюция на проверку и подключение — нет окна для DNS rebinding); IP-литералы проверяются до запроса (для них `lookup` не вызывается); смешанный DNS-ответ отказывает целиком; редиректы upstream не выполняются (как и раньше). Запрещены loopback, приватные, link-local (metadata), CGNAT, unspecified, multicast, зарезервированные и документационные диапазоны, в т. ч. IPv4, спрятанный в IPv6 (mapped, compatible, NAT64, 6to4). Резолвленный адрес в ошибку не попадает. **Поправка фазы 3 (O8)**: та же проверка (запись и страж) отказывает явному порту, отличному от 443 — исходящие с общего хоста арендаторов идут только на 443 | SSRF — главный класс атак на hosted-шлюзы; внутренний DNS хоста не раскрываем арендатору |
| **T5** | **Лимиты** из секции: 5 серверов, 5 агентов, 2 группы по умолчанию (HA7); проверяются **только на записи** | включение режима поверх большой установки не должно ломать чтение |
| **T6** | Удалённая консоль в режиме арендатора **не принимает argv, называющий путь на сервере** (`backup`, `migrate`, `start`, `stop`, `logs`, флаги-пути, `policy validate`); потоковый `export` остаётся — файл пишет клиент | ADR-0014 честно записал «owner-токен по сети ≈ shell на сервере»; арендатор — owner своей установки, но не хоста |
| **T7** | Заморозка D4 и граница «без SaaS» сняты решением владельца 2026-09-27 | ADR-0011 предполагал только self-hosted |

Режим арендатора — **не изоляция**. Он закрывает то, что продукт делает по воле владельца установки.
Изоляцию процессов, файловой системы, сети и памяти даёт контейнер на пользователя (HA2, фаза 3 PRD):
отдельная сеть без доступа к хосту и соседям, лимиты CPU/памяти, исходящие только на 443.

## Что отвергнуто

- **Поле владельца во всех сторах одной установки** — объём, риск утечки, общая цепочка журнала.
- **stdio в песочнице (microVM на пользователя)** — рынок так делает (Glama, TrueFoundry), но это
  другой продукт и другая эксплуатация; нужен stdio — ставьте у себя.
- **Проверка адреса до подключения отдельным `dns.lookup`** — между проверкой и подключением DNS
  может ответить иначе (rebinding).
- **Новый статус пробы для отказа стража** — отказ идёт как `error` с причиной; схема записей
  журнала и `verify --report` не меняются.
- **Лимит в схеме чтения** — ломал бы чтение установки, где записей больше лимита.

## Последствия

- Self-hosted установка без секции `tenant` не меняется: тесты, не знающие о режиме, не правятся.
- Hub (фаза 2) создаёт установку `setup --yes --tenant --admin <login> …`; контейнер (фаза 3) задаёт
  `MCPCUT_TENANT=1`.
- Арендатор видит понятные отказы во всех интерфейсах; тексты пиннятся тестами.
- Оператор хоста технически может читать данные установок (root); это раскрыто в Privacy (HA10),
  инструментов для этого в hub нет (HA11).

## Когда пересматриваем

- Просьбы пользователей о stdio на нашей стороне — только вместе с песочницей на пользователя.
- Первый инцидент злоупотребления или жалоба с IP хоста — переезд на отдельный VPS (HA3).
- Нужда в разных лимитах для разных пользователей — флаги `--max-*` у `setup`.

## Поправка 2026-09-27 — фаза 2 (hub)

Фаза 1 (T1–T7 выше) — режим арендатора внутри установки. Фаза 2 — отдельный процесс **hub** на
`mcpcut.com`: вход через GitHub, учётки, лист ожидания, потолок 15 учёток (HA3), правила входа (HA12).
Установки по-прежнему создаёт **оркестратор** (фаза 3, не в этой поправке) — hub держит только его
интерфейс и реализацию-заглушку, которая до готовности оркестратора кладёт человека в лист ожидания.
Решения приняты при планировании (`.claude/PRPs/plans/hub-signin-accounts.plan.md`, все — по
предложению):

| # | Решение | Почему |
|---|---|---|
| **H1** | hub импортирует из `src/` только allowlist: `src/ui/html.ts`, `src/ui/security-headers.ts`, `src/security/token.ts`, `src/store/sqlite.ts`, `src/net/origin-host.ts` (+ их транзитивные импорты) — держит `tests/architecture/hub-imports.test.ts`; `src/` не импортирует `hub/` | DRY без повторной реализации HTML-экранирования, заголовков, токенов и SQLite-обёртки, но без второй двери в состояние установки (конфиг, вольт, admin-сторы) |
| **H2** | Сессии hub — в памяти процесса (рестарт = войти заново через GitHub одним кликом); cookie `__Host-mcpcut_hub`, 7 дней абсолютно, 24 ч простоя | KISS; тот же выбор, что и у терминальной консоли и у admin UI — не строить персистентный стор сессий ради процесса, который и так должен быть недорог перезапустить |
| **H3** | Учётки, лист ожидания и надгробия — отдельная база `hub.db` (`node:sqlite`, `STRICT`-таблицы), ключ — числовой GitHub `id`, не `login` | `login` меняется и может перейти к другому человеку; привязка по нему привязала бы чужую учётку к новому владельцу того же имени |
| **H4** | Токен доступа GitHub не хранится нигде: он нужен только чтобы прочитать профиль, сразу после — отзывается (`DELETE …/token`); ошибка отзыва — запись в лог, не отказ входа | минимум данных на руках у hub (HA10 Privacy) — токен, который может звать GitHub API от имени пользователя, не должен переживать один HTTP-запрос |
| **H5** | Пока оркестратор (фаза 3) не готов, вход кладёт человека в лист ожидания и показывает номер очереди вместо отказа | hub можно развернуть и собирать реальный спрос уже сейчас, не дожидаясь фазы 3; честная формулировка на лендинге — «hosted in preview», без обещания срока |
| **H6** | `CF-Connecting-IP` считается настоящим адресом клиента только когда `HUB_TRUST_CF_CONNECTING_IP=1`, то есть hub слушает исключительно внутри сети compose и недоступен иначе как через Caddy; для зоны `mcpcut.com` — Cloudflare Authenticated Origin Pulls (mTLS), задача деплоя, не кода | без этого прямой запрос на IP origin'а подделал бы заголовок и обошёл частоту входа на IP (HA12) |
| **H7** | Операторские действия (`list`, `block`, `unblock`, `delete`, `purge-tombstones`) — CLI (`node hub/dist/hub/src/cli.js …`) на хосте, без веб-панели | доступ оператора к hub уже равен доступу оператора к хосту; отдельная панель добавила бы поверхность атаки без нового права |
| **H8** | Terms и Privacy — страницы самого hub, не внешний документ; текст — черновик, вычитывает владелец до реального запуска | HA10: обещания (бесплатно, как есть, без SLA), что хранится (GitHub id, login, даты), что журнал вызовов технически доступен оператору хоста, и что описание журнала — «tamper-evident with an external anchor», не секретность от оператора |

Как и в фазе 1, это не про изоляцию: контейнер на пользователя (HA2, фаза 3 PRD) даёт то, что hub сам
не может — отдельные процесс, файловую систему, сеть и лимиты для каждой учётки.

## Поправка 2026-09-27 — фаза 3 (оркестратор)

Фаза 3 PRD: по вызову hub появляется собственно установка — контейнер на пользователя, а не только
учётка в `hub.db`. План `.claude/PRPs/plans/tenant-orchestrator.plan.md`, решения O1–O9 (все — по
предложению, сверены владельцем при планировании):

| # | Решение | Почему |
|---|---|---|
| **O1** | **provisioner** — отдельный процесс/контейнер от того же образа hub (`hub/src/provisioner/*`, точка входа `cli.js provision`), единственный с `/var/run/docker.sock`; узкое HTTP-API для hub (create/rotate/remove/status одного tenant) за Bearer-секретом из файла; сеть только с hub (`hub-internal`, `internal: true`) | HA2 «ограниченный прокси Docker API»: вместо фильтра сырых вызовов — узкий сервис с фиксированными шаблонами (`templates.ts`); взлом hub не даёт Docker, взлом provisioner не даёт интернет |
| **O2** | Один контейнер на пользователя (`ui`+`serve` под общим PID 1, `docker/tenant-run.sh`: `first-start.sh` при пустом конфиге → оба процесса → `wait -n` → выход с кодом упавшего, второй гасится; `restart: unless-stopped` в шаблоне контейнера, не в compose) | вдвое меньше памяти, чем два контейнера; общий том без гонок (тот же инвариант, что у корневого `docker-compose.yml`) |
| **O3** | Лимиты контейнера: `Memory 256m` (+ равный `MemorySwap` — без подкачки), `NanoCpus 0.25`, `PidsLimit 128`, `CapDrop ALL`, `no-new-privileges`, `ReadonlyRootfs` (том `/home/node/.mcpcut` и `/tmp` — tmpfs `noexec,nosuid,nodev` — записываемые), пользователь `node`, `Init: true` (докеровский PID 1 собирает `ui`/`serve`'ные зомби) | HA2; stdio запрещён режимом арендатора (T3), процессов мало |
| **O4** | Своя сеть на пользователя `mcpcut-t-<sub>` (имя = имя контейнера = имя тома), не `internal` — исходящие только на 443 держит страж (T4/O8), не сетевая изоляция; к сети подключается только `caddy` (по `PROVISIONER_CADDY_CONTAINER`), соседей друг у друга нет | изоляция без iptables на общем хосте; Caddy — единственный общий участник, и он не становится членом сети арендатора — только подключается к ней |
| **O5** | Маршрутизация — один блок Caddy `*.mcpcut.com:8443`: `{http.request.host.labels.2}` (0 от правого края — `com`=0, `mcpcut`=1, `<sub>`=2) даёт upstream `mcpcut-t-<sub>`; `/mcp`, `/mcp/*` → `:8090`, остальное → `:8091`; `mcpcut.com`, `www`, `mcp` — свои более специфичные блоки (Caddy сортирует по специфичности сам, не по порядку в файле) | без перезагрузок Caddy на `provision-create`/`-remove`; префикс `mcpcut-t-` не даёт Host-заголовку добраться до `hub`/`caddy`/`provisioner` по имени; неизвестный поддомен → 502, не чужой контейнер |
| **O6** | Все имена — через прокси Cloudflare: wildcard `*` (proxied) + `mcp` (proxied) + Origin Rule на `:8443` для `mcpcut.com` и `*.mcpcut.com`; один Origin CA на `mcpcut.com, *.mcpcut.com`; **Let's Encrypt для `mcp.mcpcut.com` убран**, адрес агента стал `https://mcp.mcpcut.com/mcp` (без порта) | wildcard Origin CA теперь перекрывает ранее отдельный LE-сертификат `mcp.mcpcut.com` (та же ловушка, что 26.08 в другом месте: загруженный сертификат, совпавший по имени, отменяет ACME для этого имени) — проще одна схема TLS на все имена, чем держать вторую только ради одного поддомена |
| **O7** | Токен владельца — `mcpcut admin add <login-в-нижнем-регистре> --role owner --json` (новый флаг) внутри контейнера через `docker exec`; ротация — `admin rotate <admin> --recover --json`. **Отклонение от плана**: план предлагал имя админа = логин как есть; логины GitHub регистронезависимы и могут содержать заглавные буквы, а имена админов установки — нет (`ADMIN_NAME_PATTERN`), поэтому `adminNameOf(login)` приводит к нижнему регистру перед вызовом | надёжный разбор одной JSON-строки вместо regex по человекочитаемому выводу; регистр — не потеря информации (GitHub логины не разлличаются регистром для адресации), а совместимость с уже принятым правилом имён админов |
| **O8** | Режим арендатора отказывает записи и стражу при явном порте upstream, отличном от 443 (та же проверка T4, не новая) | HA12 «исходящие только 443» без iptables на общем хосте — сузили существующий https-only страж, не добавляли второй механизм |
| **O9** | Жёсткой квоты диска на том арендатора нет; `provisioner status <sub>` отдаёт размер тома, оператор смотрит его командой, а не автоматическим отказом | локальные тома Docker не квотируются без `xfs` project quota, которого этот хост не предполагает; жёсткая квота — триггер переезда на отдельный VPS (тот же триггер, что и в фазе 1) |

Отклонения реализации от плана (найдены при кодировании, не решения владельца — записаны для памяти):

- **Поддомен ≤ 54 символов, не 63.** Имя контейнера/сети/тома — `mcpcut-t-<sub>`, а DNS-метка, которую
  резолвит Caddy на сети арендатора, ограничена 63 символами целиком; `MAX_TENANT_SUBDOMAIN_LENGTH = 63
  - length('mcpcut-t-')` = 54. GitHub-логин ≤ 39 символов, суффикс коллизии hub — ≤ 4, так что ни один
  настоящий поддомен к границе не приближается.
- **Готовность — фиксированным `node -e`-скриптом (TCP-connect к `serve`, `GET /login` к `ui`), не по
  `status --json`**: под 0,25 CPU контейнера сама загрузка CLI (конфиг, zod, обе SQLite) уже превышала
  таймаут опроса, и provisioner никогда не видел установку готовой — найдено живым смоком на S2
  2026-09-27.
- **`PROVISIONER_MAX_TENANTS`** — параметр из плана Task 4 (`DEFAULT_MAX_TENANTS = 20`), в тексте плана
  не было отдельного пункта O; добавлен в таблицу выше как часть O1 для полноты переменных окружения.
- **`ReadonlyRootfs` + tmpfs `/tmp` нашли хвост: `export --report` без `--out`.** Команда по умолчанию
  пишет отчёт в `mcpcut-report` под текущей директорией (`src/cli/export-cmd.ts`), а `WORKDIR` образа —
  `/app`, доступный только на чтение в режиме арендатора (O3). Без явного `--out <путь в
  /home/node/.mcpcut/...>` вызов внутри контейнера арендатора получит `EROFS`. Не исправлено в этой
  фазе (оркестратор Docker не трогает; хвост — не поведение самой установки, которое правит фаза 1) —
  записано в ROADMAP для решения владельца: сузить дефолт под режимом арендатора или оставить как есть
  и документировать в подсказке `--help`.

Как и раньше, это не про безграничную изоляцию: оператор хоста с доступом к Docker технически видит
данные любого арендатора (root на хосте видит содержимое любого тома) — то же раскрытие HA10/HA11, что
и в фазе 1, теперь ещё и явно через `docker exec`/`docker cp` в чужой контейнер.

## Поправка 2026-09-27 — фаза 4 (путь «вход → первый вызов» и эксплуатация)

Фаза 4 PRD: установка создаётся в фоне, неиспользуемые останавливаются и удаляются, у агентского фронта
установки — лимит запросов. План `.claude/PRPs/plans/hosted-path-and-ops.plan.md`, решения P1–P8 (все —
по предложению плана):

| # | Решение | Почему |
|---|---|---|
| **P1** | Callback GitHub для нового человека: запись `pending` → `orchestrator.create` **в фоне** (задача в процессе hub) → сразу страница «preparing your install» с meta-refresh на `/account` раз в 3 с; `/account` для `pending` — «preparing», для готовой — токен владельца **один раз** | ответ укладывается в лимит Cloudflare (100 с), а создание может идти до 95 с; человек видит, что происходит |
| **P2** | Токен владельца между созданием и показом живёт **только в памяти hub**, привязан к учётке (GitHub id + `created_at` строки), выдаётся один раз, TTL 15 мин; не выдан (рестарт hub, истёк) — на `/account` штатная кнопка «issue a new owner token» | токен не пишется на диск нигде |
| **P3** | Сбой фоновой задачи → строка `pending` удаляется (без надгробия), на `/account` один раз «we could not create your install — sign in again» | нет «полуучёток» |
| **P4** | Старт hub (и теперь — каждый цикл sweeper'а): каждая `pending`, над которой не работает задача, сверяется с provisioner — контейнер есть → `active` (токен — ротацией), нет → строка удаляется, provisioner не ответил → остаётся `pending` | хвост фазы 2; повтор в цикле закрывает provisioner, недоступный в момент старта hub |
| **P5** | Активность установки = max(последний вход в hub, mtime `journal.db`/`state.db` и их `-wal` в томе); provisioner читает mtime через `docker exec` `stat -c %Y` в **работающем** контейнере; проверка раз в 6 ч (первая — через минуту после старта `serve`) | журнал пишется на каждый вызов агента и каждое действие админа — установка, которой пользуются только агенты, активна |
| **P6** | 60 дней без активности → `POST /tenants/:sub/stop` + `stopped_at` в `hub.db`; вход в hub или открытие `/account` → `POST /tenants/:sub/start` в фоне, после успеха `stopped_at = NULL`; 90 дней → `remove` установки + удаление учётки **без** надгробия (повторная регистрация не блокируется). `/account` заранее пишет обе даты | HA9 |
| **P7** | Лимит запросов — в самом `serve` в режиме арендатора: `tenant.maxRequestsPerSecond` (10) и `tenant.maxRequestsPerDay` (10 000), HTTP-запросы к агентскому фронту, без семантики JSON-RPC; отказ `429` + `Retry-After`; счётчики в памяти | в Caddy нет rate-limit без плагина; hub трафик агентов не видит |
| **P8** | Колонка `stopped_at` добавляется `ALTER TABLE … ADD COLUMN` (идемпотентно, по `PRAGMA table_info`), CHECK статусов не трогается; свежая и старая база проходят один и тот же путь открытия | SQLite не меняет CHECK без пересборки таблицы |

Уточнения реализации Task C (не новые решения — как именно исполнены P4–P6):

- **`stat`, не `node -e`.** GNU `stat` — из `coreutils`, пакета Essential в Debian, поэтому он есть в
  `node:24-bookworm-slim` (демон Docker при реализации был выключен — проверено по составу базового
  образа, не запуском). `node -e 'fs.statSync…'` дал бы то же, но поднимал бы второй процесс Node в
  контейнере с потолком 256 MiB на каждую проверку. Отсутствующий файл (`-wal` после checkpoint) — не
  ошибка: `stat` печатает строки только для найденных, жалуется в stderr и выходит кодом 1; берётся
  максимум из напечатанного. Любой другой код выхода или строка не из цифр — `bad-output`, а не «нет
  активности»: сбой чтения никогда не превращается в повод остановить или удалить установку.
- **Остановленная установка не опрашивается**, её активность ограничена сверху датой остановки:
  `activity = max(lastSeenAt, lastActivityAt, stoppedAt − 60 d)`. Sweeper остановил её только после
  60 дней простоя, поэтому настоящая активность была не позже `stoppedAt − 60 d` — удаление наступает
  не раньше 90 дней от неё и не позже 30 дней после остановки.
- **Запуск по входу считается входом**: `markStarted` вместе со снятием `stopped_at` ставит
  `last_seen_at = now`. Иначе следующий цикл, увидев ту же старую активность, остановил бы установку
  снова через 6 ч после того, как человек пришёл.
- **Статус provisioner'а — под тем же keyed-lock по поддомену**, что create/rotate/remove/stop/start:
  чтение не видит установку, собранную наполовину. Это закрывает гонку «рестарт hub посреди create»:
  сверка `pending` ждёт окончания create (или таймаута клиента, 30 с — и тогда строка остаётся `pending`
  до следующего цикла), вместо того чтобы увидеть контейнер, который откат тут же удалит.
- **Перед удалением строка перечитывается и решение принимается заново**: вход в hub во время цикла
  спасает учётку. Порядок — сначала установка, потом строка: сбой `remove` оставляет учётку на месте,
  и следующий цикл повторяет.
- **Метка остановки на работающем контейнере** (запущен руками, мимо hub) считается устаревшей и
  снимается; установку судят по её собственной активности.
- **Операторский `sweep [--dry-run]` не сверяет `pending`**: только процесс `serve` знает, какие из них
  он сейчас создаёт, а сверка из другого процесса могла бы удалить строку, для которой идёт create
  (осиротевшая установка), или активировать её раньше задачи (токен владельца потерян). Сверка идёт
  в каждом цикле самого `serve`.

Отклонения реализации Task A от плана (найдены при кодировании — записаны для памяти):

- **Удаление учётки в состоянии `pending` → `409`** («your install is still being prepared»): `remove`,
  пересекшийся с фоновым create, мог бы оставить установку без учётки.
- **Ротация и удаление забывают ждущий токен** (`pendingTokens.forget`): первый токен перестаёт
  работать в момент выпуска нового, а у удалённой учётки его некому показывать.
- **Отметка «создание не удалось» читается на любом GET сессионного маршрута**, не только на
  `/account`: сессия этой учётки уже мертва (строки нет), и первый же её запрос должен объяснить
  человеку причину, а не молча отправить на `/signin`.

Хвост «рестарт hub посреди create → `active` без установки при откате»: после keyed-lock на статусе
он сужен, но не исключён (например, установку удалили руками мимо hub). Sweeper видит такую учётку
как `absent` у `active` и **не удаляет её молча**: пишет в лог `install missing, account kept for the
operator`, а `/account` показывает «Your install is missing … contact the operator» (флаг — в памяти
hub, после рестарта появляется с первым циклом). Решает оператор: `delete <login>` (remove идемпотентен)
или `provision-create` руками. Автоматическое «issue a new install?» не строилось — у кнопки, создающей
установку заново, должна быть та же проверка потолка и правил входа, что у регистрации, а это отдельное
решение.

Архитектурный страж (Task D): `tests/architecture/hub-imports.test.ts` держит, что
`hub/src/provisioner/docker*.ts` импортируют только файлы `hub/src/provisioner/**` (hub'овский `cli.ts`
достаёт их лишь через `provisioner/cli.ts`, чтобы запустить сам provisioner), и что
`hub/src/{server,routes,signin,serve,provisioning,orchestrator,orchestrator-http,idle-sweeper,
install-waker,operator}.ts` не достигают Docker-клиента ни одним транзитивным путём — сокет Docker
остаётся только у provisioner'а (O1).

Закрытие MEDIUM ревью фазы 4 (установка заблокированного не работает): операторский `block` учётки в
`pending` — **отказ** (exit 1, «account is being created; try again in a minute» — иначе create,
завершившись после блокировки, оставил бы живую установку вне учёта); `block` активной — `stop`
установки (данные сохраняются, `stopped_at` ставится, сбой — предупреждение в stderr, статус всё равно
`blocked`), `unblock` ничего не запускает — запустит вход человека или оператор; каждый цикл sweeper'а
останавливает установки `blocked`-учёток без `stopped_at` (страховка на гонку, сбой `stop`, шелл без
связи с provisioner и блокировки до этого правила).
