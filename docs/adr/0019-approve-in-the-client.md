# ADR-0019: одобрение удержанного вызова прямо в клиенте (MCP form elicitation)

- **Статус**: принято (2026-10-01, решение владельца M17 «P2 и P3 в выпуске до запуска»; предложение P2)
- **Область**: `src/proxy/client-approval.ts`, `gate-router.ts` (перехват ответов, `initialize`),
  `gate-approvals.ts` (вопрос на время ожидания), `gate-core.ts`, `wire-policy.ts` (`askClientOf`),
  `src/cli/wrap-cmd.ts`, политика `approval.askClient`
- **Дополняет**: очередь одобрений M4 и правило атрибуции M5 (`cli:<admin>`, `ui:<admin>`,
  `cli:_unattributed`)

## Контекст

Главный сценарий Stop по Quick start — удержанный вызов, который человек одобряет из второго
терминала за 60 секунд ожидания агента. Прогоны незнакомца показали, что в Claude Code удержание не
видно, а второй терминал — лишнее трение. MCP form elicitation позволяет серверу задать человеку
вопрос в интерфейсе клиента. Баг Claude Code #62319 («запрос посреди вызова сам отклоняется или
висит») закрыт без исправления, поэтому сначала — живая проверка: 2026-10-01 Claude Code 2.1.286 и
2.1.287 объявили `elicitation: {form, url}`, показали окно «MCP server … requests your input … ❯ Accept
Decline · Esc to cancel» для формы с пустой схемой и вернули `accept` / `decline` / `cancel` по
нажатию.

## Решение

1. **Очередь остаётся источником истины.** Пока вызов ждёт, прокси дополнительно шлёт клиенту
   `elicitation/create` (форма с пустой схемой; `mode: "form"` — только клиенту, объявившему `form`).
   Accept и Decline записываются в ту же очередь (`resolve`, первая резолюция выигрывает), дальше
   работает прежний путь: ожидание подхватывает решение, грант, запись в журнал, вызов.
2. **Esc, ошибка, отсутствие ответа — ничего не решают**: вызов ждёт в очереди, как раньше. Сбой
   клиента (баг #62319) не может ни одобрить, ни сломать стоп-кран.
3. **Атрибуция**: резолюция хранится как `client:<имя клиента из initialize>` (символы вне
   `[A-Za-z0-9._-]` заменены, не длиннее 64) — журнал говорит, что одобрили в клиенте.
4. **Кого спрашивать** (до поправки А ниже). Только на пути `wrap`: на `connect` за клиентом сидит пользователь агента, а
   не тот, кто вправе одобрять. Только пока в установке нет админов — ровно правило `approvals approve`
   без токена (`empty`; «установки нет» не считается — конфиг клиента без `MCPCUT_DATA_DIR` не должен
   открывать то, что открывает «никого нет»; база создаётся записью в очередь до вопроса). Проверяется
   перед вопросом и ещё раз при ответе: админ, добавленный посреди сеанса, или ошибка проверки делают
   Accept недействительным, а в stderr `wrap` — команда с токеном. При первом вопросе `wrap` пишет в
   stderr одну строку: что спрашивает в клиенте и как это выключить.
5. **Случайный Enter и вопросы по одному.** Окно открывается с фокусом на Accept: Enter, набранный в
   строку ввода в момент появления окна, одобрил бы вызов. Accept быстрее 1 секунды не засчитывается:
   вопрос задаётся ещё раз с пояснением, второй быстрый Accept оставляет вызов очереди. Быстрый
   Decline засчитывается — отказ не опасное направление. Вопросы идут строго по одному: следующее окно
   открывается только после ответа на предыдущее или его снятия — иначе при нескольких удержанных
   вызовах окно ждало бы в очереди клиента и к показу было бы «старше секунды».
6. **Свои id**: `mcpcut-approval-<случайная метка сеанса>-<approvalId>[-2]`. Ответы на них прокси
   забирает из потока и не пересылает серверу (он не спрашивал), в том числе ответ на уже снятый
   вопрос; метка не даёт серверу угадать или занять такой id — его собственные id с тем же началом
   проходят к нему. Когда вызов решён
   другим путём (терминал, тайм-аут), прокси шлёт клиенту `notifications/cancelled` на свой запрос.
7. **Текст вопроса**: человек одобряет то, что видит, поэтому ничего не обрезается молча. Аргументы —
   по полям: имя каждого поля (до 12 полей, дальше «… and N more fields»), значение через редактор
   секретов и без управляющих символов, до 160 знаков с пометкой «(N more characters)»; если что-то
   скрыто — строка «Not everything is shown. Read it whole: … approvals list --json». Имена инструмента
   и сервера — до 80 знаков, чтобы Decline и Esc оставались в окне.
8. **Выключатель**: `"approval": { "askClient": false }` — для клиента, который отвечает на такие
   вопросы без человека (автоматизация через SDK, режимы без подтверждений). Поле необязательное и без
   значения по умолчанию: отсутствие значит «включено», а `policyHash` существующих политик не
   меняется. Читается при старте сессии, как `approval.timeoutMs`.

## Поправка А (2026-10-02, решение владельца): инструменты, названные админом

Владелец: «нужно, чтобы и у токена агента была возможность подтверждения конкретного тулза, не только у
админа». `approvals approve` с токеном агента не делаем: токен лежит в конфиге клиента агента, модель с
оболочкой его прочтёт и одобрит свой же вызов — стоп-кран исчезает. Вместо этого:

1. **`servers.<имя>.approveInClient: [инструменты]`** (точные имена или `префикс*`, как правила
   инструментов) — админ называет инструменты, которые человек за клиентом вправе подтверждать в
   сессии **на любом stdio-пути** (`wrap` и `connect` агента) **и при админах в установке**. Отвечает
   человек в окне клиента — **при условии, что клиент показывает окно человеку**. Клиент под управлением
   программы (SDK-хост, CI, хост, передающий вопрос модели) ответит сам, и «названный инструмент» станет
   самоодобрением агента; mcpcut этого проверить не может (`clientInfo` клиент называет сам). Для таких
   агентов список пуст или `askClient: false` — сказано в руководстве. Короткий префикс (`"a*"`)
   отдаёт клиенту почти все инструменты — руководство советует перечислять имена.
2. Неназванные удержанные инструменты — как раньше: только `wrap` и только без админов; на `connect` —
   никогда.
3. Правило — в одном месте (`src/proxy/ask-client-rule.ts`) для `wrap` (`wire-policy.ts`) и `connect`
   (`cli/connect-session.ts` → `session/core.ts`), читается **на каждый вопрос** из живой политики и ещё
   раз при ответе. `approval.askClient: false` сильнее списка. Поэтому `askClient` больше не в списке
   «требует перезапуска».
4. Атрибуция прежняя: `client:<имя клиента>`; имя агента уже есть в заявке и в записи решения.
5. HTTP-пути (`serve`, пул, hosted) по-прежнему не спрашивают — часть Б, после запуска.

## Не делаем сейчас

HTTP-пути (`serve`, пул, stateless 2026-07-28): у stateless-сессии нет долгого канала к клиенту, а у
sessionful ответ на вопрос во время удерживаемого POST требует отдельной корреляции — после запуска, по
запросам. Повторный вопрос после Esc, URL elicitation, Cursor — не проверялись.

## Последствия

- Stop в Claude Code — один клик в той же сессии; второй терминал остаётся запасным путём.
- Граница доверия прежняя: агент не может ответить на вопрос сам — его видит человек в интерфейсе
  клиента. Клиент, настроенный отвечать автоматически, одобрит сам — от этого выключатель и правило
  «быстрее секунды не считается» (которое ловит мгновенные автоответы, но не медленные).
