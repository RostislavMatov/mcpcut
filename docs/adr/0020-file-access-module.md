# ADR-0020: файловый модуль — доступ агента к выбранным папкам, корзина, аудит, Postgres и pgvector

- **Статус**: принято (2026-10-03, решения владельца M22 «доступ агентов к файлам по правам, аудит, Postgres,
  pgvector по папкам», M23 «модуль — в 0.4.0» и M24 «базовый режим без Postgres; права — в гранте агента»).
- **Область**: новый каталог `src/files/`; вариант `transport: 'builtin'` в `src/registry/schema.ts`;
  ветки `builtin` в `src/upstream/prepare.ts` и `src/cli/serve-upstream.ts`; поле `files` в гранте агента
  (`src/agents/schema.ts`, наследование через `src/agents/effective.ts`); необязательная проверка аргументов в
  `src/proxy/gate-call.ts`; команда `mcpcut files`; страница Files в веб-UI
- **Дополняет**: ADR-0001 (граница зависимостей — здесь первые необязательные пакеты), ADR-0006 (SQLite остаётся
  хранилищем ядра), ADR-0010 (группы серверов), ADR-0019 (подтверждение в клиенте работает и для файловых
  инструментов)

## Контекст

mcpcut видит и останавливает вызовы MCP-серверов, но сами серверы чужие. Официальный файловый сервер
(`@modelcontextprotocol/server-filesystem`) даёт один общий список папок на всех: нет прав по агентам, нет
режима «только чтение», нет удаления, корзины и аудита. Среди открытых файловых MCP-серверов на 2026-10-03
ни один не сочетает права по агентам, аудит и корзину.

Сценарий владельца (M22): админ выдаёт агенту папки — на машине, где стоит mcpcut, или на сетевом общем
диске — и операции «чтение», «запись», «изменение», «удаление». Права папки наследуются её файлами и
подпапками. Агент через MCP узнаёт, какие папки и файлы ему доступны, и работает только в этих правах.
Удалённое уходит в корзину. Любое событие можно найти: «кто что читал, менял, удалял». На выбранных папках
включается индексация содержимого в pgvector; эмбеддинги считает только локальная модель — содержимое файлов
не уходит ни в какой внешний API.

Две прошлые уязвимости официального сервера задают нижнюю планку проверки путей: CVE-2025-53110 (сравнение
строк `startsWith` без разделителя — `/allowed-evil` проходил как `/allowed`) и CVE-2025-53109 (симлинк
внутри разрешённой папки вёл наружу, проверка была только по строке).

## Решение

### 1. Встроенный сервер внутри того же конвейера

Файловый сервер — не отдельный процесс, а новый вид upstream: запись реестра `{ transport: 'builtin',
kind: 'files' }`. Ветки `builtin` в `prepareUpstream` и `openUpstream` отдают пару `MessageSource` /
`MessageSink`, которая отвечает на `initialize`, `tools/list` и `tools/call` в том же процессе. Всё, что
стоит между клиентом и сервером, работает без изменений: запись в журнал со скрытием секретов и цепочкой
хешей, решение политики по инструменту, `confirmInClient`, очередь одобрений, гранты агента.

Модуль требует личность агента: права — у агента. Поэтому он доступен через `connect` (токен агента) и
`serve` (HTTP-пул); у `wrap` нет агента, и встроенный сервер там не запускается. Один разработчик заводит
агента для себя (`mcpcut agent create me`). В hosted-режиме (ADR-0017) встроенный сервер выключен, пока не
решено, чьи папки у арендатора.

Инструменты:

| Инструмент | Операция | Что делает |
|---|---|---|
| `list_roots` | — | папки агента и его операции в каждой |
| `list_directory`, `get_file_info` | read | содержимое папки, сведения о файле |
| `read_file` | read | текст файла; предел размера, двоичные файлы — отказ с подсказкой |
| `search_files` | read | поиск по смыслу в проиндексированных папках, только в пределах прав агента |
| `write_file`, `create_directory` | write | новый файл или папка; перезапись существующего — операция edit, а с `expectedSha256` ещё и read |
| `edit_file` | read + edit | правки по образцу с необязательным `expectedSha256` — защита от одновременной правки двумя агентами; read нужен, потому что ответы правки («найдено один раз / не найдено») позволяют угадывать содержимое |
| `move_file` | delete на исходном + write на новом месте | перемещение и переименование; read и edit, которые есть на новом месте, должны быть и на исходном, иначе отказ с названием права (перенос из «почтового ящика» с одним delete в папку с read читал бы то, что читать нельзя) |
| `delete_file` | delete | перенос файла или папки в корзину; ответ агенту содержит только id записи и фразу «администратор восстановит», без пути корня |

Классы инструментов (чтение, запись, разрушающее) заданы в описании сервера, поэтому `servers.files.tools`
в политике и `confirmInClient` работают как для любого сервера: например, `delete_file` можно поставить на
подтверждение в клиенте или на одобрение админа.

### 2. Права — в гранте агента, с наследованием

Права лежат рядом с остальными правами агента: необязательное поле гранта `files: { paths: [{ path, ops }] }`.
Так они наследуются через группы (ADR-0010), подхватываются на лету наблюдателем агента, видны и правятся
там же, где гранты, — в CLI и на веб-странице.

- Админ сначала объявляет корни: папки, с которыми вообще работает модуль (`mcpcut files root add <путь>`).
  Путь в праве агента обязан лежать внутри корня.
- Действует самое точное правило: право на `/data/a` распространяется на всё внутри, право на `/data/a/secret`
  с пустым списком операций вырезает подпапку.
  Правила на одной папке складываются, но пустое правило побеждает в равенстве: вырезание в одной группе не
  отменяется правом другой группы.
- Правило сравнивается по идентичности папки (устройство и inode), а не по написанию пути. Путь правила хранится в
  каноническом виде при выдаче; если на проверке он ведёт в другое место (папку подменили симлинком) или не
  разрешается, закрывается весь файловый доступ агента с подсказкой «перевыдайте право» — тихо выбросить правило
  значило бы отменить вырезание. Правило на ещё не существующую папку сравнивается по пути со складыванием
  регистра и юникода там, где их складывают тома.
- Права проверяются дважды: в гейте — новый необязательный шаг `argsCheck` в `gate-call.ts`, который может
  только ужесточить решение (как `enforceCatalogTrust`), и в журнале остаётся отказ с причиной вида
  `files: no right delete on /data/a/x`; и ещё раз внутри сервера перед каждым действием. `decide()` остаётся
  чистой функцией без ввода-вывода. Какому инструменту какие права нужны, определено в одном месте —
  `tool-access.ts`; им пользуются и сервер, и проверка гейта, поэтому они не расходятся.
- Папка не прячет правила внутри себя (ревью 04.10, H1). Перед `move_file` (источник — папка) и `delete_file`
  (цель — папка) проверяется, не лежит ли строго внутри неё чьё-то правило агента или объявленный корень (сравнение
  `isWithinOn` по `lexicalKey`, то есть с NFC и регистром там, где их складывают). Если лежит — отказ одной строкой:
  `<путь> contains a separately granted folder <внутренняя>; move or delete what is inside instead, or ask an
  administrator`. Иначе перенос папки с вырезанием или с подпапкой «только чтение» вынес бы её из-под правил.
  Проверка общая для сервера и гейта (`access-checks.ts`): гейт берёт тот же контекст (правила и корни) и тот же
  путь, так что отказ попадает в журнал как `deny` с правилом `files: separately granted folder inside`.

### 3. Проверка путей

Один модуль `src/files/paths.ts`, на каждом вызове:

1. Отказ сразу: NUL-байт, пустой путь, на Windows — альтернативные потоки (`file:stream`), зарезервированные
   имена (`CON`, `NUL`…), точки и пробелы в конце имени.
2. До любого обращения к диску по пути цели — лексическая проверка: путь как написан лежит под корнем (как объявлен
   или как канонический). Иначе `\\чужой-сервер\папка` заставил бы Windows подключиться и предложить учётные данные;
   пути устройств и расширенные пути (`\\.\`, `\\?\`) отвергаются сразу.
3. `realpath.native` цели; для несуществующей цели — ближайшего существующего родителя плюс оставшиеся имена.
   Корни приводятся к `realpath.native` заново на каждом вызове.
4. Решение — по идентичностям (устройство, inode) существующих предков цели: самый глубокий корень среди них, и
   корзина любого корня среди них — отказ. Написание — NFC или NFD на macOS (`realpath` их не выравнивает,
   проверено ревью 03.10), регистр, короткие имена 8.3 — не делает одну папку похожей на другую. Складывать регистр
   в строках нельзя: на чувствительном к регистру томе это открыло бы чужую папку.
5. Открытие с `O_NOFOLLOW` там, где он есть, и сверка `dev`/`ino` открытого дескриптора с проверенным путём —
   окно между проверкой и открытием закрыто. Запись — во временный файл рядом и `rename` поверх.
6. Файл с несколькими жёсткими ссылками (`nlink > 1`) нельзя менять и удалять: вторая ссылка может лежать вне
   корня. Чтение разрешено.
7. Идентичности должны быть надёжными (ревью 04.10, M3). Некоторые тома SMB/NFS/FUSE отдают inode 0 или одну
   идентичность на все папки — тогда вложенность рассыпалась бы. Поэтому: запись цепочки с `ino = 0` от цели до
   корня — отказ `unresolvable` с пояснением, что идентичности на этой файловой системе ненадёжны; две разные
   папки цепочки с одной идентичностью — тоже; корень, чья идентичность равна идентичности его корзины или у
   которого (или у корзины) inode 0, считается непригодным: проверка путей его пропускает (закрыто по умолчанию), а
   `mcpcut files root add` отказывает одной строкой «не отдаёт стабильных идентичностей, папку нельзя безопасно
   отдать» и убирает только что созданную корзину.
8. Папка корзины `.mcpcut-trash` недоступна ни одному инструменту: по идентичности, и имя, которое какой-то том
   примет за неё (регистр, NFKC — `ſ` это `s`, точки и пробелы в конце), отвергается на любой глубине. Корзину
   создаёт mcpcut при объявлении корня, чтобы агент не создал её первым. Уже существующую корзину
   `files root add` принимает, только если на POSIX её режим ровно 0700 и в ней лежат лишь записи формы mcpcut
   (`<ulid>`, `<ulid>.json`, временный `.manifest-<ulid>.tmp`; ревью 04.10, M4), иначе отказ одной строкой с советом
   осмотреть и удалить или переименовать её.
9. Остаточное окно между проверкой и системным вызовом сужено (ревью 04.10, H2): родитель и источник
   проверяются заново непосредственно перед каждым `rename` и каждым созданием; после создания файла сверяются
   `realpath` (внутри корня) и идентичность (`lstat` = `fstat` дескриптора), иначе файл удаляется только если он
   всё ещё наш (`removeIfSame`); после переноса целевой путь должен иметь записанную идентичность, иначе
   `changed` (файл откатывается ссылкой — безопасно; папка — обратным `rename`, если старое место свободно).
   Файлы переносятся `link` + `unlink`, а не `rename`: запись, появившаяся на новом месте, даёт EEXIST и не
   затирается (папки остаются на `rename`; на томе без жёстких ссылок — откат к `rename`).

Регрессионные тесты повторяют обе CVE, симлинк на файл и на папку, `..`, юникод в NFC и NFD, регистр на
нечувствительном томе, UNC-пути и подключённые диски Windows.

### 4. Корзина

`delete_file` переносит файл или папку в `<корень>/.mcpcut-trash/<ulid>/<путь от корня>` — тот же том, поэтому
это `rename`, и на сетевом диске тоже. Рядом — манифест: кто, когда, откуда, хеш (хеш считается по сохранённой копии после переноса; `restore` сверяет его и при расхождении отказывает). Восстанавливает и очищает
корзину только админ (`mcpcut files trash list | restore | purge`, страница Files); агент не видит корзину.
Срок хранения — 30 дней, затем очистка при старте `serve` и раз в сутки. Известные пределы: падение между переносом и записью манифеста оставляет «сироту» (папку без манифеста) — админ удаляет её руками; `write_file` выдаёт факт существования имени; `list_directory` показывает имена вырезанных подпапок; квот на место нет.

### 5. Аудит

Каждый вызов уже лежит в журнале: агент, инструмент, путь (аргументы скрываются по тем же правилам), решение,
ответ. Это доказательство — журнал защищён цепочкой хешей с внешним якорем. Для быстрого ответа «кто трогал
`/data/a/x`» добавляются `mcpcut files audit --path | --agent | --since` и раздел на странице Files. С Postgres
те же события дублируются в таблицу `file_events` с индексами по пути, агенту и времени и ссылкой на запись
журнала; источник истины остаётся в журнале.

### 6. Postgres и pgvector

Postgres хранит данные модуля, к которым одновременно обращаются несколько агентов: каталог файлов корней
(путь, размер, время изменения, хеш), `file_events`, записи корзины и куски с векторами. Права и журнал
остаются в SQLite ядра (ADR-0006) — у них уже есть наследование, наблюдение на лету и цепочка хешей.

- Клиент — `pg` (MIT). Строка подключения — секрет в сейфе (`vault:files-pg-url`), в конфиге только имя.
- Миграции — файлы `migrations/NNN_*.sql` и таблица `schema_migrations`; при старте `pg_advisory_lock`,
  каждая миграция в своей транзакции.
- `mcpcut files db init` печатает готовую команду для Postgres с pgvector
  (`docker run … pgvector/pgvector:pg18`, порт только на `127.0.0.1`) и следующую команду с настоящими значениями.
- Каталог обновляется сразу после каждой записи через модуль и периодическим обходом корней (время изменения,
  размер). Наблюдатель файловой системы не используется: на сетевых дисках он ненадёжен, а обход нужен всё равно.
- Индексация включается на папке и наследуется её содержимым; выключение на подпапке вырезает её. Модель по
  умолчанию — `multilingual-e5-small` (русский и английский, 384 измерения, ≈ 118 МБ, int8), имя модели и
  размерность хранятся вместе с векторами. `search_files` фильтрует результаты по правам агента в SQL-запросе:
  поиск не может стать обходом прав.
- Перед индексацией содержимое проходит то же скрытие секретов, что и журнал; файлы вида `.env`, ключи и
  сертификаты не индексируются.

### 7. Необязательные зависимости

Ядро остаётся с двумя прод-зависимостями (ADR-0001). `pg` и `@huggingface/transformers` (с onnxruntime-node)
ставятся только при включении модуля в отдельный каталог `~/.mcpcut/modules` с закреплёнными версиями
(`mcpcut files setup`) и загружаются через `import()`. Если пакета нет, команда говорит одной строкой, что
выполнить. Пакет `mcpcut` и первая минута для тех, кому модуль не нужен, не тяжелеют.

## Два режима (M24)

- **Базовый, без Postgres**: корни, права, все инструменты кроме `search_files`, корзина, аудит по журналу. Модуль
  проверяется за минуту без установки базы, и при сдвиге сроков базовая часть выходит независимо.
- **С Postgres**: дополнительно каталог, `file_events` для быстрого аудита и `search_files` по проиндексированным папкам.

Права агента на папки — в его гранте (SQLite ядра), а не в Postgres: наследование через группы, правка в CLI и UI и
наблюдение на лету уже есть, а несколько агентов работают через один mcpcut.

## Отвергнуто

- **Готовый файловый сервер за прокси с правилами по аргументам.** Нет удаления, корзины и прав по агентам;
  проверять пути снаружи чужого сервера — значит угадывать, как он их разрешает.
- **Права в `policy.json`.** В политике нет агентов (кроме `confirmInClient`), она правится файлом и
  перечитывается целиком; права на папки — данные агента, как гранты.
- **Наблюдатель файловой системы (chokidar, `fs.watch`).** На SMB и NFS события от других машин не приходят;
  периодический обход нужен в любом случае.
- **Эмбеддинги через внешний API.** Содержимое файлов ушло бы наружу — против решения владельца и обещания
  продукта.
- **PGlite (встроенный Postgres).** Проверен 2026-10-03 — pgvector работает, но одно подключение на процесс; к
  данным модуля обращаются несколько агентов и процессов (решение владельца M22).

## Последствия

- (+) Права, журнал, политика, подтверждение в клиенте и одобрения работают для файлов так же, как для любого
  сервера; новый код — сервер, проверка путей, корзина, каталог.
- (+) Аудит «кто что трогал» опирается на журнал с цепочкой хешей, а не на отдельный лог, который можно
  переписать.
- (−) Первые необязательные зависимости и внешняя база; установка модуля — отдельный шаг.
- (−) Полный аудит возможен, только если агент добирается до папок лишь через mcpcut. Если клиент агента
  работает на той же машине под тем же пользователем ОС, его встроенные инструменты (Read, Bash) идут мимо
  журнала — это та же граница доверия, что и у сейфа. В документации — прямо и с рецептом: папки на сервере
  с mcpcut или под отдельным пользователем ОС.
- (−) Жёсткие ссылки и регистр имён на разных томах — источник ошибок; закрыты правилами раздела 3 и тестами.

## Когда пересматриваем
