# ADR-0006: Хранилище — SQLite (`node:sqlite`, WAL) двумя базами вместо JSON-файлов под межпроцессным локом

- **Статус**: принято (2026-08-13). Гейт рантайма пройден, пол зафиксирован на **Node 24 LTS**
  (см. «Условие принятия»)
- **Область**: `src/lockfile.ts` (удаляется), `src/policy/store.ts` (`createJsonStore`),
  `src/registry/store.ts`, `src/agents/store.ts`, `src/admin/store.ts`, `src/policy/inventory-store.ts`,
  `src/policy/approvals/**`, `src/journal/**`; новый `src/store/sqlite.ts`
- **Основание**: замеры 2026-08-13 (ниже), PRD `.claude/prds/storage-architecture-sqlite.prd.md`,
  бэклог ROADMAP (окно CAS, кэш `agents.json`, retention `approvals/resolved`), требования M5
  из треда ECZ-ID

## Контекст

Всё контрольное состояние (реестр, агенты, админы, инвентарь тулзов, очередь одобрений) лежит в
JSON-файлах, которые перезаписываются целиком под межпроцессным локом (`src/lockfile.ts`,
362 строки, с nonce-владением и восстановлением битого чужого лока). Журнал — per-session JSONL,
`appendFile` на запись, без `fsync`, с политикой fail-open (один ретрай → дроп со счётчиком).
Писателей три класса: CLI, `serve`, `ui` — плюс по процессу на каждую `connect`-сессию.

Замеры на рабочей машине (Node v25.6.0, macOS/APFS, 20 000 записей ~380 байт, поверх реальных
модулей из `dist/`):

| Операция | Сейчас | SQLite WAL |
|---|---|---|
| Журнал, 1 сессия | 18 387 rec/с (без `fsync`) | 181 934 rec/с (txn по 256, `synchronous=NORMAL`) |
| Журнал, 64 сессии | 16 661 rec/с | 193 356 rec/с (`synchronous=FULL`) |
| `store.update()`, 200 агентов | 471 упд/с | 40 361 упд/с |
| `store.update()`, **8 процессов** | **553 упд/с суммарно** | — |
| `store.read()` (на каждый HTTP-запрос и полл отзыва) | 1 071 чт/с, O(файла) | 426 792 чт/с, индекс |
| Поиск по журналу | полный скан JSONL | 0.36 мс, индекс |
| sha256-цепочка (нагрузка M5) | — | 210 691 rec/с |

Оговорка: на macOS `fsync` не гонит кэш накопителя (нужен `F_FULLFSYNC`), поэтому durable-числа
на Linux/ext4 будут ниже; порядки величин это не меняет. Скрипты бенчмарков переносятся в
репозиторий первой волной.

Из цифр следуют четыре факта, а не один:

1. **Запись состояния не масштабируется вовсе**: восемь конкурирующих процессов дают ту же
   пропускную способность, что один. Лок сериализует, а каждое обновление — это чтение всего
   файла, валидация zod, перезапись и `rename`.
2. **Чтение дороже записи по совокупности**: 0.93 мс × (каждый запрос агента + полл отзыва каждой
   сессии), растёт линейно с числом агентов. Это пункт бэклога «кэш `agents.json` по mtime», но
   кэш лечит симптом, а не модель доступа.
3. **Журнал недолговечен**: `appendFile` без `fsync` — подтверждённая агенту запись живёт в page
   cache до падения хоста. Для продукта, чей тезис — доказательный журнал, это дыра в самом
   заявлении.
4. **Главное: M5 на этой раскладке не строится честно.** Хеш-цепочка требует атомарного «прочитать
   предыдущее звено — записать следующее». Сегодня каждая сессия пишет свой файл из своего
   процесса. Глобальная цепочка потребовала бы общего лока на каждую запись — то есть падения
   журнала с 18 000 до 553 записей/с. Цепочка «на файл» доказывает только порядок внутри файла:
   **удаление целого файла сессии не обнаруживается ничем**. Решение о хранилище стоит на
   критическом пути следующего milestone, а не «когда-нибудь потом».

## Решение

**Контрольное состояние и журнал переезжают на SQLite через встроенный `node:sqlite`, в режиме
WAL, двумя раздельными базами. Межпроцессный лок удаляется.**

```
~/.mcp-journal/
  state.db      WAL, synchronous=NORMAL   реестр, агенты, админы, инвентарь, очередь одобрений
  journal.db    WAL, synchronous=FULL     записи трафика + звенья хеш-цепочки (M5)
  vault.enc     без изменений — ADR-0003
  vault.key     без изменений — ADR-0003
  policy.json   без изменений — единственный hand-edited файл (решение M3)
```

1. **`node:sqlite`, не npm-пакет.** Модуль — часть рантайма, поэтому инвариант ADR-0001 «ровно две
   прод-зависимости» сохраняется буквально, а поверхность цепочки поставки не растёт.
2. **Две базы, не одна.** Журнальный поток (тысячи коммитов) и контрольное состояние (единицы в
   час) не делят writer-лок, политику `synchronous`, расписание бэкапа и архивацию.
3. **Батчевые коммиты журнала** (256 записей или 10 мс, что раньше). SQLite допускает одного
   писателя за раз на базу — батчинг превращает тысячи записей/с в единицы коммитов/с на процесс,
   и конкуренция писателей вырождается. Это не оптимизация, а условие работоспособности.
4. **Шов уже существует**: `createJsonStore(read/update)` переписывается изнутри на транзакцию,
   все шесть сторов меняются без правки вызывающего кода. Read-modify-write под транзакцией даёт
   настоящий CAS и закрывает известное окно между проверкой владения локом и `rename`.
5. **`src/lockfile.ts` удаляется** вместе с классом отказов «протухший чужой лок / восстановление /
   holder-nonce»; `StoreLockLostError` вырождается в конфликт транзакции с ретраем.
6. **Вся работа с `node:sqlite` — в одном адаптере `src/store/sqlite.ts`** (PRAGMA-набор,
   открытие, ретраи). Тот же приём, что с `src/protocol/mcp.ts` для спеки: экспериментальный API
   имеет ровно одну точку правки.
7. **Границы не двигаются**: вольт остаётся отдельным AEAD-конвертом (модель угроз ADR-0003 не
   улучшается от переезда, а смешение секретных значений с plaintext-БД её ухудшает); `policy.json`
   остаётся hand-edited; редакция как единственный путь к персистенции лежит выше хранилища и не
   затрагивается; права 0600/0700 сохраняются.

Выбирая **SQL**, а не собственный формат, мы оставляем открытым путь на PostgreSQL, если партнёр
потребует HA: переносится схема, а не архитектура.

## Условие принятия (гейт)

`node:sqlite` требует Node ≥ 22 (в 20.x LTS модуля нет — **проверяется прямым прогоном на
CI-матрице до любой другой работы**), а в v25.6.0 всё ещё печатает `ExperimentalWarning`. Пока
гейт не пройден, статус ADR — «предложено». Отказ от подъёма пола рантайма отменяет решение
целиком, а не переделывает его: тогда действует «минимальный фикс» из отвергнутых вариантов, и
M5 требует отдельного решения по цепочке.

**Результат гейта (2026-08-13)** — прогон на версиях CI-матрицы (официальные бинарники
nodejs.org, darwin-arm64):

| Рантайм | `node:sqlite` |
|---|---|
| v20.20.2 (latest 20.x) | нет — `ERR_UNKNOWN_BUILTIN_MODULE` |
| v22.23.2 (latest 22.x) | есть без флага (`DatabaseSync`, `StatementSync`, `constants`, `backup`); `ExperimentalWarning`; класса `Session` нет |
| v24.19.0 (latest 24.x) | есть без флага, полный набор включая `Session` (changesets) |

Гейт пройден. **Пол рантайма зафиксирован на Node 24 LTS** (а не минимальном 22): Node 20 вышел
из поддержки в апреле 2026, а 24 даёт полный API `node:sqlite`. CI-матрица и `engines`
переведены на `>=24`.

**Поправка 2026-09-18 (`ExperimentalWarning` на стороне пользователя).** Предупреждение, названное
выше как свойство рантайма, печаталось двумя строками stderr на каждую команду и попадало в шапку
`run/ui.log` и `run/serve.log` — первое, что читает оператор, ищущий настоящую проблему (смок
сквозного пути 2026-09-18, UX-7). CLI теперь гасит **ровно это одно** предупреждение
(`src/cli/warning-filter.ts`): своя замена слушателя `'warning'`, которая пропускает всё остальное,
а не `--no-warnings`, который скрыл бы и настоящий deprecation будущего рантайма. Побочное
следствие в этом ADR: адаптер берёт значения драйвера через `createRequire`, а типы — через
стираемый `import type`, потому что встроенный ES-модуль компилируется на фазе **линковки** графа
входа, до первой строки любого тела модуля; так момент загрузки сдвинулся внутрь эволюации
`src/store/sqlite.ts`. Единственная точка контакта с `node:sqlite` от этого не изменилась, и
архитектурный тест по-прежнему видит один файл.

## Что отвергнуто и почему

| Вариант | Почему нет |
|---|---|
| **Оставить файлы, добавить `revision`-CAS и батчинг журнала** (минимальный фикс) | Чинит два симптома из пяти: не даёт кросс-процессной цепочки для M5, индексного поиска, retention и масштабирования чтения — и оставляет lockfile со всей логикой восстановления. Больше кода ради меньшего результата |
| **`better-sqlite3` / LMDB (npm)** | Нативный модуль с prebuild-бинарником в цепочке поставки продукта, который партнёр проверяет на аудите. Ровно та зависимость, которую ADR-0001 и ADR-0004 отказались брать даже ради htmx |
| **PostgreSQL или любая сетевая СУБД** | Ломает self-hosted-онбординг «10 минут» и добавляет сетевую поверхность. Путь остаётся открытым через выбор SQL, но не в MVP |
| **Одна общая база** | Общий writer-лок для двух несопоставимых профилей записи; одна политика `synchronous` на оба; архивация журнала тянет за собой состояние |
| **Перенос вольта в БД** | Модель угроз ADR-0003 не улучшается, а секретные значения в plaintext-БД ухудшают поверхность |
| **Свой append-only лог с индексом в памяти** | Это написание СУБД. Против KISS и против позиционирования «мы контроль доступа, а не хранилище» |
| **Демон-писатель с сокетом** (единая точка записи) | YAGNI: измеренный запас батчевых коммитов — два порядка. Порог возврата назван ниже |

## Последствия

- (+) Потолок записи состояния снимается (553 → десятки тысяч упд/с), чтение становится
  индексным (1 071 → сотни тысяч чт/с) — пункт бэклога «кэш `agents.json`» отпадает вместе с
  причиной.
- (+) Запись журнала и её звено цепочки коммитятся **одной транзакцией** — M5 становится
  реализуемым; сегодня падение между append и обновлением цепи оставило бы непроверяемый разрыв.
- (+) Retention появляется как `DELETE ... WHERE`, а не как обходчик каталогов: закрываются пункты
  бэклога про `approvals/resolved` и историю дескрипторов.
- (+) WAL: читатели не блокируют писателя — браузер журнала в UI перестаёт конкурировать с прокси
  за те же файлы.
- (+) `db.backup()` даёт консистентный горячий снапшот вместо «скопируйте каталог и надейтесь».
- (+) Минус 362 строки лока и целый класс отказов.
- (−) **Пол рантайма поднимается до Node 24 LTS** (решение по итогам гейта); CI-матрица и
  `engines` меняются на `>=24`.
- (−) **Экспериментальный API** с предупреждением в проде; смягчение — один адаптер и пин версий.
- (−) **Радиус повреждения растёт**: битый файл терял один стор, битая база теряет всё состояние.
  Смягчение: две базы, `PRAGMA integrity_check` при старте, миграция не удаляет исходные файлы до
  подтверждения.
- (−) **Журнал перестаёт грепаться.** Операторская инспектируемость компенсируется
  `journal export --jsonl` (он всё равно нужен для аудит-экспорта M5) и наличием `sqlite3` везде.
- (−) **Бэкап меняет семантику**: `-wal`/`-shm`, копирование «на живую» больше не корректно —
  только `backup()`/`VACUUM INTO`. Правка README обязательна в той же волне.
- (=) Компрометация хоста или того же uid по-прежнему не покрывается: ребёнок под тем же uid может
  испортить базу так же, как портил файлы. Хранилище здесь ничего не меняет; закрытие — отдельный
  uid писателя / append-only / отгрузка off-box, пункт бэклога M5.

## Когда пересматриваем

- **Гейт не пройден** (нет `node:sqlite` на приемлемом поле рантайма) — решение отменяется целиком,
  см. «Условие принятия».
- **Контенция писателей**: если доля времени в ожидании writer-лока превысит 5% на реальной
  нагрузке партнёра — возвращаемся к варианту «демон-писатель с сокетом» отдельным ADR.
- **Партнёр требует HA/кластер** — Postgres-ветка; переносится схема, и это отдельное решение.
- **Требование «журнал отгружаем off-box»** (бэклог M5) окажется несовместимым с `.db` — тогда
  пересматривается формат журнальной базы, но не состояния.
- **`node:sqlite` меняет API** — правка в одном адаптере; смена мажорного поведения (например,
  отказ от синхронного API) — повод перепроверить решение.

## Связанные решения

- ADR-0001 — граница зависимостей (два прод-пакета), которую это решение обязано сохранить и
  сохраняет: `node:sqlite` встроен в рантайм.
- ADR-0003 — вольт и граница доверия «учётная запись ОС»: не меняется ни в плюс, ни в минус.
- ADR-0004 — третий писатель в сторы (UI) назван последствием с обострением узких мест лока; это
  решение снимает саму причину.
- ADR-0005 — `policy.json` остаётся вне БД, правило выбора источника не затрагивается.
- PRD `.claude/prds/storage-architecture-sqlite.prd.md` — метрики успеха, фазы и открытые вопросы.
